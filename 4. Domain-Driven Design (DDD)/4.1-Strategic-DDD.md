## Ubiquitous Language

### Tại sao quan trọng?

Ubiquitous Language là ngôn ngữ chung giữa **developers** và **domain experts**.
Khi developer nói "User" nhưng business nói "Customer", khi code dùng `processOrder()` nhưng
business nói "fulfill an order" — bugs xuất hiện vì **translation errors**.

### ❌ Bad: Developer tự đặt tên theo kiểu kỹ thuật

```typescript
class DataProcessor {
  async handleRecord(data: Record<string, unknown>): Promise<void> {
    // "handle" nghĩa là gì? Business hỏi: approve hay reject?
    if (data.status === 'P') {        // 'P' = Pending? Paid? Processing?
      await this.updateFlag(data.id, true);  // "flag" gì?
    }
  }
}
```

### ✅ Good: Code phản ánh chính xác ngôn ngữ domain

```typescript
// Business nói: "Underwriter reviews a loan application and either approves or declines it"
class LoanApplication {
  approve(underwriter: UnderwriterId, reason: ApprovalReason): void {
    if (this.status !== ApplicationStatus.UnderReview) {
      throw new InvalidApplicationStateError(
        `Cannot approve application in ${this.status} status`
      );
    }
    this.status = ApplicationStatus.Approved;
    this.approvedBy = underwriter;
    this.addDomainEvent(new LoanApplicationApproved(this.id, underwriter, reason));
  }

  decline(underwriter: UnderwriterId, reason: DeclineReason): void {
    if (this.status !== ApplicationStatus.UnderReview) {
      throw new InvalidApplicationStateError(
        `Cannot decline application in ${this.status} status`
      );
    }
    this.status = ApplicationStatus.Declined;
    this.addDomainEvent(new LoanApplicationDeclined(this.id, underwriter, reason));
  }
}
```

### Cách xây dựng Ubiquitous Language

| Bước | Hoạt động | Kết quả |
|------|-----------|---------|
| 1 | Ngồi với domain experts, lắng nghe cách họ nói về công việc | Danh sách thuật ngữ thô |
| 2 | Hỏi lại: "Khi bạn nói X, ý bạn là...?" | Thuật ngữ rõ nghĩa |
| 3 | Viết glossary — mỗi term có definition + example | Domain Glossary |
| 4 | Đưa thuật ngữ vào code: class names, method names | Code = Ubiquitous Language |
| 5 | Review liên tục — language evolve theo thời gian | Living document |

```typescript
/**
 * DOMAIN GLOSSARY — Order Management Context
 *
 * Order:       Đơn hàng do Customer đặt. Chứa >= 1 Line Items.
 * Line Item:   Một sản phẩm cụ thể trong Order, có quantity và unit price.
 * SKU:         Stock Keeping Unit — mã duy nhất cho mỗi variant sản phẩm.
 * Fulfillment: Quá trình chuẩn bị và giao hàng cho Order.
 * Shipment:    Một lần vận chuyển. Một Order có thể có nhiều Shipments.
 * Return:      Customer gửi trả hàng. Khác với Refund (hoàn tiền).
 */
```

### Khi nào dùng / Khi nào KHÔNG dùng

| Dùng | Không cần |
|------|-----------|
| Domain phức tạp với nhiều thuật ngữ chuyên ngành | CRUD app đơn giản (todo list, blog) |
| Team > 3 người, cần common understanding | Solo developer, domain quá quen thuộc |
| Hệ thống sống lâu, cần onboard members mới | Prototype sẽ vứt đi |

## Bounded Context

Bounded Context là **ranh giới** mà trong đó một Ubiquitous Language cụ thể có ý nghĩa.
Cùng một từ, ở hai Bounded Context khác nhau, có thể mang nghĩa hoàn toàn khác.

```
"Account" trong 3 contexts:
- Banking Context:     Account = tài khoản ngân hàng (balance, transactions)
- Identity Context:    Account = tài khoản đăng nhập (email, password, roles)
- Accounting Context:  Account = tài khoản kế toán (debit/credit entries)
```

### ❌ Bad: Một model dùng chung cho mọi contexts

```typescript
// God model — mọi context nhét vào cùng 1 class
class User {
  // Identity context
  id: string; email: string; passwordHash: string; roles: string[];
  // Order context
  shippingAddresses: Address[]; orders: Order[]; cart: CartItem[];
  // Billing context
  paymentMethods: PaymentMethod[]; taxId: string; invoices: Invoice[];
  // Marketing context
  segments: string[]; referralCode: string; lifetimeValue: number;
}
// Kết quả: class 500+ fields, mọi team sửa cùng 1 file, merge conflicts liên tục
```

### ✅ Good: Mỗi context có model riêng

```typescript
// === Identity Context — chỉ quan tâm authentication ===
class UserAccount {
  constructor(
    readonly id: UserId, private email: Email,
    private passwordHash: string, private roles: Set<Role>,
  ) {}
  authenticate(password: string): AuthResult { /* ... */ }
}

// === Order Context — "User" ở đây là Customer ===
class Customer {
  constructor(
    readonly customerId: CustomerId,  // = UserId từ Identity context
    private name: string,
    private shippingAddresses: ShippingAddress[],
  ) {}
  placeOrder(items: OrderItem[], address: ShippingAddress): Order { /* ... */ }
}

// === Billing Context — chỉ cần billing info ===
class BillingAccount {
  constructor(
    readonly accountId: BillingAccountId,
    private customerId: CustomerId,  // reference by ID only
    private paymentMethods: PaymentMethod[],
  ) {}
  charge(amount: Money, description: string): PaymentResult { /* ... */ }
}
```

### Cách xác định boundaries

| Signal | Giải thích |
|--------|-----------|
| Cùng từ, khác nghĩa | "Product" trong Catalog != "Product" trong Warehouse |
| Khác team ownership | Team A quản lý orders, Team B quản lý inventory |
| Khác lifecycle | Customer profile ít đổi, Orders tạo liên tục |
| Khác consistency requirements | Payment cần strong consistency, Analytics cần eventual |

## Context Mapping

Context Map mô tả **mối quan hệ** giữa các Bounded Contexts. Có 8 patterns chính:

### 1. Shared Kernel

Hai contexts chia sẻ một phần code/model nhỏ. Cả hai team cùng own phần shared.

```typescript
// shared-kernel/src/types.ts — Cả Order và Shipping context dùng chung
export class Money {
  constructor(readonly amount: number, readonly currency: Currency) {
    if (amount < 0) throw new InvalidMoneyError('Amount cannot be negative');
  }
  add(other: Money): Money {
    this.ensureSameCurrency(other);
    return new Money(this.amount + other.amount, this.currency);
  }
  private ensureSameCurrency(other: Money): void {
    if (this.currency !== other.currency)
      throw new CurrencyMismatchError(this.currency, other.currency);
  }
}
// → Dùng khi overlap tự nhiên. KHÔNG dùng khi contexts evolve ở tốc độ khác nhau.
```

### 2. Customer-Supplier

Upstream cung cấp data/API cho downstream. Downstream có quyền yêu cầu thay đổi.

```typescript
// Upstream: Product Catalog (Supplier) — downstream có thể yêu cầu thêm endpoint
interface ProductCatalogService {
  getProduct(productId: ProductId): Promise<ProductDto>;
  getProductPricing(productId: ProductId): Promise<PricingDto>;
}

// Downstream: Order context (Customer) — gọi upstream API
class OrderService {
  constructor(private readonly productCatalog: ProductCatalogService) {}

  async createOrder(customerId: CustomerId, items: OrderItemRequest[]): Promise<Order> {
    const products = await Promise.all(
      items.map(item => this.productCatalog.getProductPricing(item.productId))
    );
    return Order.create(customerId, items.map((item, i) =>
      OrderItem.create(item.productId, products[i].price, item.quantity)
    ));
  }
}
```

### 3. Conformist

Downstream **phải chấp nhận** model của upstream, không có quyền thay đổi.

```typescript
// Upstream: Stripe — họ không thay đổi API vì bạn yêu cầu
interface StripeCharge {
  id: string;
  amount: number;       // cents, không phải dollars
  currency: string;
  status: 'succeeded' | 'pending' | 'failed';
}
// → Dùng khi cost build ACL quá cao. KHÔNG dùng khi external model quá khác domain.
```

### 4. Anti-Corruption Layer (ACL) — Pattern quan trọng nhất

Translation layer chuyển đổi external model sang domain model riêng.

```typescript
// Domain model — pure, không biết gì về Stripe
class Payment {
  constructor(
    readonly id: PaymentId, readonly orderId: OrderId,
    readonly amount: Money, readonly status: PaymentStatus,
  ) {}
}

// ACL translates Stripe → Domain
class StripePaymentAdapter implements PaymentGateway {
  constructor(private readonly stripe: Stripe) {}

  async charge(orderId: OrderId, amount: Money, method: PaymentMethodToken): Promise<Payment> {
    const stripeCharge = await this.stripe.charges.create({
      amount: Math.round(amount.amount * 100),  // Money → cents
      currency: amount.currency.toLowerCase(),
      source: method.value,
    });
    return new Payment(
      PaymentId.generate(), orderId, amount,
      this.mapStatus(stripeCharge.status),  // string → enum
    );
  }

  private mapStatus(s: string): PaymentStatus {
    const map: Record<string, PaymentStatus> = {
      'succeeded': PaymentStatus.Completed,
      'pending': PaymentStatus.Pending,
      'failed': PaymentStatus.Failed,
    };
    return map[s] ?? PaymentStatus.Failed;
  }
}
// → Dùng khi integrate third-party. KHÔNG dùng khi external model gần giống domain.
```

### 5. Open Host Service (OHS)

Context expose **public API chuẩn** cho nhiều consumers. Versioned, documented.

```typescript
// Published API — ổn định, slim
interface ProductApiV1 {
  id: string; name: string; description: string;
  price: { amount: number; currency: string };
  availability: 'in_stock' | 'out_of_stock' | 'preorder';
}

// Internal domain model — richer, tự do thay đổi
class Product {
  private pricing: PricingStrategy;  // Complex bulk/tiered pricing
  private categories: Category[];     // Multiple categories
  private seoMetadata: SeoMetadata;
  // Controller maps rich model → slim API
}
// → Dùng khi nhiều consumers cần data. KHÔNG dùng khi chỉ 1-2 consumers.
```

### 6. Published Language

Format chuẩn hoá (schema) để giao tiếp giữa contexts. Thường kết hợp với OHS.

```typescript
// Domain Events dùng schema chuẩn — mọi consumer hiểu format này
interface OrderPlacedEvent {
  eventId: string;
  eventType: 'order.placed';
  occurredAt: string;
  payload: {
    orderId: string;
    customerId: string;
    totalAmount: { amount: number; currency: string };
    items: Array<{ productId: string; quantity: number; unitPrice: number }>;
  };
}
// → Dùng cho event-driven architecture. KHÔNG cần cho in-process communication.
```

### 7. Partnership

Hai teams hợp tác **ngang hàng**, cùng evolve interfaces. Không ai upstream/downstream.

```typescript
// Order context + Inventory context cùng design interface này
interface InventoryReservation {
  reserve(orderId: OrderId, items: ReservationItem[]): Promise<ReservationResult>;
  confirm(reservationId: ReservationId): Promise<void>;
  cancel(reservationId: ReservationId): Promise<void>;
}
// → Dùng khi hai contexts phụ thuộc lẫn nhau, teams sync thường xuyên.
```

### 8. Separate Ways

Hai contexts **không giao tiếp**. Mỗi context tự giải quyết vấn đề.

```typescript
// Reporting context đọc data warehouse — không gọi Order/Inventory APIs
class SalesReportService {
  constructor(private readonly dataWarehouse: DataWarehouse) {}

  async generateMonthlySales(month: YearMonth): Promise<SalesReport> {
    const data = await this.dataWarehouse.query(`
      SELECT product_category, SUM(revenue) as total_revenue
      FROM fact_sales WHERE sale_month = $1 GROUP BY product_category
    `, [month.toString()]);
    return SalesReport.fromRawData(data);
  }
}
// → Dùng khi integration cost > benefit. KHÔNG dùng khi cần real-time data.
```

## Subdomain Types

### Core Domain — competitive advantage, đầu tư cao nhất

```typescript
// Core Domain cho e-commerce: Pricing & Recommendation Engine
class DynamicPricingEngine {
  calculatePrice(product: ProductId, customer: CustomerSegment, context: PricingContext): Money {
    const basePrice = this.getBasePrice(product);
    const adjustments = this.rules
      .filter(rule => rule.applies(product, customer, context))
      .map(rule => rule.calculateAdjustment(basePrice, context));
    return adjustments.reduce((price, adj) => adj.apply(price), basePrice);
  }
}
// → Build in-house, best engineers, full DDD tactical patterns
```

### Supporting Domain — cần custom nhưng không phải differentiator

```typescript
class OrderService {

// → Build in-house, DDD lite
```

## Event Storming

Workshop format do Alberto Brandolini tạo ra — khám phá domain bằng **Domain Events**.

### Format

```
Người tham gia: Developers + Domain Experts + PM (5-15 người)
Thời gian:      2-4 giờ (Big Picture) hoặc 1-2 ngày (Design Level)
Vật liệu:       Sticky notes nhiều màu, bảng trắng lớn
```

### Sticky note colors

```
Orange:  Domain Event      "OrderPlaced", "PaymentFailed"
Blue:    Command           "PlaceOrder", "CancelOrder"
Yellow:  Actor/User        "Customer", "Admin"
Purple:  Policy            "When order placed -> reserve inventory"
Green:   Read Model        "Order Summary", "Dashboard"
Red:     Hotspot/Problem   "unclear", "disagreement"
```

### Quy trình 4 phases

```
Phase 1: Chaotic Exploration (30-45 min)
  Mọi người viết Domain Events (past tense). Dán lên bảng. KHÔNG thảo luận.

Phase 2: Enforce Timeline (20-30 min)
  Sắp xếp events theo thời gian. Tìm duplicates. Đánh dấu hotspots.

Phase 3: Add Commands & Actors (30 min)
  [Customer] -> "Place Order" -> "OrderPlaced"
  [System]   -> "Process Payment" -> "PaymentProcessed"

Phase 4: Find Aggregates & Bounded Contexts (30 min)
  Nhóm events liên quan -> Aggregates. Vẽ boundary -> Bounded Contexts.
```

### Event Storming -> Code

```typescript
// 1. Domain Events (orange sticky notes)
class OrderPlaced implements DomainEvent {
  constructor(
    readonly orderId: OrderId, readonly customerId: CustomerId,
    readonly items: ReadonlyArray<{ productId: string; quantity: number }>,
    readonly totalAmount: Money,
  ) {}
}

// 2. Commands (blue sticky notes)
class PlaceOrderCommand {
  constructor(
    readonly customerId: CustomerId,
    readonly items: OrderItemRequest[],
    readonly shippingAddress: Address,
  ) {}
}

// 3. Aggregates (grouping events)
class Order { /* Handles: PlaceOrder, CancelOrder. Emits: OrderPlaced, OrderCancelled */ }

// 4. Policies (purple sticky notes)
class OrderPlacedPolicy {
  async handle(event: OrderPlaced): Promise<void> {
    await this.inventory.reserve(event.orderId, event.items);
  }
}
```

## Real-world: E-commerce Bounded Contexts

### Subdomain Map

```
┌──────────────────────────────────────────────────────────┐
│                  E-COMMERCE PLATFORM                      │
│  CORE: Product Search | Recommendation | Pricing Engine  │
│  SUPPORTING: Order Mgmt | Inventory | Shipping | Support │
│  GENERIC: Auth (Auth0) | Payment (Stripe) | Email (SaaS) │
└──────────────────────────────────────────────────────────┘
```

### Bounded Context Models — same entity, different shapes

```typescript
// CATALOG CONTEXT: rich product info
interface CatalogProduct {
  id: ProductId; name: string; description: RichText;
  brand: Brand; categories: Category[];
  variants: ProductVariant[]; images: ProductImage[];
}

// PRICING CONTEXT: only price-related data
interface PricedProduct {
  productId: ProductId; basePrice: Money; currentPrice: Money;
  activePromotions: Promotion[];
}

// INVENTORY CONTEXT: stock tracking
interface InventoryItem {
  sku: SKU; warehouse: WarehouseId;
  quantityOnHand: number; quantityReserved: number;
  quantityAvailable: number; // = onHand - reserved
}

// ORDER CONTEXT: order lifecycle
interface OrderSnapshot {
  id: OrderId; customerId: CustomerId; lineItems: LineItem[];
  total: Money; status: OrderStatus;
}
```

### Communication Flow

```
[Order Context]                 [Inventory Context]
     |                                |
     | 1. PlaceOrder command          |
     | 2. Validate & create Order     |
     | 3. Publish OrderPlaced ------->|
     |                                | 4. Reserve stock
     |                                | 5. Publish InventoryReserved -->
     |                          [Payment Context]
     |          <-- PaymentProcessed  |
     | 6. Confirm order               |
     | 7. Publish OrderConfirmed ---->|
     |                                | 8. Confirm reservation
```

### Khi nào dùng / Khi nào KHÔNG dùng Strategic DDD

| Dùng | Không cần |
|------|-----------|
| Domain phức tạp (fintech, healthcare, logistics) | Simple CRUD (blog, todo app) |
| Nhiều team cùng develop | Solo developer |
| Business rules thay đổi thường xuyên | Static business rules |
| Long-lived system (5+ năm) | Prototype, MVP |

## Tổng kết

```
Strategic DDD = HIỂU bài toán trước khi code

1. Ubiquitous Language -> Team nói cùng ngôn ngữ
2. Bounded Context    -> Chia hệ thống thành phần có boundary rõ ràng
3. Context Mapping    -> Define cách các phần giao tiếp (8 patterns)
4. Subdomain Types    -> Biết đầu tư resource vào đâu (Core/Supporting/Generic)
5. Event Storming     -> Workshop khám phá domain cùng business
```

> **Rule of thumb**: Nếu bạn không nói chuyện với domain experts ít nhất 1 lần/tuần,
> bạn chưa làm DDD — bạn chỉ đang dùng patterns.
