## Communicating to Non-Technical Stakeholders

### Họ KHÔNG quan tâm vs QUAN TÂM

```
❌ Technology names, implementation details, technical elegance
✅ Impact lên customers, revenue/cost, timeline, risk
```

### Framework: BLUF (Bottom Line Up Front)

```
❌ BAD: "Hệ thống dùng synchronous request-response pattern, mỗi API
call chờ downstream services, latency 1200ms, đề xuất event-driven..."

✅ GOOD: "Chúng tôi giảm thời gian tạo order từ 2s xuống 0.5s,
giảm 80% lỗi thanh toán. Cần 3 tuần, chi phí thêm $50/tháng."
```

### Translate to Business Language

```
"Technical debt"         → "Ship chậm hơn mỗi sprint vì code cũ cản trở"
"Refactoring"            → "Đầu tư để ship nhanh hơn trong tương lai"
"Caching layer"          → "Trang web load nhanh hơn 5x cho customers"
"CI/CD pipeline"         → "Code → customer dùng được: 1 giờ thay vì 1 ngày"
"Security audit"         → "Bảo vệ data khách hàng, tránh rủi ro pháp lý"
```

### Dùng analogy

```
Technical debt = quán ăn không bao giờ dọn bếp.
Ban đầu nấu nhanh hơn. Sau vài tháng, nấu 1 món đơn giản
mất gấp đôi thời gian vì bếp bừa bộn.
Dọn BÂY GIỜ: 2 tuần. Chờ 6 tháng: 2 tháng + pause features.
```

## Writing Effective Technical Proposals

### Cấu trúc

```
1. EXECUTIVE SUMMARY — 1 paragraph, business impact, no jargon
2. PROBLEM — Data-driven, framed as BUSINESS problem
3. PROPOSED SOLUTION — High-level what & why (vs alternatives)
4. IMPACT & RISKS — Quantified improvements + what if we do NOTHING
5. ASK — Exactly what you need: time, people, money, decision
```

### Ví dụ summary

```markdown
**Problem:** Trang web load 4.5s mobile, gấp 3x competitor. 35% users
bounce, ước tính mất $50K revenue/tháng.

**Proposal:** Tối ưu performance trong 6 tuần, target < 1.5s.

**Expected:** Bounce rate giảm 20-25%, conversion tăng ~15%, +$30-40K/tháng.

**Cost:** 2 engineers × 6 tuần (pause Feature Y, không deadline KH).

**Ask:** Approval re-prioritize Feature Y.
```

## Saying "No" to Bad Ideas

> Mục tiêu: giúp người kia tự thấy vấn đề, không phải tạo conflict.

### Kỹ thuật "Yes, and..." → redirect

```
❌ "Không, microservices cho 3 người là điên rồ"

✅ "Microservices có nhiều ưu điểm cho scaling. Với team size hiện tại,
    modular monolith cho cùng benefits (module separation, boundaries)
    mà không tốn overhead vận hành. Khi grow lên 15-20 người, chúng ta
    sẽ có foundation tốt để tách."
```

### Ask questions thay vì state opinions

```
❌ "NoSQL không phù hợp cho dữ liệu tài chính"
✅ "Khi 2 transactions xảy ra cùng lúc trên 1 account, consistency
    handle thế nào? Regulatory cần audit trail — với eventual
    consistency, reporting accuracy đảm bảo thế nào?"
→ Câu hỏi tự dẫn đến kết luận
```

### Khi PM muốn feature "không thể" trong timeline

```
❌ "Không thể" / "Cần 3 tháng"

✅ "3 options:
   Option A: Full — 8 tuần (production-ready, edge cases, tests)
   Option B: MVP — 3 tuần (80% use cases, skip admin/export)
   Option C: Prototype — 1 tuần (demo-ready, validate với 10 users)
   Recommend Option B — đủ launch, iterate dựa trên feedback."
→ Không nói "no", cung cấp OPTIONS với trade-offs rõ ràng
```

### Khi idea đến từ C-level

```
1. Assume good intent — họ có context bạn không có
2. Clarify the goal — idea sai nhưng goal có thể đúng
3. Present data — "Dựa trên X, approach Y hiệu quả hơn"
4. Offer alternatives — không "no", mà "and also..."
```

## Managing Technical Risk

### Risk cần 4 thông tin

```
WHAT — Risk gì? (mô tả rõ, không jargon)
PROBABILITY — Low/Medium/High + reasoning
IMPACT — Business terms (không technical)
MITIGATION — Đang làm gì để giảm risk?
```

### Communicate cho leadership: STAR framework

```
❌ "RabbitMQ có thể split-brain nếu network partition, message duplication..."

✅ Situation: "Hệ thống messaging có weakness khi network không ổn định"
   Threat:    "10% khả năng đơn hàng bị xử lý 2 lần"
   Action:    "Implement kiểm tra trùng lặp, xong tuần tới"
   Result:    "Sau đó risk giảm xuống < 0.1%"
```

## Technical Roadmap Creation

### Now / Next / Later framework

```
NOW (Quarter này — committed):
  ✅ Specific, scoped, assigned, clear success criteria
  "Migrate auth → Auth0 [Team A, 6 weeks]"

NEXT (Quarter sau — planned):
  ⚠️ Scoped nhưng flexible, owner identified
  "Event-driven Phase 1 [Backend team]"

LATER (6-12 tháng — directional):
  📌 Vision, not commitment
  "Multi-region deployment"
```

### Balancing tech debt vs features

```
Heuristic: 20% capacity cho technical investment, 80% features

Cách implement:
  - Sprint 5 weeks: Week 5 = tech debt
  - 1 engineer rotation mỗi sprint focus tech
  - Khi debt quá nhiều: tăng 30-40% có deadline rõ ràng
```

## Estimating Effort

### Tại sao estimation khó

```
1. Unknown unknowns — "API docs nói support X, thực tế không"
2. Optimism bias — Brain nghĩ happy path, quên edge cases
3. Scope creep — "Nhân tiện thêm feature nhỏ này"
4. Context switching — Effective coding: 4-5 giờ/ngày, không phải 8
```

### Kỹ thuật estimation

**Multiply by Pi:** Initial estimate x 3.14 = realistic estimate.

```
"1 tuần" → thực tế ~3 tuần
Tại sao: edge cases (x1.5) × testing/review (x1.5) × unexpected (x1.4) ≈ π
```

**Three-point estimation:**

```
O (Optimistic) + 4M (Most likely) + P (Pessimistic) / 6

OAuth2 Google: O=2 days, M=5 days, P=12 days
Expected = (2 + 20 + 12) / 6 ≈ 6 days
Communicate: "5-6 ngày, có thể 12 nếu Google API issues"
```

**Communicate properly:**

```
❌ "Sẽ xong trong 2 tuần" (nghe như commitment)

✅ "Estimate 2 tuần, confidence 70%. Có thể 3 tuần nếu third-party
    API issues. Update cuối tuần 1 nếu timeline cần adjust."
```

## Disagree and Commit

> Principle Intel/Amazon: Sau khi discuss đủ, MỌI NGƯỜI — kể cả người không đồng ý
> — fully commit vào quyết định.

```
TRƯỚC quyết định: Voice concerns CLEARLY với evidence
SAU quyết định:   Commit 100%, không sabotage, không "I told you so"
                  Help team succeed, bring up new evidence constructively

EXCEPTION: Vi phạm ethics/legal, irreversible damage, concerns chưa được nghe
```

### Không có disagree & commit:

```
Senior Dev muốn REST, team chọn GraphQL:
→ Mỗi bug: "Nếu REST thì không có vấn đề này"
→ Không invest learn GraphQL → self-fulfilling prophecy

Với disagree & commit:
→ Senior Dev dùng expertise giúp GraphQL succeed
→ Nếu thực sự không work → evidence-based discussion
```

## Building Technical Culture

### 5 Pillars

```
1. CODE REVIEW — Mọi code reviewed (kể cả senior), teaching opportunity
2. DOCUMENTATION — ADRs, RFCs, comments cho "why" không "what"
3. LEARNING — Tech talks, book club, conference budget, blameless post-mortems
4. QUALITY — Tests in Definition of Done, monitoring mọi feature
5. OWNERSHIP — "You build it, you run it", teams own decisions + consequences
```

### Coding standards process

```
1. Collect input (survey team, review PR comments) → 1 tuần
2. Draft based on established guides (Airbnb, Google) → 2-3 ngày
3. Team review + vote controversial items → 1 tuần
4. AUTOMATE (ESLint/Biome + Prettier + CI) → 1 tuần
5. Review mỗi quarter, anyone can propose changes
```

### Anti-patterns

```
🚩 "The Hero" — 1 người fix mọi thứ → Fix: knowledge sharing, pairing
🚩 "The Gatekeeper" — 1 người block mọi thứ → Fix: distribute responsibility
🚩 "Ivory Tower" — Architect thiết kế isolation → Fix: RFC process, team buy-in
🚩 "Resume-Driven" — Chọn tech vì CV → Fix: ADRs requiring justification
```

## Mentoring Junior Engineers

### Dạy CÁCH NGHĨ, không chỉ cách làm

```
❌ "Dùng Repository Pattern"
✅ "Khi nào Repository Pattern thêm giá trị, khi nào over-engineering?"

❌ "Dùng PostgreSQL"
✅ "Evaluate 3 DB options. Criteria: data model fit, team familiarity, cost."
```

### Progressive autonomy

```
Level 1: OBSERVE — Watch senior make decisions, read RFCs
Level 2: ASSIST — Research options, write comparisons
Level 3: DRIVE (guided) — Choose testing approach, propose API design
Level 4: OWN — Design features end-to-end, write RFCs
Timeline: 6-18 months
```

### Mistakes khi mentoring

```
❌ Always giving answers → Junior không learn independently
❌ Throwing into deep end → Overwhelmed, lose confidence
❌ Only reviewing code → Learn syntax, not judgment
❌ Shielding from failure → Không learn from consequences
```

## Refactor vs Rewrite vs Accept Debt

```
                REFACTOR          REWRITE            ACCEPT DEBT
When            Structure can     Beyond saving      Debt doesn't impact
                improve gradually                    velocity much
Risk            Low-Medium        HIGH               Low now, HIGH later
Success rate    80%+              30-50%             N/A
Recommendation  DEFAULT choice    Last resort        If isolated
```

### Refactor (gần như luôn đúng)

Strangler Fig Pattern: interface mới quanh code cũ → implement mới → chuyển consumers → xóa cũ.

### Rewrite (rất hiếm — CHỈ khi TẤT CẢ đúng)

```
- Component < 50K LOC
- No tests, can't add tests
- Fundamental architectural mismatch
- Team hiểu deep DOMAIN
- Business can afford feature freeze
```

### Accept Debt (khi isolated + tracked)

```typescript
// TODO(TECH-DEBT-123): Refactor khi migrate v2
// Context: Quick fix cho launch deadline Q3
// Impact: 30% slower bulk operations
// Plan: Refactor in v2 migration (Q1 2025)
→ Link Jira ticket, review mỗi quarter
```

## Evaluating New Technologies

### Hype Cycle awareness

```
                PEAK OF INFLATED EXPECTATIONS
               ╱            ╲
              ╱              ╲         PLATEAU OF
INNOVATION   ╱                ╲        PRODUCTIVITY
TRIGGER     ╱                  ╲──────────────────
                                ╲    ╱
                                 ╲  ╱ TROUGH OF
                                  ╲╱  DISILLUSIONMENT

→ ĐỪNG adopt ở Peak (hype, chưa battle-tested)
→ Evaluate ở Slope (proven, docs mature)
→ Adopt ở Plateau (safe, ecosystem stable)
```

### Technology Radar (4 rings)

```
ADOPT:  Proven, default choice (TypeScript, PostgreSQL, Docker)
TRIAL:  Promising, thử non-critical (Bun, Drizzle, tRPC)
ASSESS: Theo dõi, chưa dùng production (Effect, WASM backend)
HOLD:   Tránh cho project mới (jQuery, Moment.js, TypeORM)
Review MỖI QUARTER. Document trong ADR khi move to ADOPT.
```

## Real-World: Navigating Architectural Decisions

### Scenario: 3 competing proposals cho Order Management rebuild

```
Sarah (Staff, 8 YOE): "Event Sourcing + CQRS — industry best practice"
Michael (Senior, 5 YOE, built current): "Clean Architecture — vấn đề là code, không phải arch"
Lisa (EM): "Microservices — 3 teams nên own 3 services"
```

### Navigation steps

**Step 1: Understand INTERESTS, not positions (1:1s)**

```
Sarah muốn:   Reliable audit trail, complex state management
Michael muốn: Code quality, maintainability, simplicity
Lisa muốn:    Team independence, faster shipping
→ Tất cả valid. Có solution satisfy hầu hết?
```

**Step 2: Synthesize**

```
PROPOSED: Modular Monolith + Domain Events + Clean Architecture

For Sarah:   Domain Events cho audit trail (không full ES — quá phức tạp)
For Michael: Clean Architecture first, tests, module-by-module refactor
For Lisa:    Module = team ownership, future service boundary
```

**Step 3: Get buy-in**

```
1. Share RFC acknowledging mỗi người contribution
2. "Sarah's insight → domain events. Michael's focus → code quality.
    Lisa's goal → module ownership model."
3. Set checkpoint: 3 months evaluate
→ Mọi người thấy idea của mình TRONG quyết định → buy-in tự nhiên
```

### Lessons

```
1. POSITIONS vs INTERESTS — understand interests, one solution serves many
2. EGO MANAGEMENT — make people feel heard, give credit explicitly
3. DATA beats OPINIONS — prototype resolves debates faster than arguments
4. DOCUMENT EVERYTHING — prevent re-litigating in 6 months
```

### 10 Commandments of Engineering Leadership

```
1.  Mọi quyết định là trade-off — embrace nó
2.  Quyết định tốt + communicate > quyết định tuyệt vời không ai hiểu
3.  Data > Opinion > Authority
4.  Build trust qua transparency — share reasoning, không chỉ conclusion
5.  "Tôi không biết" mạnh hơn giả vờ biết
6.  Mentor bằng câu hỏi, không chỉ câu trả lời
7.  Commit 100% sau khi quyết định, dù disagree
8.  Document decisions — institutional memory > individual memory
9.  Review decisions quarterly — context thay đổi
10. Legacy = people you grow + systems you build + decisions you document
```
