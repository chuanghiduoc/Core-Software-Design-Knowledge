# 10.2 Technical RFC Process

> RFC (Request for Comments) là quy trình biến quyết định cá nhân thành quyết định
> tập thể có hệ thống. Nó không chỉ giúp đưa ra quyết định tốt hơn, mà còn xây dựng
> **institutional memory** — kiến thức tổ chức tồn tại lâu hơn bất kỳ cá nhân nào.

## RFC là gì và khi nào cần viết

```
RFC = Tài liệu kỹ thuật mô tả:
  1. VẤN ĐỀ cần giải quyết
  2. CONTEXT và constraints
  3. Các OPTIONS đã xem xét
  4. RECOMMENDATION và lý do
  5. RISKS và mitigation plan

Mục đích: Thu thập feedback TRƯỚC KHI implement.
```

### Khi nào CẦN / KHÔNG cần RFC

```
✅ Cần RFC:                              ❌ Không cần:
  - Ảnh hưởng ≥ 2 teams                    - Bug fix, small feature
  - Introduce tech mới vào stack            - Refactoring trong 1 module
  - Thay đổi architecture                  - Chọn lib cho internal use
  - Migration lớn (DB, framework)           - Đã có convention rõ ràng
  - Thay đổi public API contract            - Urgent production issue
  - Team không đồng ý → cần align          - 1 team đã consensus
```

### Chi phí của KHÔNG viết RFC

```
Senior engineer đổi REST sang gRPC, không viết RFC. 3 tháng sau:
- Mobile team: gRPC không work qua mobile network → 2 tuần workaround
- Frontend team: viết proxy REST → gRPC → 1 tuần
- DevOps: không biết cần HTTP/2 → 3 ngày infra changes

Nếu có RFC → Mobile team flag issue ở review phase → quyết định khác
```

## RFC Template

```markdown
# RFC-[NUMBER]: [Title]

## Metadata
- **Author(s):** [Names]
- **Status:** Draft | In Review | Accepted | Rejected | Superseded
- **Created / Decision Deadline:** [Dates]
- **DACI:** Driver: [X] | Approver: [Y] | Contributors: [Z] | Informed: [W]

## Summary
[2-3 câu: quyết định cần đưa ra + recommendation]

## Problem Statement
[Vấn đề hiện tại. Data cụ thể: metrics, incidents, feedback]

## Context & Constraints
[Team size, timeline, budget, existing stack, business requirements]

## Options Considered
### Option 1-3: [Name]
- Description | Pros | Cons | Effort (S/M/L/XL) | Risk

## Recommendation
[Option nào, TẠI SAO, trade-offs đã chấp nhận]

## Implementation Plan
[Phases, milestones, timeline]

## Risks & Mitigation
[Risks cụ thể + cách giảm thiểu]

## Success Metrics
[Đo bằng gì để biết quyết định đúng?]

## Open Questions
[Cần input từ reviewers]
```

### Tips viết RFC hiệu quả

```
1. NGẮN GỌN — 3-5 trang, không ai đọc 20 trang
2. HONEST về trade-offs — liệt kê cons THẬT, không strawman
3. DATA > OPINION — "Kafka 100K msg/s vs RabbitMQ 50K msg/s" > "Kafka nhanh hơn"
4. SPECIFIC — "Redis 3 nodes, TTL 5 min" > "dùng caching"
5. ADDRESS concerns proactively — biết team sẽ hỏi gì → trả lời trước
```

## Design Document Structure

> RFC là quy trình ra quyết định. Design Doc là tài liệu thiết kế chi tiết
> SAU KHI quyết định đã được đưa ra.

```
Problem     → TẠI SAO?     |  Goals & Non-Goals → RANH GIỚI scope
Context     → HIỆN TẠI?    |  Options → Đã xem xét gì?
Recommendation → Chọn gì?  |  Detailed Design → Chi tiết implement
Risks       → Sai được gì? |  Milestones → Timeline
```

### Goals vs Non-Goals (cực kỳ quan trọng)

```markdown
## Goals
- Giảm API P95 từ 2s xuống 500ms
- Support 10x traffic without horizontal scaling

## Non-Goals (ngăn scope creep)
- KHÔNG redesign data model (RFC riêng)
- KHÔNG support real-time (phase 2)
- KHÔNG optimize mobile (separate project)
```

### Detailed Design nên include

```typescript
// 1. DATA MODEL
interface OrderEvent {
  eventId: string;
  orderId: string;
  eventType: 'ORDER_CREATED' | 'ORDER_PAID';
  payload: Record<string, unknown>;
  metadata: { userId: string; timestamp: Date; correlationId: string };
}

// 2. API CONTRACTS
// POST /api/v2/orders → 201 { orderId, status, estimatedTotal }

// 3. SEQUENCE DIAGRAMS (text-based)
// Client → API → Order Service → Payment Service → Event Bus

// 4. ERROR HANDLING
// Payment fails → 402, no order created
// Event bus down → Outbox pattern, background retry
```

## ADR vs RFC vs Design Doc

```
┌──────────────┬──────────────┬──────────────┬──────────────────┐
│              │ ADR          │ RFC          │ Design Doc       │
├──────────────┼──────────────┼──────────────┼──────────────────┤
│ Mục đích     │ GHI LẠI      │ THU THẬP     │ MÔ TẢ CHI TIẾT  │
│              │ quyết định   │ feedback     │ thiết kế         │
├──────────────┼──────────────┼──────────────┼──────────────────┤
│ Thời điểm    │ SAU quyết    │ TRƯỚC quyết  │ SAU quyết định,  │
│              │ định         │ định         │ TRƯỚC implement  │
├──────────────┼──────────────┼──────────────┼──────────────────┤
│ Độ dài       │ 1-2 trang    │ 3-5 trang    │ 5-15 trang       │
├──────────────┼──────────────┼──────────────┼──────────────────┤
│ Lifespan     │ Permanent    │ Đến khi      │ Đến khi          │
│              │ (immutable)  │ accepted     │ implement xong   │
└──────────────┴──────────────┴──────────────┴──────────────────┘

Flow: RFC (proposal) → Decision → ADR (ghi lại) → Design Doc → Implement
```

### ADR Example

```markdown
# ADR-007: PostgreSQL làm primary database
**Status:** Accepted (2024-03-15)

**Context:** Team 8 devs, majority SQL experience. 100K → 1M users.

**Decision:** PostgreSQL 16 trên AWS RDS.

**Rationale:** Team familiarity (6/8), JSONB, excellent TS tooling, proven scale.

**Alternatives:** MongoDB (team ít KN), PlanetScale (MySQL-based, ít features).

**Consequences:** Cần PgBouncer sớm, careful migration planning.
```

## Review Process

### Ai review?

```
MUST: Tech Lead team liên quan, engineers sẽ implement, engineers bị ảnh hưởng
SHOULD: DevOps (infra impact), PM (timeline), senior từ team khác
OPTIONAL: Junior (learning), Engineering Manager (resource)
```

### Give feedback hiệu quả

```
❌ "Tôi không thích"     |  ✅ Specific: "Section 3 thiếu latency impact"
❌ "Sao không dùng X?"   |  ✅ Constructive: "Webhook approach giảm load"
❌ "Sẽ không work"       |  ✅ Evidence: "Team Y thử Q3/2024, fail. Link: [x]"

Phân loại:
  🔴 BLOCKER: "Missing payment failure handling"
  🟡 SUGGESTION: "Consider circuit breaker"
  🟢 NIT: "Typo: OrderServce → OrderService"
```

### Receive feedback

```
1. SEPARATE ego from work — RFC critique ≠ bạn critique
2. THANK reviewers — họ dành thời gian
3. RESPOND to EVERY comment — agree/disagree/need more info
4. ITERATE — RFC tốt hiếm khi perfect ở draft 1
```

## Decision Timeline

```
Ngày 1-3:   Author viết draft
Ngày 4:     Gửi cho reviewers
Ngày 4-10:  Review period (7 ngày)
Ngày 11:    Address feedback, update
Ngày 12-14: Final review (3 ngày)
Ngày 15:    Decision: Accept / Reject / Revise

Tổng: ~2-3 tuần major | ~1 tuần medium
```

### Tránh endless discussion

```
1. DEADLINE cứng — "Review closes Friday 5PM"
2. SCOPE — "Focus: data model + migration. Details ở Design Doc"
3. ESCALATE — 2 seniors disagree → Approver quyết định
4. DEFAULT — "Không blocker trước deadline → auto-accepted"
```

## Archiving Decisions

### Tại sao quan trọng

```
Engineer mới: "Tại sao MongoDB cho profiles, PostgreSQL cho orders?"
Không archive: "Ờ, anh A quyết định... anh A nghỉ rồi"
Có archive (ADR-003): Full context, rationale, alternatives → onboard nhanh
```

### Cách tổ chức

```
docs/
├── adr/
│   ├── README.md              ← Index
│   ├── 001-use-typescript.md
│   ├── 004-event-bus-rabbitmq.md  ← Superseded by 009
│   └── 009-migrate-to-kafka.md    ← Supersedes 004
├── rfc/
│   ├── 2024-001-graphql-migration.md      ← Accepted
│   └── 2024-002-kubernetes-adoption.md    ← Rejected
└── design-docs/
    └── graphql-gateway-design.md

ADR là IMMUTABLE — thay đổi = ADR MỚI supersedes ADR cũ
KHÔNG xóa hoặc reuse numbers
```

## Full Example: RFC cho Event-Driven Architecture

```markdown
# RFC-2024-007: Event-Driven Architecture cho Order Processing

## Metadata
- **Author:** Nguyen Van A (Senior Backend)
- **Status:** In Review | **Deadline:** 2024-06-15
- **DACI:** D: Nguyen A | A: Tran B (VP Eng) | C: DevOps Lead, Payment Lead
- **Informed:** Frontend, QA, Support

## Summary
Chuyển Order Processing từ synchronous sang event-driven (message broker).
Giải quyết cascading failures, tight coupling, response time degradation.

## Problem Statement
Order API thực hiện 6 calls TUẦN TỰ: validate(50ms) → payment(500ms) →
inventory(100ms) → email(300ms) → analytics(50ms) → warehouse(200ms)

- P95 latency: 2.1s (target < 500ms)
- 3 incidents Q1 do downstream failures
- 15% orders failed do timeout
- Q3 thêm loyalty + fraud detection → thêm 200-400ms

## Options

### Option 1: BullMQ (Background Jobs)
- Giữ sync: validate + payment. Async: email, analytics, warehouse
- ✅ Team quen, no new infra, P95 → ~600ms | ❌ Không true event-driven
- Effort: S (2-3 weeks) | Risk: Low

### Option 2: RabbitMQ
- True event-driven, fan-out, decoupled services
- ✅ Mature, TS support | ❌ Team chưa vận hành, no event replay
- Effort: M (4-6 weeks) | Risk: Medium

### Option 3: Kafka
- Full event streaming + event sourcing
- ✅ Best throughput, replay | ❌ Highest ops complexity, overkill
- Effort: L (8-12 weeks) | Risk: High

## Recommendation: Phase 1 BullMQ → Phase 2 RabbitMQ

**Phase 1 (Week 1-3):** BullMQ cho non-critical tasks
```typescript
// Outbox pattern: order + events trong 1 transaction
async function createOrder(input: CreateOrderInput): Promise<Order> {
  return await prisma.$transaction(async (tx) => {
    const order = await tx.order.create({ data: orderData });
    await processPayment(order); // Vẫn sync — critical

    await tx.orderOutboxEvent.create({
      data: {
        orderId: order.id,
        eventType: 'ORDER_CREATED',
        payload: { order, customer },
        status: 'PENDING',
      },
    });
    return order;
  });
}

// Background worker publishes from outbox mỗi 5s
// → Email, analytics, warehouse nhận event async
```

**Phase 2 (Week 4-8, sau Q3 peak):** RabbitMQ
- Migrate BullMQ → RabbitMQ consumers
- Decouple payment service
- Add loyalty, fraud as new consumers

**Rationale:** Phase 1 giải quyết 80% vấn đề với 20% effort. Kịp Q3.
Team có thời gian learn event-driven. Kafka revisit khi > 100K orders/day.

## Risks & Mitigation
| Risk | Prob | Impact | Mitigation |
|------|------|--------|------------|
| Job fails silently | Med | High | Dead letter queue + alerting |
| Event ordering | Med | Med | Timestamp + sequence in events |
| Redis fails | Low | High | Redis Sentinel + sync fallback |

## Success Metrics
- [ ] P95 < 600ms (from 2.1s)
- [ ] Zero order failures from downstream services
- [ ] New services added without touching order API
```

### Khi RFC bị reject

```
RFC rejected ≠ thất bại:
1. Ghi lại LÝ DO reject trong ADR → future engineers biết "đã consider X"
2. Tìm ROOT CAUSE:
   - Timing sai? (không phải lúc này)
   - Solution sai? (vấn đề đúng, giải pháp chưa phù hợp)
   - Problem sai? (không thực sự là vấn đề cần giải quyết)
3. Iterate: viết RFC mới approach khác, hoặc chấp nhận status quo
```

## Tổng kết

```
RFC Process = COMMUNICATION TOOL:
  TRƯỚC: Thu thập diverse perspectives
  TRONG: Structured discussion, avoid bikeshedding
  SAU:   Permanent record, organizational learning

Team CÓ RFC:                    Team KHÔNG CÓ RFC:
  ✅ Quyết định nhanh hơn          ❌ "Ai nói to hơn" quyết định
  ✅ Onboard nhanh — đọc ADRs      ❌ Debate lặp lại mỗi 6 tháng
  ✅ Distributed decision-making    ❌ Tribal knowledge mất khi nghỉ
  ✅ Ít revisit quyết định cũ       ❌ Không ai biết TẠI SAO hệ thống
                                      trông như hiện tại
```
