## Scaling Fundamentals

### Capacity Planning

```
Bước 1: Estimate traffic
  - DAU (Daily Active Users): 100K
  - Requests per user per day: ~50
  - Total: 5M requests/day
  - Peak: 3x average = ~170 req/s peak
  - QPS (Queries Per Second): 5M / 86400 ≈ 58 QPS avg, 170 QPS peak

Bước 2: Storage estimate
  - Users: 100K × 1KB = 100MB
  - Orders: 10K/day × 2KB = 20MB/day → 7GB/year
  - Media: 1K uploads/day × 500KB = 500MB/day → 180GB/year

Bước 3: Bandwidth
  - Average response: 5KB
  - Bandwidth: 170 × 5KB = 850KB/s peak = ~7 Mbps

→ Cho 170 QPS: 1 server đủ. Đừng microservice.
→ Cho 17,000 QPS: cần horizontal scaling.
→ Cho 170,000 QPS: cần caching, CDN, DB sharding, queue.
```

## Horizontal vs Vertical Scaling

```
Vertical Scaling (Scale Up):
  Thêm CPU/RAM/Disk cho 1 server
  ✅ Đơn giản, không cần thay đổi code
  ❌ Giới hạn hardware, single point of failure, downtime khi upgrade

Horizontal Scaling (Scale Out):
  Thêm nhiều servers
  ✅ Theoretically unlimited, fault tolerant
  ❌ Phức tạp: stateless requirement, data sync, load balancing
```

### Stateless Services — Prerequisite cho horizontal scaling

```typescript
// ❌ Stateful: session trong memory
const sessions = new Map<string, Session>(); // Chỉ tồn tại trên server này!

app.post('/login', (req, res) => {
  const session = createSession(req.user);
  sessions.set(session.id, session);
  res.cookie('sessionId', session.id);
});

// User gửi request tiếp theo → load balancer route đến server KHÁC → 404 session!

// ✅ Stateless: session trong external store
app.post('/login', async (req, res) => {
  const session = createSession(req.user);
  await redis.set(`session:${session.id}`, JSON.stringify(session), 'EX', 86400);
  res.cookie('sessionId', session.id);
});

// Hoặc tốt hơn: JWT (stateless token)
app.post('/login', async (req, res) => {
  const token = jwt.sign({ userId: req.user.id, role: req.user.role }, secret, { expiresIn: '24h' });
  res.json({ token });
});
// JWT tự chứa thông tin → KHÔNG cần shared store
// Mọi server verify JWT independently
```

## Load Balancing

### Algorithms

```
Round Robin:
  Request 1 → Server A
  Request 2 → Server B
  Request 3 → Server C
  Request 4 → Server A
  ✅ Simple, fair
  ❌ Không biết server nào đang busy

Least Connections:
  Route đến server có ÍT connections nhất
  ✅ Better distribution cho long-running requests
  ❌ Slightly more overhead

IP Hash:
  hash(client_ip) % num_servers → consistent server
  ✅ Same client → same server (session affinity)
  ❌ Uneven distribution nếu 1 IP có nhiều users

Weighted:
  Server A (8 CPU) → weight 4
  Server B (4 CPU) → weight 2
  Server C (2 CPU) → weight 1
  ✅ Accounts for different server capacities
```

### Health Checks

```typescript
// Load balancer cần biết server nào healthy

app.get('/health', async (_req, res) => {
  const checks = await Promise.allSettled([
    checkDatabase(),
    checkRedis(),
    checkDiskSpace(),
  ]);

  const status = checks.every(c => c.status === 'fulfilled') ? 'healthy' : 'degraded';
  const statusCode = status === 'healthy' ? 200 : 503;

  res.status(statusCode).json({
    status,
    timestamp: new Date().toISOString(),
    checks: {
      database: checks[0].status === 'fulfilled' ? 'ok' : 'fail',
      redis: checks[1].status === 'fulfilled' ? 'ok' : 'fail',
      disk: checks[2].status === 'fulfilled' ? 'ok' : 'fail',
    },
  });
});

// /health/live — "Is the process running?" (for kubernetes liveness)
app.get('/health/live', (_req, res) => res.send('ok'));

// /health/ready — "Can it serve traffic?" (for kubernetes readiness)
app.get('/health/ready', async (_req, res) => {
  const dbOk = await checkDatabase().catch(() => false);
  res.status(dbOk ? 200 : 503).send(dbOk ? 'ready' : 'not ready');
});
```

## Database Scaling

### Read Replicas

```
                    ┌──────────────┐
      Writes ──────►│   Primary    │
                    │  (Read/Write)│
                    └───┬──────┬───┘
                        │      │
                   Replication  │
                        │      │
              ┌─────────▼──┐ ┌─▼────────────┐
   Reads ────►│  Replica 1 │ │  Replica 2   │◄──── Reads
              │ (Read-only)│ │ (Read-only)  │
              └────────────┘ └──────────────┘
```

```typescript
// Application-level read/write splitting

class DatabaseCluster {
  constructor(
    private readonly primary: Pool,          // Write + critical reads
    private readonly replicas: Pool[],       // Read-only queries
  ) {}

  // Write queries → always primary
  async write(sql: string, params?: unknown[]): Promise<QueryResult> {
    return this.primary.query(sql, params);
  }

  // Read queries → round-robin replicas
  private replicaIndex = 0;

  async read(sql: string, params?: unknown[]): Promise<QueryResult> {
    const replica = this.replicas[this.replicaIndex % this.replicas.length];
    this.replicaIndex++;
    return replica.query(sql, params);
  }

  // Read-after-write consistency → use primary for reads after writes
  async readFromPrimary(sql: string, params?: unknown[]): Promise<QueryResult> {
    return this.primary.query(sql, params);
  }
}

// Usage
class UserRepository {
  constructor(private readonly db: DatabaseCluster) {}

  async findById(id: string): Promise<User | null> {
    // Read from replica (eventual consistency OK for most reads)
    const result = await this.db.read('SELECT * FROM users WHERE id = $1', [id]);
    return result.rows[0] ?? null;
  }

  async save(user: User): Promise<void> {
    // Write to primary
    await this.db.write(
      'INSERT INTO users (...) VALUES (...) ON CONFLICT (id) DO UPDATE ...',
      [user.id, user.name, user.email],
    );
  }

  async findByIdAfterWrite(id: string): Promise<User> {
    // Read-after-write: must read from primary to see own writes
    const result = await this.db.readFromPrimary('SELECT * FROM users WHERE id = $1', [id]);
    return result.rows[0];
  }
}
```

### Sharding (Horizontal Partitioning)

```typescript
// Chia data across multiple database instances

// Strategy: Hash-based sharding
function getShardId(userId: string, totalShards: number): number {
  const hash = crypto.createHash('md5').update(userId).digest();
  return hash.readUInt32BE(0) % totalShards;
}

class ShardedUserRepository {
  constructor(private readonly shards: Pool[]) {}

  private getPool(userId: string): Pool {
    const shardId = getShardId(userId, this.shards.length);
    return this.shards[shardId];
  }

  async findById(userId: string): Promise<User | null> {
    const pool = this.getPool(userId);
    const result = await pool.query('SELECT * FROM users WHERE id = $1', [userId]);
    return result.rows[0] ?? null;
  }

  async save(user: User): Promise<void> {
    const pool = this.getPool(user.id);
    await pool.query('INSERT INTO users (...) VALUES (...)', [...]);
  }

  // Cross-shard query → query ALL shards, merge results
  async findByEmail(email: string): Promise<User | null> {
    const results = await Promise.all(
      this.shards.map(pool =>
        pool.query('SELECT * FROM users WHERE email = $1', [email])
      ),
    );
    for (const result of results) {
      if (result.rows[0]) return result.rows[0];
    }
    return null;
  }
}

// Vấn đề với sharding:
// - Cross-shard queries CHẬM (scan all shards)
// - Cross-shard JOIN impossible
// - Rebalancing khi thêm shard phức tạp
// - Transactions cross-shard rất khó

// → Sharding là BIỆN PHÁP CUỐI CÙNG. Thử trước:
// 1. Optimize queries (indexes, query plans)
// 2. Caching (Redis)
// 3. Read replicas
// 4. Vertical scaling (bigger server)
// 5. Partitioning (same server, different tables)
// 6. Sharding (last resort)
```

## Connection Pooling

```typescript
// ❌ New connection per request = slow + resource exhaustion
app.get('/users', async (req, res) => {
  const conn = await pg.connect(connectionString); // 50-100ms to establish
  const result = await conn.query('SELECT * FROM users');
  await conn.end(); // Connection destroyed
  res.json(result.rows);
});

// ✅ Connection pool: reuse connections
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  min: 5,                  // Keep minimum 5 connections warm
  max: 20,                 // Maximum 20 concurrent connections
  idleTimeoutMillis: 30_000, // Close idle connections after 30s
  connectionTimeoutMillis: 5_000, // Fail fast if can't connect in 5s
  maxUses: 7500,           // Recycle connection after N uses (prevent memory leaks)
});

// Pool sizes guideline:
// max connections = (core_count * 2) + effective_spindle_count
// For cloud DB: check your plan's connection limit
// RDS db.t3.micro: 66 max connections
// RDS db.r5.large: 1000+ max connections
// PgBouncer: use for connection multiplexing when many app instances

// Monitor pool health
setInterval(async () => {
  console.log({
    poolTotal: pool.totalCount,
    poolIdle: pool.idleCount,
    poolWaiting: pool.waitingCount,
  });
}, 10_000);
```

## Async Processing

```typescript
// Move slow/heavy work OUT of request path

// ❌ Synchronous: user waits for everything
app.post('/orders', async (req, res) => {
  const order = await createOrder(req.body);           // 50ms
  await chargePayment(order);                          // 500ms
  await reserveInventory(order);                       // 200ms
  await generateInvoicePdf(order);                     // 2000ms ← User waits!
  await sendConfirmationEmail(order);                  // 300ms ← User waits!
  await updateAnalytics(order);                        // 100ms ← User waits!
  res.json(order);
  // Total: ~3150ms. User stares at spinner.
});

// ✅ Async: respond fast, process in background
app.post('/orders', async (req, res) => {
  const order = await createOrder(req.body);           // 50ms
  await chargePayment(order);                          // 500ms (must be sync — need result)
  await reserveInventory(order);                       // 200ms (must be sync — need result)

  // Queue background jobs — return immediately
  await jobQueue.add('generate-invoice', { orderId: order.id });
  await jobQueue.add('send-confirmation', { orderId: order.id });
  await jobQueue.add('update-analytics', { orderId: order.id });

  res.status(201).json(order);
  // Total: ~750ms. User happy.
});

// Background workers process jobs independently
// BullMQ worker
const worker = new Worker('default', async (job) => {
  switch (job.name) {
    case 'generate-invoice':
      await generateInvoicePdf(job.data.orderId);
      break;
    case 'send-confirmation':
      await sendConfirmationEmail(job.data.orderId);
      break;
    case 'update-analytics':
      await updateAnalytics(job.data.orderId);
      break;
  }
}, { connection: redis, concurrency: 10 });
```

## CDN & Static Assets

```
Without CDN:                    With CDN:
User (Tokyo) ──────────────►    User (Tokyo) ──► CDN Edge (Tokyo)
  3000km to US server               │                    │
  Latency: 200ms                     │  cache miss        │ cache hit
                                     ▼                    ▼
                               Origin (US)          Serve from edge
                                                    Latency: 20ms
```

```typescript
// Serve static assets with cache headers

// Immutable assets (hashed filenames): cache forever
// main.a1b2c3d4.js → cache forever (new hash = new URL)
app.use('/assets', express.static('dist/assets', {
  maxAge: '1y',
  immutable: true,
}));

// Mutable assets (HTML, manifest): short cache + revalidation
app.use(express.static('dist', {
  maxAge: '5m',
  etag: true,
  lastModified: true,
}));

// Upload to S3/R2 + serve via CloudFront/Cloudflare
// → Origin offloaded, bandwidth reduced, latency reduced globally
```

## Performance Optimization Checklist

```
Database:
  □ Slow query log enabled? (queries > 100ms)
  □ EXPLAIN ANALYZE cho top 10 slowest queries?
  □ Indexes cho WHERE, JOIN, ORDER BY columns?
  □ N+1 queries eliminated? (DataLoader, eager loading)
  □ Connection pooling configured?
  □ Unnecessary data fetched? (SELECT * → SELECT needed columns)

Application:
  □ Heavy computation trong request path? → Move to background job
  □ Sequential external calls? → Parallelize with Promise.all
  □ Memory leaks? (monitor heap over time)
  □ CPU-intensive sync operations blocking event loop?

Caching:
  □ Hot data cached? (Redis for DB results, CDN for static)
  □ Cache invalidation strategy defined?
  □ Cache hit ratio monitored? (target > 80%)
  □ Thundering herd protection? (cache stampede lock)

Network:
  □ Response compression enabled? (gzip/brotli)
  □ HTTP/2 enabled?
  □ Keep-alive connections?
  □ Appropriate timeouts set? (connect, read, write)

Monitoring:
  □ P50/P95/P99 latency tracked?
  □ Error rate tracked?
  □ Throughput (RPS) tracked?
  □ Resource utilization (CPU, memory, disk I/O)?
  □ Alerts configured for anomalies?
```
