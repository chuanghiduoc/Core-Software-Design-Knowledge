## Architecture Decision Records

ADR = document 1 QUYẾT ĐỊNH architecture quan trọng. Tại sao chọn X thay vì Y, trong context nào, trade-offs là gì.

### ADR Template

```markdown
# ADR-001: Chọn PostgreSQL thay vì MongoDB cho primary database

## Status
Accepted (2024-03-15)

## Context
Chúng ta cần chọn primary database cho order management system.
Requirements:
- ACID transactions cho payment + inventory updates
- Complex queries (join orders-users-products)
- Team có 3 năm kinh nghiệm PostgreSQL, 0 MongoDB
- Expected data volume: ~10GB first year, ~100GB by year 3

## Decision
Chọn PostgreSQL 16 trên AWS RDS.

## Alternatives Considered

### MongoDB
- Pros: flexible schema, horizontal scaling built-in
- Cons: no multi-document ACID transactions (tại thời điểm đánh giá),
  team không có kinh nghiệm, complex joins khó, eventual consistency
  không phù hợp cho financial data

### MySQL
- Pros: mature, team có kinh nghiệm
- Cons: JSON support yếu hơn PostgreSQL, extension ecosystem nhỏ hơn,
  MVCC implementation kém hơn PostgreSQL cho concurrent writes

### CockroachDB
- Pros: PostgreSQL-compatible, horizontal scaling, distributed ACID
- Cons: operational complexity cao, cost cao hơn, team chưa familiar,
  overkill cho expected data volume

## Consequences

### Positive
- Team productive ngay (familiar technology)
- Strong ACID guarantees cho financial transactions
- Rich ecosystem (PostGIS, pg_trgm, JSONB)
- Lower operational cost (managed RDS)

### Negative
- Vertical scaling limit (~5TB practical limit trên single instance)
- Khi cần horizontal scaling → phải add read replicas hoặc migrate
- Schema migrations cần careful planning (zero-downtime)

### Risks
- Nếu data vượt 500GB: cần partitioning strategy
- Nếu write throughput vượt 10K TPS: cần evaluate sharding hoặc CQRS

## Review Date
Revisit khi data > 100GB hoặc write throughput > 5K TPS
```

### ADR Best Practices

```
1. WRITE ADRs for decisions that are:
   - Hard to reverse (database choice, architecture pattern)
   - Frequently questioned ("Why do we use X?")
   - Controversial (team disagreed, need to document reasoning)

2. DON'T write ADRs for:
   - Obvious choices (using TypeScript for a TS project)
   - Easily reversible decisions (which logging library)
   - Implementation details (which sort algorithm)

3. ADRs are IMMUTABLE after acceptance.
   If decision changes → new ADR superseding the old one.
   Old ADR status changes to "Superseded by ADR-XXX"

4. Keep them SHORT. 1-2 pages max.
   Long ADR = probably multiple decisions bundled.
```

## Technical Documentation Strategy

### Documentation Pyramid

```
                    ╱╲
                   ╱  ╲
                  ╱ WHY ╲         ADRs, Design Docs
                 ╱────────╲       (Why did we choose this?)
                ╱   WHAT   ╲      API docs, Architecture overview
               ╱────────────╲     (What does it do? How does it fit?)
              ╱     HOW      ╲    README, Setup guides, Runbooks
             ╱────────────────╲   (How to use/run/deploy?)
            ╱    REFERENCE     ╲  Auto-generated API docs, Type docs
           ╱────────────────────╲ (Lookup specific details)

Top of pyramid: manual, high-value, changes rarely
Bottom of pyramid: automated, always up-to-date
```

## API Documentation

### OpenAPI / Swagger — Auto-generated from code

```typescript
// Zod-to-OpenAPI: generate docs from validation schemas

import { OpenAPIRegistry, OpenApiGeneratorV3 } from '@asteasolutions/zod-to-openapi';
import { z } from 'zod';

const registry = new OpenAPIRegistry();

// Register schemas
const UserSchema = registry.register('User', z.object({
  id: z.string().uuid().openapi({ example: 'a1b2c3d4-...' }),
  name: z.string().openapi({ example: 'Alice Johnson' }),
  email: z.string().email().openapi({ example: 'alice@example.com' }),
  role: z.enum(['viewer', 'editor', 'admin']),
  createdAt: z.string().datetime(),
}));

// Register endpoints
registry.registerPath({
  method: 'get',
  path: '/api/users/{id}',
  summary: 'Get user by ID',
  request: {
    params: z.object({ id: z.string().uuid() }),
  },
  responses: {
    200: {
      description: 'User found',
      content: { 'application/json': { schema: UserSchema } },
    },
    404: {
      description: 'User not found',
      content: { 'application/json': { schema: ErrorSchema } },
    },
  },
});

// Generate OpenAPI spec
const generator = new OpenApiGeneratorV3(registry.definitions);
const spec = generator.generateDocument({
  openapi: '3.0.0',
  info: { title: 'My API', version: '1.0.0' },
  servers: [{ url: 'https://api.myapp.com' }],
});

// Serve Swagger UI
app.use('/docs', swaggerUi.serve, swaggerUi.setup(spec));

// Source of truth = Zod schemas (used for BOTH validation AND documentation)
// Schemas change → docs update automatically. Zero drift.
```

### Documentation Rules

```
1. Docs live WITH the code (same repo, same PR)
   → Changes to code + docs reviewed together

2. Automate what you can
   → API docs from schemas
   → Diagrams from code
   → Type docs from TypeScript

3. Document WHY, not WHAT
   → Code says WHAT. Docs say WHY.
   → "We chose X because Y" not "X does Z" (code already shows Z)

4. Kill stale docs
   → Outdated docs worse than no docs
   → Review docs in PRs that change related code

5. README = entry point, must be current
   → If Quick Start doesn't work → FIX IT immediately
```
