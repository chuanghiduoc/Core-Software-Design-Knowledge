## Monolith

Toàn bộ application chạy trong **1 process**, deploy **1 artifact**.

### Khi nào Monolith đúng đắn

- **Giai đoạn đầu** — team nhỏ (< 10 devs), chưa hiểu rõ domain boundaries
- **CRUD apps** — admin panels, internal tools, content management
- **Startups** — cần ship nhanh, pivot liên tục
- **Tight coupling giữa features** — mọi feature share cùng data model

### Monolith tốt ≠ Big Ball of Mud

```typescript
// ✅ Well-structured monolith

// src/
// ├── modules/           ← Mỗi module = 1 bounded context
// │   ├── users/
// │   │   ├── user.service.ts
// │   │   ├── user.repository.ts
// │   │   ├── user.controller.ts
// │   │   └── index.ts   ← Public API of module
// │   ├── orders/
// │   │   └── ...
// │   ├── billing/
// │   │   └── ...
// │   └── notifications/
// │       └── ...
// ├── shared/             ← Shared utilities, NOT shared business logic
// └── main.ts

// Module boundary enforcement
// modules/users/index.ts — CHỈ export public API
export { UserService } from './user.service';
export type { User, UserId } from './user.entity';
export type { CreateUserInput } from './user.dto';
// Internal implementation details KHÔNG export

// modules/orders/order.service.ts
import { UserService } from '../users'; // Import qua public API
// KHÔNG: import { UserRepository } from '../users/user.repository';
// → Truy cập internal = coupling sai

class OrderService {
  constructor(
    private readonly userService: UserService, // Depend on module's public API
    private readonly orderRepo: OrderRepository,
  ) {}

  async placeOrder(userId: string, items: OrderItem[]): Promise<Order> {
    const user = await this.userService.findById(userId);
    if (!user) throw new UserNotFoundError(userId);
    // ...
  }
}
```

### Monolith Pitfalls

| Pitfall | Dấu hiệu |
|---------|-----------|
| **Big Ball of Mud** | Mọi file import mọi file khác, circular dependencies |
| **Database coupling** | 20 tables JOIN trong 1 query, mọi module share 1 schema |
| **Deployment fear** | "Đừng deploy thứ 6" vì 1 change có thể break everything |
| **Scaling limit** | 1 module cần 10x resources nhưng phải scale cả monolith |

## Modular Monolith

**Deploy 1 artifact** nhưng **tổ chức như microservices**. Mỗi module có boundaries rõ ràng, communicate qua defined interfaces, có thể tách ra service riêng khi cần.

### Đây là sweet spot cho phần lớn dự án

```typescript
// === Module Structure ===
// src/
// ├── modules/
// │   ├── identity/              ← Module 1: User identity & auth
// │   │   ├── domain/
// │   │   │   ├── user.ts
// │   │   │   └── auth-token.ts
// │   │   ├── application/
// │   │   │   ├── register.handler.ts
// │   │   │   ├── login.handler.ts
// │   │   │   └── identity.facade.ts  ← Public API
// │   │   ├── infrastructure/
// │   │   │   └── postgres-user.repo.ts
// │   │   ├── http/
// │   │   │   └── identity.routes.ts
// │   │   └── index.ts           ← Module entry point
// │   │
// │   ├── catalog/               ← Module 2: Product catalog
// │   │   ├── domain/
// │   │   ├── application/
// │   │   │   └── catalog.facade.ts
// │   │   ├── infrastructure/
// │   │   ├── http/
// │   │   └── index.ts
// │   │
// │   └── ordering/              ← Module 3: Order management
// │       ├── domain/
// │       ├── application/
// │       │   └── ordering.facade.ts
// │       ├── infrastructure/
// │       ├── http/
// │       └── index.ts

// === Module Communication Rules ===
// 1. Modules communicate ONLY through Facades (public APIs)
// 2. No direct DB access across modules
// 3. Each module owns its tables
// 4. Async communication via internal event bus

// modules/identity/application/identity.facade.ts
export class IdentityFacade {
  constructor(
    private readonly userRepo: UserRepository,
    private readonly authService: AuthService,
  ) {}

  async getUserById(id: UserId): Promise<UserView | null> {
    const user = await this.userRepo.findById(id);
    return user ? UserView.from(user) : null;
  }

  async validateToken(token: string): Promise<AuthenticatedUser> {
    return this.authService.verify(token);
  }
}

// modules/ordering/application/place-order.handler.ts
export class PlaceOrderHandler {
  constructor(
    private readonly identityFacade: IdentityFacade,  // Module communication
    private readonly catalogFacade: CatalogFacade,    // Module communication
    private readonly orderRepo: OrderRepository,       // Own module's repo
    private readonly eventBus: InternalEventBus,
  ) {}

  async handle(command: PlaceOrderCommand): Promise<OrderId> {
    // Cross-module query through facade
    const user = await this.identityFacade.getUserById(command.userId);
    if (!user) throw new UserNotFoundError(command.userId);

    // Cross-module query
    const products = await this.catalogFacade.getProductsByIds(command.productIds);

    // Domain logic
    const order = Order.create(user.id, products, command.shippingAddress);
    await this.orderRepo.save(order);

    // Async notification to other modules
    await this.eventBus.publish(new OrderPlacedEvent(order));

    return order.id;
  }
}

// === Internal Event Bus (in-process) ===
class InternalEventBus {
  private handlers = new Map<string, Array<(event: any) => Promise<void>>>();

  subscribe<T>(eventType: string, handler: (event: T) => Promise<void>): void {
    const existing = this.handlers.get(eventType) ?? [];
    existing.push(handler);
    this.handlers.set(eventType, existing);
  }

  async publish(event: { type: string }): Promise<void> {
    const handlers = this.handlers.get(event.type) ?? [];
    // In-process: có thể chọn sequential hoặc parallel
    await Promise.allSettled(handlers.map(h => h(event)));
  }
}

// Module registration
// modules/notifications/index.ts
export function registerNotificationHandlers(eventBus: InternalEventBus): void {
  eventBus.subscribe<OrderPlacedEvent>('OrderPlaced', async (event) => {
    await sendOrderConfirmationEmail(event);
  });

  eventBus.subscribe<UserRegisteredEvent>('UserRegistered', async (event) => {
    await sendWelcomeEmail(event);
  });
}
```

### Database Boundaries

```typescript
// Mỗi module sở hữu tables riêng. KHÔNG join cross-module.

// Module: identity
// Tables: users, auth_tokens, sessions

// Module: ordering
// Tables: orders, order_items, order_status_history
// Column: user_id (reference, KHÔNG foreign key vào identity.users)

// Module: catalog
// Tables: products, categories, product_images

// Khi cần data từ module khác → gọi Facade, KHÔNG join
// "Duplicate data" (denormalize) ở ordering module:
// order_items có product_name, product_price snapshot
// → KHÔNG join vào catalog.products vì price có thể thay đổi
```

## Microservices

Mỗi service là **1 deployment unit riêng**, có **database riêng**, communicate qua **network** (HTTP, gRPC, messaging).

### Khi nào THỰC SỰ cần Microservices

| ✅ Cần khi | ❌ Không cần khi |
|-----------|-----------------|
| Team > 20 devs, multiple squads | Team < 10, communication dễ |
| Module cần scale independently (thực tế, có data) | "Chắc tương lai sẽ cần scale" |
| Khác nhau về tech stack (ML team dùng Python) | Cùng 1 stack |
| Deployment independence bắt buộc (module A deploy 10x/day, B 1x/month) | Deploy cùng nhau OK |
| Regulatory isolation (PCI DSS cho payment) | Không có compliance requirements |

### Chi phí thực sự của Microservices

```
Microservices thêm complexity:
├── Network latency (1ms → 50-200ms per call)
├── Distributed transactions (2PC, Saga patterns)
├── Data consistency (eventual consistency, not ACID)
├── Operational complexity (deploy, monitor, debug N services)
├── Service discovery & load balancing
├── API versioning & backward compatibility
├── Distributed tracing (1 request → 10 service calls → debug how?)
├── Shared nothing architecture (no shared DB)
├── Team coordination overhead (contract changes, breaking changes)
└── Infrastructure cost (N×kubernetes pods, N×databases, N×CI pipelines)
```

### Microservice Boundaries — How to Split

```
Bounded Contexts (DDD) = Service boundaries

❌ Sai: Split theo technical layer
  User Service, Database Service, Auth Service, Validation Service
  → Vẫn coupled, chỉ là distributed monolith

✅ Đúng: Split theo business capability
  Identity Service (auth + user profiles)
  Order Service (order lifecycle)
  Payment Service (payment processing)
  Notification Service (email, SMS, push)
  Catalog Service (products, categories)
  Inventory Service (stock management)

Mỗi service:
- Sở hữu data riêng (own database)
- Có team riêng (or clear ownership)
- Deploy independently
- Scale independently
- Có thể down mà không crash cả hệ thống
```

### Service Communication

```typescript
// === Synchronous: HTTP/gRPC (request-response) ===
// Dùng khi: cần response ngay lập tức

// Order Service gọi Payment Service
class PaymentClient {
  constructor(
    private readonly baseUrl: string,
    private readonly httpClient: HttpClient,
  ) {}

  async charge(request: ChargeRequest): Promise<ChargeResponse> {
    const response = await this.httpClient.post(`${this.baseUrl}/charges`, {
      body: request,
      timeout: 5000,
      retries: 2,
    });

    if (!response.ok) {
      throw new PaymentServiceError(response.status, response.body);
    }

    return response.body as ChargeResponse;
  }
}

// === Asynchronous: Message Queue (event-driven) ===
// Dùng khi: không cần response ngay, fire-and-forget

// Order Service publishes event
class OrderEventPublisher {
  constructor(private readonly producer: KafkaProducer) {}

  async orderPlaced(order: Order): Promise<void> {
    await this.producer.send({
      topic: 'order-events',
      messages: [{
        key: order.id,
        value: JSON.stringify({
          type: 'OrderPlaced',
          data: {
            orderId: order.id,
            customerId: order.customerId,
            items: order.items,
            total: order.total,
          },
          timestamp: new Date().toISOString(),
        }),
      }],
    });
  }
}

// Notification Service consumes event
class OrderEventConsumer {
  constructor(
    private readonly consumer: KafkaConsumer,
    private readonly emailService: EmailService,
  ) {}

  async start(): Promise<void> {
    await this.consumer.subscribe({ topic: 'order-events' });

    await this.consumer.run({
      eachMessage: async ({ message }) => {
        const event = JSON.parse(message.value!.toString());

        switch (event.type) {
          case 'OrderPlaced':
            await this.emailService.sendOrderConfirmation(event.data);
            break;
          case 'OrderShipped':
            await this.emailService.sendShippingNotification(event.data);
            break;
        }
      },
    });
  }
}
```

## Communication Patterns

### Synchronous Patterns

```typescript
// 1. API Gateway Pattern
// Client → API Gateway → Microservices
// Gateway handles: routing, auth, rate limiting, response aggregation

// 2. Backend for Frontend (BFF)
// Mobile App → Mobile BFF → Services
// Web App → Web BFF → Services
// Mỗi BFF tailor-made cho client type

// 3. Service-to-Service direct calls
// Order Service → Payment Service (HTTP/gRPC)
// Vấn đề: tight coupling, cascading failures
// Giải pháp: Circuit Breaker (xem 3.8)
```

### Asynchronous Patterns

```typescript
// 1. Event Notification — "something happened"
interface OrderPlacedEvent {
  type: 'OrderPlaced';
  orderId: string;
  // Minimal data — consumers query for details if needed
}

// 2. Event-Carried State Transfer — "something happened, here's the data"
interface OrderPlacedEvent {
  type: 'OrderPlaced';
  orderId: string;
  customerId: string;
  items: Array<{ productId: string; name: string; quantity: number; price: number }>;
  total: number;
  shippingAddress: Address;
  // Full data — consumers don't need to call back
}

// 3. Command Message — "please do this"
interface SendEmailCommand {
  type: 'SendEmail';
  to: string;
  template: string;
  data: Record<string, unknown>;
  // Explicit request to another service
}
```

### Saga Pattern — Distributed Transactions

```typescript
// Vấn đề: Place Order = charge payment + reserve inventory + create shipping
// Nếu inventory fails sau payment success → phải rollback payment

// === Choreography Saga (event-driven, no coordinator) ===
// Order Service: CreateOrder → emit OrderCreated
// Payment Service: listen OrderCreated → charge → emit PaymentCharged
// Inventory Service: listen PaymentCharged → reserve → emit InventoryReserved
// Shipping Service: listen InventoryReserved → create shipment → emit ShipmentCreated
// Order Service: listen ShipmentCreated → mark order as completed

// Compensation (nếu inventory fails):
// Inventory Service: emit InventoryReservationFailed
// Payment Service: listen InventoryReservationFailed → refund → emit PaymentRefunded
// Order Service: listen PaymentRefunded → mark order as failed

// === Orchestration Saga (central coordinator) ===
class PlaceOrderSaga {
  private state: SagaState = 'initial';
  private paymentId?: string;
  private reservationId?: string;

  constructor(
    private readonly paymentClient: PaymentClient,
    private readonly inventoryClient: InventoryClient,
    private readonly shippingClient: ShippingClient,
    private readonly orderRepo: OrderRepository,
  ) {}

  async execute(order: Order): Promise<SagaResult> {
    try {
      // Step 1: Charge payment
      this.state = 'charging_payment';
      const payment = await this.paymentClient.charge({
        amount: order.total,
        customerId: order.customerId,
      });
      this.paymentId = payment.id;

      // Step 2: Reserve inventory
      this.state = 'reserving_inventory';
      const reservation = await this.inventoryClient.reserve({
        items: order.items,
        orderId: order.id,
      });
      this.reservationId = reservation.id;

      // Step 3: Create shipment
      this.state = 'creating_shipment';
      await this.shippingClient.createShipment({
        orderId: order.id,
        items: order.items,
        address: order.shippingAddress,
      });

      // All succeeded
      this.state = 'completed';
      order.markConfirmed();
      await this.orderRepo.save(order);

      return SagaResult.success(order.id);
    } catch (error) {
      return this.compensate(order, error as Error);
    }
  }

  private async compensate(order: Order, error: Error): Promise<SagaResult> {
    const compensationErrors: Error[] = [];

    // Reverse order compensation
    if (this.reservationId) {
      try {
        await this.inventoryClient.cancelReservation(this.reservationId);
      } catch (e) {
        compensationErrors.push(e as Error);
      }
    }

    if (this.paymentId) {
      try {
        await this.paymentClient.refund(this.paymentId);
      } catch (e) {
        compensationErrors.push(e as Error);
      }
    }

    order.markFailed(error.message);
    await this.orderRepo.save(order);

    this.state = 'compensated';
    return SagaResult.failed(error, compensationErrors);
  }
}
```

| | Choreography | Orchestration |
|--|-------------|---------------|
| **Coupling** | Loose (events) | Tighter (coordinator knows all steps) |
| **Complexity** | Hard to follow flow | Clear sequential flow |
| **Error handling** | Distributed compensation | Centralized compensation |
| **Visibility** | Hard to monitor | Easy to monitor saga state |
| **Best for** | Simple flows (3-4 steps) | Complex flows (5+ steps, conditional logic) |

## Migration Path

### Strangler Fig Pattern — Monolith → Microservices dần dần

```
Phase 1: Monolith (well-structured, modular)
Phase 2: Extract first service (lowest risk, highest independence)
Phase 3: Repeat for next module
Phase N: Monolith shrinks, services grow

                ┌──────────────────────────┐
Phase 1:        │       Monolith           │
                │  [Users][Orders][Billing] │
                └──────────────────────────┘

                ┌──────────────────────────┐   ┌─────────────┐
Phase 2:        │       Monolith           │   │ Notification│
                │  [Users][Orders][Billing] │──►│   Service   │
                └──────────────────────────┘   └─────────────┘

                ┌──────────────────┐   ┌─────────────┐
Phase 3:        │    Monolith      │   │ Notification│
                │ [Users][Orders]  │   │   Service   │
                └────────┬─────────┘   └─────────────┘
                         │
                ┌────────▼─────────┐
                │  Billing Service │
                └──────────────────┘
```

```typescript
// Strangler implementation: proxy pattern

// Trước: tất cả billing logic trong monolith
app.post('/api/billing/invoice', billingController.createInvoice);

// Sau: proxy đến new service, fallback về monolith
app.post('/api/billing/invoice', async (req, res, next) => {
  try {
    // Try new billing service
    const response = await billingServiceClient.createInvoice(req.body);
    res.json(response);
  } catch (error) {
    if (error instanceof ServiceUnavailableError) {
      // Fallback to monolith
      return billingController.createInvoice(req, res, next);
    }
    next(error);
  }
});

// Dần dần: khi confident, bỏ fallback, xoá code billing trong monolith
```

## Decision Framework

```
Team size < 10 AND domain đơn giản?
  → Monolith (modular)

Team size 5-20 AND domain phức tạp?
  → Modular Monolith

Team size > 20 AND clear bounded contexts AND DevOps maturity?
  → Microservices

Không chắc?
  → Modular Monolith.
    Nếu sau này cần micro → tách module ra service.
    Cost of wrong choice: Micro → Mono = very hard.
                          Modular Mono → Micro = manageable.
```

### Distributed Monolith — Anti-pattern tệ nhất

```
❌ Distributed Monolith = chi phí của microservices + coupling của monolith

Dấu hiệu:
- Deploy phải deploy TẤT CẢ services cùng lúc
- Thay đổi 1 service → phải sửa 5 services khác
- Shared database giữa services
- Synchronous call chains (A → B → C → D → E)
- Không thể test 1 service independently

Đây là KẾT QUẢ của việc chọn microservices khi chưa sẵn sàng.
```
