## Pattern Map — Tổng quan 23 patterns

### Creational — "Tạo object như thế nào?"

| Pattern | 1-line summary | TypeScript idiom |
|---------|---------------|-----------------|
| **Singleton** | 1 instance duy nhất | Module-level `export const` |
| **Factory Method** | Delegate việc tạo object | `createXxx()` function |
| **Abstract Factory** | Tạo family objects tương thích | Factory returning interface implementations |
| **Builder** | Step-by-step construction | Fluent API / chaining |
| **Prototype** | Clone existing objects | `structuredClone()` / spread |

### Structural — "Kết nối objects như thế nào?"

| Pattern | 1-line summary | TypeScript idiom |
|---------|---------------|-----------------|
| **Adapter** | Chuyển interface A → B | Wrapper class implementing target interface |
| **Bridge** | Tách abstraction ↔ implementation | Composition with interface field |
| **Composite** | Tree structure, uniform processing | Recursive types |
| **Decorator** | Thêm behavior bằng wrapping | Wrapper class cùng interface |
| **Facade** | Simplify complex subsystem | Service class orchestrating nhiều services |
| **Flyweight** | Share intrinsic state | Cached immutable instances |
| **Proxy** | Control access to object | Wrapper cùng interface + access logic |

### Behavioral — "Objects giao tiếp thế nào?"

| Pattern | 1-line summary | TypeScript idiom |
|---------|---------------|-----------------|
| **Strategy** | Swap algorithm at runtime | Function parameter / interface |
| **Observer** | 1-to-many notifications | EventEmitter / callbacks |
| **Command** | Encapsulate request as object | Action objects with execute/undo |
| **Chain of Responsibility** | Pass request qua chain | Middleware pipeline |
| **Iterator** | Traverse collection | `for...of` / generators |
| **Mediator** | Centralize communication | Event bus / coordinator class |
| **State** | Behavior changes with state | State objects / state machine |
| **Template Method** | Fixed algorithm, variable steps | Abstract class with abstract methods |
| **Memento** | Save/restore state | Snapshot objects |
| **Visitor** | Add operations without modifying types | Double dispatch / pattern matching |
| **Interpreter** | Evaluate domain language | AST + evaluate function |

## Patterns hay bị nhầm lẫn

### Decorator vs Proxy

```
Cả hai đều wrap object cùng interface. Khác nhau ở MỤC ĐÍCH:

Decorator: THÊM behavior mới
  LoggingRepo(CachingRepo(PostgresRepo))
  → Mỗi layer thêm: logging, caching

Proxy: KIỂM SOÁT access
  AuthProxy(RealService)
  → Check permissions trước khi delegate

Dấu hiệu phân biệt:
- Decorator thường composable (stack nhiều layers)
- Proxy thường là 1 layer kiểm soát
```

### Strategy vs State

```
Cả hai đều delegate behavior cho object khác. Khác nhau:

Strategy: CLIENT chọn algorithm → inject từ ngoài
  const sorter = new Sorter(quickSortStrategy);

State: OBJECT TỰ chuyển state → transitions nội bộ
  order.pay(); // order tự chuyển từ PendingState → PaidState

Dấu hiệu phân biệt:
- Strategy: object KHÔNG biết strategies khác tồn tại
- State: mỗi state BIẾT states khác (để transition)
```

### Factory Method vs Abstract Factory

```
Factory Method: tạo 1 loại object
  createLogger(env) → Logger

Abstract Factory: tạo FAMILY objects tương thích
  createDBFactory(type) → { QueryBuilder, Pool, SchemaBuilder }

Dấu hiệu phân biệt:
- Factory Method: 1 create method
- Abstract Factory: multiple create methods cho related objects
```

### Observer vs Mediator

```
Observer: 1 → many broadcast, listeners don't know each other
  EventEmitter: emitter.emit('event', data)
  Bất kỳ ai subscribe đều nhận

Mediator: many ↔ many through coordinator
  FormMediator: country changes → mediator decides → update city + shipping
  Mediator biết TẤT CẢ components, quyết định ai nhận gì

Dấu hiệu phân biệt:
- Observer: fire-and-forget, no coordination
- Mediator: complex interaction rules between specific objects
```

### Adapter vs Facade

```
Adapter: chuyển đổi 1 interface → 1 interface khác
  StripeAdapter: Stripe SDK → PaymentGateway interface

Facade: simplify complex subsystem (nhiều objects → 1 simple API)
  OrderFacade: Inventory + Payment + Shipping + Notification → placeOrder()

Dấu hiệu phân biệt:
- Adapter: 1-to-1 interface mapping
- Facade: many-to-1 simplification
```

## Kết hợp Patterns trong real-world systems

### E-commerce Order System

```typescript
// Pattern combination: nhiều patterns cooperate

// 1. FACTORY METHOD — tạo đúng payment processor
function createPaymentProcessor(method: PaymentMethod): PaymentProcessor {
  switch (method) {
    case 'credit_card': return new StripeProcessor(config.stripe);
    case 'paypal': return new PayPalProcessor(config.paypal);
    case 'bank_transfer': return new BankTransferProcessor(config.bank);
  }
}

// 2. STRATEGY — pricing calculation
const pricingStrategy = new CompositePricing([
  new SeasonalDiscount(seasonRules),
  new LoyaltyDiscount(user.loyaltyTier),
  new BulkDiscount(cart.totalQuantity),
]);

// 3. STATE — order lifecycle
class Order {
  private state: OrderState; // State pattern manages transitions
}

// 4. OBSERVER — react to state changes
eventBus.on('order:placed', async (event) => {
  await inventoryService.reserve(event.items);      // Observer handler 1
  await emailService.sendConfirmation(event.order);  // Observer handler 2
  await analyticsService.trackPurchase(event.order); // Observer handler 3
});

// 5. DECORATOR — repository with cross-cutting concerns
const orderRepo: OrderRepository =
  new LoggedRepository(
    new CachedRepository(
      new PostgresOrderRepository(db),
      cache,
    ),
    logger,
  );

// 6. FACADE — simplified API for controllers
class OrderFacade {
  async placeOrder(request: PlaceOrderRequest): Promise<OrderConfirmation> {
    const pricing = pricingStrategy.calculate(request.items);
    const processor = createPaymentProcessor(request.paymentMethod);
    const payment = await processor.charge(pricing.total);
    const order = Order.create(request, payment);
    await orderRepo.save(order);
    await eventBus.publish(new OrderPlacedEvent(order));
    return OrderConfirmation.from(order);
  }
}

// 7. COMMAND — admin operations with audit trail
class RefundOrderCommand implements Command {
  async execute(): Promise<void> { /* refund logic */ }
  async undo(): Promise<void> { /* reverse refund */ }
}

// 8. CHAIN OF RESPONSIBILITY — middleware pipeline
app.post('/orders',
  rateLimitMiddleware,    // Chain link 1
  authMiddleware,         // Chain link 2
  validateMiddleware,     // Chain link 3
  orderController.create, // Chain link 4
);

// 8 patterns cooperating cleanly — each solving its specific problem
```

### Content Management System

```typescript
// 1. COMPOSITE — content tree
interface ContentNode {
  render(): string;
  findById(id: string): ContentNode | null;
}

class Page implements ContentNode { /* contains sections */ }
class Section implements ContentNode { /* contains blocks */ }
class TextBlock implements ContentNode { /* leaf */ }
class ImageBlock implements ContentNode { /* leaf */ }

// 2. VISITOR — different output formats
class HtmlRenderer implements ContentVisitor<string> { /* ... */ }
class MarkdownRenderer implements ContentVisitor<string> { /* ... */ }
class PdfRenderer implements ContentVisitor<Buffer> { /* ... */ }

// 3. MEMENTO — version history
class ContentEditor {
  save(): ContentSnapshot { /* save state */ }
  restore(snapshot: ContentSnapshot): void { /* restore */ }
}

// 4. BUILDER — complex content creation
const page = new PageBuilder()
  .title('About Us')
  .addSection(s => s
    .heading('Our Team')
    .addTextBlock('We are...')
    .addImageBlock('/team.jpg', 'Team photo')
  )
  .addSection(s => s
    .heading('Contact')
    .addContactForm()
  )
  .build();

// 5. TEMPLATE METHOD — publish workflow
abstract class PublishWorkflow {
  async publish(content: Content): Promise<void> {
    await this.validate(content);     // Step 1
    await this.transform(content);    // Step 2 (varies)
    await this.deploy(content);       // Step 3 (varies)
    await this.notifySubscribers(content); // Step 4
  }
  protected abstract transform(content: Content): Promise<void>;
  protected abstract deploy(content: Content): Promise<void>;
}
```

### TypeScript-specific Patterns

```typescript
// 1. MODULE PATTERN (Singleton by nature)
// TypeScript modules are cached → every import gets same instance
export const db = new Pool(config);
export const cache = new Redis(config);

// 2. DISCRIMINATED UNIONS (replaces Visitor/State in many cases)
type Result<T, E = Error> =
  | { success: true; data: T }
  | { success: false; error: E };

// 3. BRANDED TYPES (replaces some Flyweight/Value Object patterns)
type UserId = string & { __brand: 'UserId' };
type OrderId = string & { __brand: 'OrderId' };

function createUserId(id: string): UserId {
  if (!id.startsWith('usr_')) throw new Error('Invalid user ID');
  return id as UserId;
}

// 4. TYPE-LEVEL PROGRAMMING (replaces runtime checks)
// Readonly, Pick, Omit, Record — TypeScript built-in type transformers

// 5. FUNCTION OVERLOADS (replaces some Factory patterns)
function parse(input: string): JsonObject;
function parse(input: Buffer): BinaryData;
function parse(input: string | Buffer): JsonObject | BinaryData {
  if (typeof input === 'string') return JSON.parse(input);
  return decodeBinary(input);
}
```

## Anti-Patterns: Khi dùng Pattern sai cách

### 1. Pattern Fever — Dùng pattern everywhere

```typescript
// ❌ Simple CRUD app nhưng có:
// - Abstract Factory cho database (chỉ dùng PostgreSQL)
// - Strategy cho validation (chỉ có 1 cách validate)
// - Observer cho logging (console.log đủ rồi)
// - Builder cho User entity (chỉ có 3 fields)
// - Singleton cho config (module export đủ rồi)

// ✅ Just write the code
async function createUser(input: CreateUserInput): Promise<User> {
  const user = { id: uuid(), ...input, createdAt: new Date() };
  await db.query('INSERT INTO users ...', [user.id, user.name, user.email]);
  return user;
}
```

### 2. Golden Hammer — 1 pattern giải quyết mọi thứ

```typescript
// ❌ "Mọi thứ đều là Observer pattern!"
// Login? → Event
// Validation? → Event
// Database query? → Event
// Rendering? → Event
// → Spaghetti event flow, impossible to debug

// ✅ Use the right tool for the job
// Login → direct function call
// Validation → synchronous validation function
// Database → repository pattern
// Side effects after login → Observer pattern (here it fits)
```

### 3. Wrong Level of Abstraction

```typescript
// ❌ Strategy pattern cho 2 branches
interface GreetingStrategy {
  greet(name: string): string;
}

class FormalGreeting implements GreetingStrategy {
  greet(name: string): string { return `Dear ${name},`; }
}

class CasualGreeting implements GreetingStrategy {
  greet(name: string): string { return `Hey ${name}!`; }
}

// 2 classes, 1 interface, cho cái này? Really?

// ✅ Just use a conditional
function greet(name: string, formal: boolean): string {
  return formal ? `Dear ${name},` : `Hey ${name}!`;
}
```

### 4. Incomplete Pattern Implementation

```typescript
// ❌ "Observer pattern" nhưng không handle unsubscribe, error handling, memory leaks
class EventBus {
  private listeners: Record<string, Function[]> = {};

  on(event: string, fn: Function): void {
    this.listeners[event] = [...(this.listeners[event] ?? []), fn];
    // No unsubscribe mechanism
    // No error handling
    // Potential memory leak if listeners accumulate
  }
}

// ✅ Proper implementation hoặc dùng existing library
// Xem TypedEventEmitter ở phần Observer pattern
```

## Decision Guide

### Tôi đang gặp vấn đề gì? → Pattern nào giải quyết?

```
"Tạo object phức tạp có nhiều optional config"
→ Builder

"Cần swap algorithm tùy context"
→ Strategy (function-based preferred in TS)

"Object behaves differently based on state"
→ State (or state machine)

"Cần notify nhiều components khi data thay đổi"
→ Observer / EventEmitter

"Cần undo/redo"
→ Command + Memento

"Integrate third-party lib với interface khác"
→ Adapter

"Thêm logging/caching/auth cho existing service"
→ Decorator

"Complex subsystem, cần simple API"
→ Facade

"Request qua nhiều handlers, mỗi handler xử lý hoặc pass"
→ Chain of Responsibility (middleware)

"Dữ liệu dạng cây, xử lý uniform"
→ Composite

"Cần tạo family of related objects"
→ Abstract Factory

"Lazy load expensive resource"
→ Proxy (Virtual)

"Kiểm soát access / permissions"
→ Proxy (Protection)

"Nhiều objects cùng type, tiết kiệm memory"
→ Flyweight

"2 dimensions of variation (type × implementation)"
→ Bridge

"Thêm operations cho stable type hierarchy"
→ Visitor / discriminated union + functions

"Simple DSL / rule engine"
→ Interpreter / expression evaluator

"Fixed algorithm structure, variable steps"
→ Template Method

"Many-to-many communication through coordinator"
→ Mediator

"Only 1 instance of resource"
→ Singleton (module-level in TS)

"Clone objects as templates"
→ Prototype (structuredClone in TS)

"Duyệt collection mà ẩn implementation"
→ Iterator (generators in TS)
```

### Quick Reference: Bao nhiêu patterns THỰC SỰ cần?

```
Cho 80% dự án TypeScript, bạn chỉ cần nắm vững:

Must-know (dùng hàng ngày):
  1. Strategy (function/interface)
  2. Observer (EventEmitter)
  3. Factory (createXxx functions)
  4. Builder (fluent APIs)
  5. Decorator (wrapping services)
  6. Adapter (third-party integration)
  7. Facade (simplify subsystem)
  8. Chain of Responsibility (middleware)

Good-to-know (dùng khi cần):
  9. Command (undo/redo, job queues)
  10. State (workflow/lifecycle management)
  11. Composite (tree structures)
  12. Proxy (lazy load, access control)
  13. Iterator (generators, pagination)
  14. Template Method (ETL pipelines)

Nice-to-know (niche use cases):
  15-23. Bridge, Flyweight, Memento, Visitor,
         Interpreter, Mediator, Abstract Factory,
         Prototype, Singleton
```

### Nguyên tắc cuối cùng

> **Đừng bắt đầu bằng pattern. Bắt đầu bằng vấn đề.**
>
> 1. Viết code đơn giản nhất giải quyết vấn đề
> 2. Khi code bắt đầu đau (khó test, khó extend, khó đọc)
> 3. Nhận ra DẤU HIỆU cho biết pattern nào có thể giúp
> 4. Refactor theo pattern phù hợp
>
> Code không có pattern ≠ code xấu.
> Code có pattern ≠ code tốt.
> Code giải quyết vấn đề rõ ràng, dễ maintain = code tốt.
