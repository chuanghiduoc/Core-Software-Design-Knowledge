## SRE Philosophy

### Tại sao SRE tồn tại?

```
Traditional Ops:                    SRE:
──────────────                      ────
"Giữ hệ thống ổn định"             "Giữ hệ thống đủ ổn định để ship feature nhanh"
Manual operations                   Automate everything
Phản ứng khi sự cố xảy ra          Proactively engineer reliability
Ops vs Dev (xung đột)              Ops = Dev (cùng team, cùng mục tiêu)
"Không thay đổi = không lỗi"       "Thay đổi có kiểm soát = innovation"
```

### 7 Nguyên lý cốt lõi của SRE

```
1. EMBRACE RISK
   → 100% reliability là sai mục tiêu. Hãy chấp nhận mức risk phù hợp.

2. SERVICE LEVEL OBJECTIVES (SLOs)
   → Đo lường và đặt mục tiêu reliability cụ thể, dựa trên data.

3. ELIMINATE TOIL
   → Tự động hóa mọi công việc manual, lặp lại, không mang lại giá trị lâu dài.

4. MONITORING
   → Hệ thống phải tự nói cho bạn biết nó đang ổn hay không.

5. RELEASE ENGINEERING
   → Ship nhanh, an toàn, có thể rollback bất cứ lúc nào.

6. SIMPLICITY
   → Hệ thống đơn giản = hệ thống đáng tin cậy hơn.

7. SHARE OWNERSHIP
   → Dev và Ops cùng chịu trách nhiệm, không đổ lỗi.
```

### SRE vs DevOps

```
DevOps = cultural movement (triết lý, văn hóa)
SRE = prescriptive implementation (phương pháp cụ thể)

DevOps nói: "Dev và Ops phải làm việc cùng nhau"
SRE nói:    "Đây là CÁCH CỤ THỂ để Dev và Ops làm việc cùng nhau"

Google nói: "class SRE implements DevOps"
```

## SLI — Service Level Indicators

### SLI là gì?

SLI là **metric đo lường chất lượng dịch vụ từ góc nhìn của user**. Không phải CPU usage, không phải disk space — mà là thứ **user thực sự quan tâm**.

### Nguyên tắc chọn SLI

```
1. Đo từ góc nhìn user, không phải server
   → Request latency tại client, không phải server-side processing time

2. Là tỷ lệ (ratio), không phải số tuyệt đối
   → "99.5% requests < 200ms", không phải "trung bình 150ms"

3. Đo được tự động, liên tục
   → Không cần human để kiểm tra

4. Đơn giản, dễ hiểu
   → Mọi người trong team phải hiểu SLI nghĩa là gì
```

### SLI cho các loại service khác nhau

## SLO — Service Level Objectives

### SLO là gì?

SLO = **mục tiêu cụ thể** cho mỗi SLI. Ví dụ: "99.9% requests phải thành công trong mỗi rolling 30-day window."

### Cách đặt SLO

```
Bước 1: Đo SLI hiện tại trong 2-4 tuần
Bước 2: Đặt SLO hơi thấp hơn hiện tại (có buffer)
Bước 3: Review và điều chỉnh mỗi quý
Bước 4: Tightening dần khi hệ thống mature

Ví dụ:
  Đo được availability hiện tại = 99.95%
  Đặt SLO = 99.9% (có buffer 0.05%)
  Sau 2 quý, nếu stable → cân nhắc nâng lên 99.95%
```

### SLO Template

```typescript
interface SLO {
  sliName: string;
  target: number;              // 0.999 = 99.9%
  window: '7d' | '28d' | '30d' | '90d';
  windowType: 'rolling' | 'calendar';
  consequences: string;        // Chuyện gì xảy ra khi vi phạm SLO
}

// Production SLO examples
const productionSLOs: SLO[] = [
  {
    sliName: 'api_availability',
    target: 0.999,             // 99.9% — cho phép ~43 phút downtime/tháng
    window: '30d',
    windowType: 'rolling',
    consequences: 'Freeze feature releases, focus on reliability',
  },
  {
    sliName: 'api_latency_p99',
    target: 0.99,              // 99% requests < 300ms
    window: '30d',
    windowType: 'rolling',
    consequences: 'Investigate and fix performance regression',
  },
  {
    sliName: 'checkout_success_rate',
    target: 0.995,             // 99.5% checkouts thành công
    window: '7d',
    windowType: 'rolling',
    consequences: 'P1 incident, immediate investigation',
  },
];

// ===== Tính toán "nines" =====
// Bảng chuyển đổi giữa % uptime và thời gian downtime cho phép:
//
// 99%     (2 nines)  = 7.31 giờ/tháng     = 3.65 ngày/năm
// 99.9%   (3 nines)  = 43.8 phút/tháng    = 8.77 giờ/năm
// 99.95%  (3.5)      = 21.9 phút/tháng    = 4.38 giờ/năm
// 99.99%  (4 nines)  = 4.38 phút/tháng    = 52.6 phút/năm
// 99.999% (5 nines)  = 26.3 giây/tháng    = 5.26 phút/năm

function calculateAllowedDowntime(sloTarget: number, windowDays: number): string {
  const totalMinutes = windowDays * 24 * 60;
  const allowedDowntimeMinutes = totalMinutes * (1 - sloTarget);

  if (allowedDowntimeMinutes >= 60) {
    return `${(allowedDowntimeMinutes / 60).toFixed(1)} giờ`;
  }
  if (allowedDowntimeMinutes >= 1) {
    return `${allowedDowntimeMinutes.toFixed(1)} phút`;
  }
  return `${(allowedDowntimeMinutes * 60).toFixed(1)} giây`;
}

// 99.9% trong 30 ngày = 43.2 phút downtime cho phép
console.log(calculateAllowedDowntime(0.999, 30)); // "43.2 phút"
```

### Đừng đặt SLO quá cao

```
❌ SAI: "Chúng ta cần 99.99% availability!"
   → Bạn chỉ có 4.38 phút downtime/tháng
   → Mọi deployment đều là risk
   → Team sợ ship feature
   → Chi phí infrastructure tăng gấp 10x

✅ ĐÚNG: "User cần gì? Ứng dụng internal? 99.5% là đủ."
   → 3.65 giờ downtime/tháng
   → Ship feature thoải mái
   → Chi phí hợp lý
   → Team focus vào tạo giá trị

Quy tắc ngón tay cái:
  Internal tools:           99% - 99.5%
  B2B SaaS:                 99.9%
  Consumer-facing:          99.9% - 99.95%
  Payment/Financial:        99.95% - 99.99%
  Infrastructure (DNS, CDN): 99.99%+
```

## SLA — Service Level Agreements

### SLA vs SLO

```
SLO = internal goal (team tự đặt)
SLA = external contract (cam kết với khách hàng, có hậu quả pháp lý/tài chính)

Quy tắc: SLA phải THẤP HƠN SLO
  SLO = 99.95%  →  SLA = 99.9%
  Nếu SLO bị vi phạm → team sửa, không ai bên ngoài biết
  Nếu SLA bị vi phạm → company mất tiền, mất trust
```

### SLA trong thực tế

```typescript
interface SLAContract {
  metric: string;
  target: number;
  measurementWindow: string;
  credits: SLACredit[];
  exclusions: string[];
}

interface SLACredit {
  availabilityRange: { min: number; max: number };
  creditPercentage: number; // % of monthly bill credited back
}

const exampleSLA: SLAContract = {
  metric: 'monthly_uptime_percentage',
  target: 0.999,
  measurementWindow: 'calendar_month',
  credits: [
    { availabilityRange: { min: 0.99, max: 0.999 }, creditPercentage: 10 },
    { availabilityRange: { min: 0.95, max: 0.99 },  creditPercentage: 25 },
    { availabilityRange: { min: 0, max: 0.95 },      creditPercentage: 50 },
  ],
  exclusions: [
    'Scheduled maintenance (thông báo trước 48 giờ)',
    'Force majeure (thiên tai, chiến tranh)',
    'Lỗi do chính customer gây ra (abuse, misconfiguration)',
    'Beta features / Preview features',
  ],
};

// Business impact calculation
function calculateSLACredit(
  contract: SLAContract,
  actualAvailability: number,
  monthlyBill: number,
): number {
  if (actualAvailability >= contract.target) return 0;

  const applicableCredit = contract.credits.find(
    c => actualAvailability >= c.availabilityRange.min
      && actualAvailability < c.availabilityRange.max
  );

  if (!applicableCredit) return 0;
  return monthlyBill * (applicableCredit.creditPercentage / 100);
}

// Ví dụ: availability = 99.5%, bill = $10,000/tháng
// → Credit = $10,000 * 10% = $1,000
```

## Error Budgets

### Concept

Error Budget là **lượng unreliability cho phép** trong một khoảng thời gian. Đây là công cụ quan trọng nhất để **cân bằng giữa velocity và reliability**.

```
Error Budget = 1 - SLO target

SLO = 99.9%  →  Error Budget = 0.1% = 43.2 phút/tháng
SLO = 99.5%  →  Error Budget = 0.5% = 3.6 giờ/tháng
SLO = 99%    →  Error Budget = 1%   = 7.3 giờ/tháng
```

### Error Budget Calculation

```typescript
interface ErrorBudgetStatus {
  sloTarget: number;
  windowDays: number;
  totalRequests: number;
  failedRequests: number;
  budgetTotal: number;          // Tổng error budget (requests)
  budgetConsumed: number;       // Đã dùng bao nhiêu
  budgetRemaining: number;      // Còn lại bao nhiêu
  budgetConsumedPercent: number; // % đã dùng
  burnRate: number;             // Tốc độ tiêu thụ (1.0 = bình thường)
  projectedExhaustion: Date | null; // Dự kiến hết budget khi nào
}

function calculateErrorBudget(
  sloTarget: number,
  windowDays: number,
  totalRequests: number,
  failedRequests: number,
  elapsedDays: number,
): ErrorBudgetStatus {
  const budgetTotal = Math.floor(totalRequests * (1 - sloTarget));
  const budgetConsumed = failedRequests;
  const budgetRemaining = Math.max(0, budgetTotal - budgetConsumed);
  const budgetConsumedPercent = budgetTotal > 0
    ? (budgetConsumed / budgetTotal) * 100
    : 0;

  // Burn rate: nếu = 1, đang tiêu budget đúng tốc độ
  // Nếu > 1, đang tiêu nhanh hơn → sẽ hết trước khi hết window
  const expectedConsumedPercent = (elapsedDays / windowDays) * 100;
  const burnRate = expectedConsumedPercent > 0
    ? budgetConsumedPercent / expectedConsumedPercent
    : 0;

  // Dự kiến hết budget khi nào
  let projectedExhaustion: Date | null = null;
  if (burnRate > 1 && budgetConsumed > 0) {
    const daysPerBudgetUnit = elapsedDays / budgetConsumed;
    const daysUntilExhaustion = budgetRemaining * daysPerBudgetUnit;
    projectedExhaustion = new Date();
    projectedExhaustion.setDate(projectedExhaustion.getDate() + daysUntilExhaustion);
  }

  return {
    sloTarget,
    windowDays,
    totalRequests,
    failedRequests,
    budgetTotal,
    budgetConsumed,
    budgetRemaining,
    budgetConsumedPercent,
    burnRate,
    projectedExhaustion,
  };
}

// Ví dụ thực tế:
const status = calculateErrorBudget(
  0.999,        // SLO 99.9%
  30,           // 30-day window
  10_000_000,   // 10M requests trong window
  5_000,        // 5,000 failed requests
  15,           // Đã qua 15 ngày
);
// budgetTotal = 10,000 requests
// budgetConsumed = 5,000 (50%)
// Nhưng mới qua 50% thời gian → burnRate = 1.0 → Ổn!
```

### Error Budget Policy

```typescript
// Error Budget Policy: quy định hành động dựa trên % budget đã dùng

interface ErrorBudgetPolicy {
  thresholds: ErrorBudgetThreshold[];
}

interface ErrorBudgetThreshold {
  budgetConsumedPercent: number;
  actions: string[];
}

const errorBudgetPolicy: ErrorBudgetPolicy = {
  thresholds: [
    {
      budgetConsumedPercent: 50,   // Đã dùng 50% budget
      actions: [
        'Review tất cả recent changes đã gây lỗi',
        'Tăng cường monitoring cho high-risk components',
        'Prioritize reliability fixes trong sprint tiếp theo',
      ],
    },
    {
      budgetConsumedPercent: 75,   // Đã dùng 75% budget
      actions: [
        'Freeze tất cả risky feature launches',
        'Chỉ cho phép deploy với canary + gradual rollout',
        'Bắt buộc load test trước khi deploy',
        'Daily standup review error budget status',
      ],
    },
    {
      budgetConsumedPercent: 100,  // Budget hết
      actions: [
        'FREEZE toàn bộ feature development',
        'Team 100% focus vào reliability',
        'Mọi deploy phải có VP approval',
        'Postmortem cho tất cả incidents đã xảy ra',
        'Không resume feature work cho đến khi budget recover',
      ],
    },
  ],
};

function getRequiredActions(
  policy: ErrorBudgetPolicy,
  currentConsumedPercent: number,
): string[] {
  const applicableThresholds = policy.thresholds
    .filter(t => currentConsumedPercent >= t.budgetConsumedPercent)
    .sort((a, b) => b.budgetConsumedPercent - a.budgetConsumedPercent);

  return applicableThresholds.length > 0
    ? applicableThresholds[0].actions
    : ['Business as usual — ship features!'];
}
```

## Toil

### Toil là gì?

Toil là **công việc manual, lặp lại, có thể tự động hóa, không mang lại giá trị lâu dài, và tỷ lệ tăng theo kích thước hệ thống**.

```
Toil có 5 đặc điểm:
  1. MANUAL       → Cần người làm bằng tay
  2. REPETITIVE   → Lặp đi lặp lại
  3. AUTOMATABLE  → Có thể viết script/tool thay thế
  4. TACTICAL     → Phản ứng, không proactive
  5. NO LASTING VALUE → Không cải thiện service vĩnh viễn

Ví dụ toil:
  ❌ Restart service khi memory leak
  ❌ Manually approve mỗi deployment
  ❌ Copy-paste config khi scale up
  ❌ Manually create user accounts
  ❌ Check logs hàng ngày để tìm lỗi
  ❌ Manually rotate SSL certificates

KHÔNG phải toil:
  ✅ On-call (reactive, nhưng cần judgment)
  ✅ Postmortem writing (creative work)
  ✅ Architecture design (strategic)
  ✅ Code review (requires expertise)
```

### Đo lường và giảm Toil

```typescript
interface ToilItem {
  name: string;
  description: string;
  frequency: 'daily' | 'weekly' | 'monthly' | 'per_incident';
  timePerOccurrence: number;  // phút
  occurrencesPerMonth: number;
  automationEffort: 'low' | 'medium' | 'high';  // effort để tự động hóa
  automationPriority: number; // tính từ impact / effort
}

function calculateToilMetrics(items: ToilItem[]): {
  totalToilHoursPerMonth: number;
  toilPercentage: number;       // % thời gian team dành cho toil
  topAutomationTargets: ToilItem[];
} {
  const totalMinutes = items.reduce(
    (sum, item) => sum + item.timePerOccurrence * item.occurrencesPerMonth,
    0,
  );

  const totalToilHours = totalMinutes / 60;
  // Giả sử team 5 người, mỗi người 160 giờ/tháng
  const totalTeamHours = 5 * 160;
  const toilPercentage = (totalToilHours / totalTeamHours) * 100;

  const topAutomationTargets = [...items]
    .sort((a, b) => b.automationPriority - a.automationPriority)
    .slice(0, 5);

  return { totalToilHoursPerMonth: totalToilHours, toilPercentage, topAutomationTargets };
}

// Google khuyến nghị: Toil không nên vượt quá 50% thời gian của SRE team
// Mục tiêu lý tưởng: < 30%
// Nếu > 50% → team không có thời gian cho engineering work → dần dần tệ hơn

// Ví dụ thực tế:
const toilItems: ToilItem[] = [
  {
    name: 'Manual deployment approvals',
    description: 'Review và approve mỗi deploy request',
    frequency: 'daily',
    timePerOccurrence: 15,
    occurrencesPerMonth: 60,
    automationEffort: 'medium',
    automationPriority: 9, // high impact, medium effort
  },
  {
    name: 'SSL certificate renewal',
    description: 'Manually renew và deploy SSL certs',
    frequency: 'monthly',
    timePerOccurrence: 60,
    occurrencesPerMonth: 2,
    automationEffort: 'low',
    automationPriority: 8, // medium impact, low effort
  },
  {
    name: 'Log investigation for alerts',
    description: 'SSH vào server, grep logs khi có alert',
    frequency: 'per_incident',
    timePerOccurrence: 30,
    occurrencesPerMonth: 20,
    automationEffort: 'high',
    automationPriority: 7, // high impact, high effort
  },
];
```

### Toil Reduction Strategies

```
Chiến lược giảm toil theo thứ tự ưu tiên:

1. ELIMINATE
   → Công việc này có thực sự cần không? Bỏ luôn nếu không cần.
   Ví dụ: Manual approval cho deploy to staging → bỏ luôn

2. AUTOMATE
   → Viết script/tool để thay thế
   Ví dụ: SSL renewal → Let's Encrypt + cert-manager

3. REDUCE FREQUENCY
   → Không bỏ được, không automate được → giảm tần suất
   Ví dụ: Daily manual DB backup check → weekly

4. REDUCE TIME
   → Tạo tool để làm nhanh hơn
   Ví dụ: Runbook automation → 30 phút → 5 phút

5. SHARE LOAD
   → Chia đều cho team, không để 1 người gánh hết
   Ví dụ: On-call rotation thay vì "hero engineer"
```

## Risk Analysis & Management

### Risk Matrix

```typescript
interface RiskItem {

// Risk scoring: probability x impact
function riskScore(probability: string, impact: string): number {
  const probMap: Record<string, number> = { low: 1, medium: 2, high: 3 };
  const impactMap: Record<string, number> = { low: 1, medium: 2, high: 3, critical: 4 };
  return probMap[probability] * impactMap[impact];
}
```

### Tổng kết SRE Principles

```
1. Đặt SLI/SLO/SLA cho MỌI service quan trọng
2. Tính Error Budget và enforce Error Budget Policy
3. Đo và giảm Toil xuống < 50%
4. Phân tích Risk và có mitigation plan
5. Review SLOs mỗi quý, điều chỉnh theo data
6. Blameless culture: đổ lỗi cho SYSTEM, không phải NGƯỜI
7. Balance velocity và reliability qua Error Budget

SRE không phải là "không bao giờ có incident".
SRE là "có incident nhưng biết trước, phản ứng nhanh, và học từ nó."
```
