## Senior vs Junior: Tư duy khác biệt

```
Junior Engineer:                          Senior Engineer:
"Cái nào cool hơn?"                       "Context của chúng ta là gì?"
"Blog/tutorial nói gì?"                   "Trade-offs là gì?"
"Cái nào mình biết?"                      "Quyết định này reversible không?"
"Senior nói gì?" (follow blindly)         "Ai sẽ bị ảnh hưởng?"
                                          "6 tháng sau sẽ ra sao?"
                                          "Data nào support quyết định?"
```

### 6 đặc điểm tư duy của người ra quyết định giỏi

**1. Comfort with ambiguity** — Senior biết 70% thông tin đã đủ để quyết định.

```typescript
interface DecisionContext {
  knownFacts: string[];          // Những gì chắc chắn biết
  assumptions: string[];         // Những gì giả định (cần validate)
  unknowns: string[];            // Những gì chưa biết
  riskIfWrong: 'low' | 'medium' | 'high';
}
```

**2. Thinking in trade-offs** — Không có "best", chỉ có "best for our context".

**3. Time awareness** — Quyết định tốt HÔM NAY > Quyết định hoàn hảo THÁNG SAU.

**4. Stakeholder empathy** — Hiểu impact lên từng nhóm người.

**5. Historical perspective** — Học từ quyết định trong quá khứ.

**6. Intellectual humility** — Sẵn sàng nhận sai và thay đổi.

## Trade-off Analysis

> Mọi quyết định kỹ thuật đều là trade-off. Nếu ai đó nói "giải pháp này không có
> nhược điểm" — họ chưa hiểu đủ sâu.

### Trade-off phổ biến trong software

```
Consistency     ↔  Availability       (CAP theorem)
Performance     ↔  Readability        (Optimized code khó đọc)
Flexibility     ↔  Simplicity         (Abstraction tốn complexity)
Speed to market ↔  Code quality       (Tech debt)
DRY             ↔  Decoupling         (Shared code = coupling)
Type safety     ↔  Developer velocity (Strict typing tốn effort)
Build           ↔  Buy                (Control vs speed)
```

### Framework phân tích trade-off

```typescript
interface Option {
  name: string;
  pros: string[];
  cons: string[];
  risks: Array<{ description: string; probability: string; impact: string; mitigation: string }>;
  effort: 'low' | 'medium' | 'high';
  reversibility: 'easy' | 'moderate' | 'difficult';
}
```

### Ví dụ: State Management cho React app (5 developers)

```
Option A: Redux Toolkit → ✅ Predictable, team quen  ❌ Verbose, overkill
Option B: Zustand       → ✅ Đơn giản, TS-first     ❌ Team chưa biết
Option C: React Query   → ✅ Server state native     ❌ Chỉ server state

→ QUYẾT ĐỊNH: Option C — 80% state là server state, React Query đủ.
→ RISK MITIGATION: Nếu client state phức tạp → Zustand (two-way door).
```

### Bẫy phổ biến

| Bias | Ví dụ sai | Cách đúng |
|------|-----------|-----------|
| False dichotomy | "Monolith HOẶC Microservices" | Modular Monolith là option giữa |
| Anchoring | "Research PostgreSQL 2 tuần, dùng luôn" | So sánh fair với alternatives |
| Bandwagon | "K8s vì mọi company lớn dùng" | 3 services + 2 devs → docker-compose đủ |
| Recency | "Bun mới ra, chuyển hết" | Thử internal tools trước, chưa production |

## Reversibility: One-Way Doors vs Two-Way Doors

> Framework của Jeff Bezos. Mental model quan trọng nhất cho việc ra quyết định
> nhanh mà không liều lĩnh.

```
TWO-WAY DOOR (Type 2):              ONE-WAY DOOR (Type 1):
  Có thể quay lại nếu sai             Không thể/rất tốn kém để quay lại
  Quyết định NHANH, ủy quyền          Quyết định CẨN THẬN, review kỹ
  Chấp nhận risk                       Cần consensus và analysis sâu
```

### Phân loại trong software

```
ONE-WAY DOORS:                        TWO-WAY DOORS:
├── Programming language chính         ├── Testing framework
├── Database engine cho core data      ├── Linting/formatting rules
├── Monolith vs microservices          ├── UI component library
├── Cloud provider                     ├── CI/CD tool
├── Core data model                    ├── Monitoring platform
├── Public API contract                ├── Internal code organization
└── Pricing model                      └── Branching strategy
```

### Checklist xác định loại quyết định

```
1. Chi phí revert cao?           → One-way
2. Nhiều người/system bị ảnh hưởng? → One-way
3. Cần data migration?           → Nghiêng one-way
4. Có public contract (API/SDK)? → One-way
```

### Biến one-way thành two-way: Abstraction layer

```typescript
// Dùng interface để tạo seam — database có thể swap
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

class PostgresOrderRepository implements OrderRepository { /* ... */ }
class MongoOrderRepository implements OrderRepository { /* ... */ }
// → Application code không đổi khi swap database
```

## DACI Framework

> Khi nhiều người tham gia, DACI làm rõ ai chịu trách nhiệm gì.

```
D — Driver:       Dẫn dắt quá trình, 1 người duy nhất
A — Approver:     Quyết định cuối cùng, 1-2 người
C — Contributors: Chuyên gia cung cấp input, 3-5 người
I — Informed:     Được thông báo kết quả sau khi quyết định
```

**Ví dụ:** Migrate REST sang GraphQL cho mobile APIs

```
D: Tech Lead Mobile    |  A: VP Engineering
C: Senior Backend, Mobile Lead, DevOps Lead, PM
I: Frontend team, QA team, Customer Support
Timeline: 2 tuần research + 1 tuần review → quyết định
```

**Dùng DACI khi:** Ảnh hưởng nhiều team, ý kiến trái chiều, one-way door.
**Không cần khi:** Trong 1 team nhỏ, two-way door, đã có consensus.

## Decision Matrix với Weighted Criteria

### Ví dụ: Chọn message queue (E-commerce, 10K orders/day, team 8 người)

```
| Criteria           | Weight | RabbitMQ | Kafka | AWS SQS | Redis Streams |
|--------------------|--------|----------|-------|---------|---------------|
| Performance        | 20%    | 4        | 5     | 3       | 4             |
| Team familiarity   | 25%    | 2        | 1     | 4       | 5             |
| Ops complexity     | 20%    | 3        | 2     | 5       | 4             |
| Ecosystem          | 15%    | 4        | 5     | 4       | 3             |
| Cost               | 10%    | 3        | 2     | 4       | 5             |
| Scalability        | 10%    | 3        | 5     | 4       | 3             |
| WEIGHTED TOTAL     |        | 3.00     | 3.10  | 4.00    | 4.10          |

→ Winner: Redis Streams — team đã quen Redis, ops đơn giản
→ Lưu ý: Nếu scalability weight tăng 25%, Kafka thắng
```

### Lưu ý quan trọng

```
Decision matrix là CÔNG CỤ HỖ TRỢ, không phải oracle:
1. Garbage In, Garbage Out — weights và scores chủ quan
2. 3-5 criteria đủ — quá nhiều → averaged out
3. "Gut check" — nếu matrix nói A nhưng gut nói B, tìm hiểu tại sao
4. Document weights TRƯỚC khi score — tránh adjust để fit kết quả
```

## Second-Order Thinking

> First-order: "Chuyện gì xảy ra?" Second-order: "Rồi sau đó thì sao?"

```
Action:        "Thêm caching layer"
First-order:   Response time giảm 80%
Second-order:  Cache invalidation phức tạp → stale data bugs
Third-order:   Team debug stale data → velocity giảm → delivery chậm
```

### Ví dụ: "Tách microservices để team work độc lập"

```
1st: ✅ Team A và B deploy độc lập
2nd: ⚠️ API contracts cần negotiate, versioning phức tạp
3rd: ❌ Cross-service debugging tốn 3x, cần distributed tracing,
        hiring cần distributed systems experience
```

### Mental model: Pre-mortem

```
Thay vì: "Giải pháp này sẽ thành công vì..."
Hãy hỏi: "Giả sử 6 tháng sau project thất bại. Tại sao?"

Pre-mortem cho GraphQL adoption:
- "Federation quá phức tạp cho team size"
- "N+1 query problem không phát hiện sớm"
- "Client team không adopt vì learning curve"
→ Mỗi failure reason = 1 risk cần mitigation plan
```

## Sunk Cost Fallacy trong Software

> "Chúng ta đã đầu tư 6 tháng, không thể bỏ được."
> — Câu nói đắt giá nhất trong software engineering.

```
Chi phí đã chi = KHÔNG liên quan đến quyết định tiếp theo.
Câu hỏi đúng: "Biết những gì biết BÂY GIỜ,
               nếu bắt đầu lại từ đầu, có chọn giải pháp này không?"
```

### Framework: Abandon vs Persist

```
1. Bắt đầu lại từ ZERO, có chọn lại không? → KHÔNG = abandon signal
2. Trend tốt lên hay xấu đi?               → Xấu = abandon sớm
3. Ongoing cost (maintenance + opportunity)? → Tính cụ thể
4. Switching cost (migration + risk)?        → Tính cụ thể
5. 6 tháng nữa có cải thiện?                → KHÔNG = abandon ngay
```

### Ví dụ: Custom CMS đã 18 tháng, 2 devs full-time maintain

```
- 40% fix bugs, 30% build features mà Strapi đã có
- Ongoing cost: $300K/year  |  Switching cost: ~$40K (3 tháng)
→ QUYẾT ĐỊNH: Abandon, migrate sang Payload CMS
→ 18 tháng "mất" không phải lý do để mất thêm 18 tháng
```

### Kỹ thuật giảm bias

1. **Regular checkpoints** — Review quyết định mỗi quarter
2. **Kill criteria** — Đặt trước điều kiện dừng ("adoption < 30% → reconsider")
3. **Devil's advocate** — Assign người phản biện
4. **Opportunity cost framing** — "2 devs này có thể ship gì khác?"

## Analysis Paralysis

> Ngược với sunk cost: thay vì tiếp tục sai, bạn không bắt đầu được.

### Dấu hiệu

```
❌ Research hàng tuần cho two-way door  |  ❌ So sánh 10+ options
❌ POC cho MỌI option trước khi chọn   |  ❌ Meetings lặp lại, không ai quyết
```

### Khi nào DỪNG phân tích

```
70/30 Rule:  70% thông tin đủ để quyết định (trừ one-way doors cần 85-90%)
Timeboxing:  Two-way door: 1-3 ngày | One-way medium: 1-2 tuần | One-way high: 1 tháng
```

### Kỹ thuật thoát

**Default options** — Dùng khi không có lý do mạnh để chọn khác:
```
ORM → Prisma  |  Testing → Vitest  |  CI/CD → GitHub Actions
Cloud → AWS   |  Database → PostgreSQL
"Need a REASON to deviate, not a reason to use the default."
```

**Satisficing > Maximizing** — Tìm option ĐỦ TỐT thay vì TỐT NHẤT.
Context thay đổi nhanh → "best" hôm nay khác "best" tháng sau.

## Real-World Decision Examples

### Ví dụ 1: Monolith hay Microservices?

```
Context: Fintech startup, Series A, 15 engineers, lending platform

                           Monolith    Microservices
Team đủ sức?                ✅          ❌ (cần DevOps, k8s)
Time to market?             ✅ Nhanh    ❌ Chậm 2-3x
Operational complexity?     ✅ Thấp     ❌ Cao
Independent scaling?        ❌          ✅
Team independence?          ❌ Limited  ✅

QUYẾT ĐỊNH: Modular Monolith
  → Deploy 1 artifact, code tổ chức theo module/domain
  → Enforce boundaries qua lint rules & code review
  → Khi team > 25, tách module thành service

KILL CRITERIA: deploy < 1/week do coupling → bắt đầu tách
```

### Ví dụ 2: Chọn Database cho Social Media App (musicians)

```
Context: 100K users Y1, 1M Y3, team 6 fullstack TypeScript devs

| Criteria         | Weight | PostgreSQL | MongoDB | PlanetScale |
|------------------|--------|------------|---------|-------------|
| Data model fit   | 30%    | 4          | 4       | 4           |
| Team familiarity | 25%    | 5          | 3       | 4           |
| Ops simplicity   | 20%    | 3          | 3       | 5           |
| Scalability      | 15%    | 4          | 4       | 5           |
| Cost             | 10%    | 5          | 4       | 3           |
| TOTAL            |        | 4.15       | 3.55    | 4.15        |

→ PostgreSQL (tie-break: team experience, free, JSONB flexible)
→ Polyglot: + Redis (cache/realtime) + Typesense khi search traffic lớn
```

### Ví dụ 3: TypeScript vs Go vs Rust cho Image Processing

```
Context: 500K images/day, < 2s latency, team 8 TS devs, 0 Go/Rust

TypeScript + Sharp: ✅ Team biết, Sharp rất nhanh  ❌ GC pressure
Go:                 ✅ Concurrency tốt             ❌ Team learn 3-6 tháng
Rust:               ✅ Best performance             ❌ Learn 6-12 tháng, hiring khó

→ TypeScript + Sharp: 200ms/image đủ, 6 img/s average, horizontal scale
→ Two-way door: stateless service, rewrite Go/Rust khi THỰC SỰ cần
```

## Decision-Making Checklist

```
□ 1. CONTEXT — Team, timeline, budget, constraints
□ 2. TYPE — One-way hay two-way door?
□ 3. OPTIONS — Ít nhất 3 options
□ 4. TRADE-OFFS — Mỗi option được/mất gì?
□ 5. SECOND-ORDER — Hậu quả của hậu quả
□ 6. STAKEHOLDERS — Ai bị ảnh hưởng?
□ 7. EVIDENCE — Data/benchmark/POC support?
□ 8. REVERSIBILITY — Quay lại tốn bao nhiêu?
□ 9. TIMELINE — Deadline quyết định
□ 10. DOCUMENT — Ghi lại trong ADR/RFC
```

### Khi nào dùng checklist nào

```
Quyết định nhanh (two-way door):
  → Chỉ cần items 1, 2, 3, 4 — 30 phút đủ

Quyết định trung bình:
  → Items 1-8 — 1-3 ngày research + team discussion

Quyết định lớn (one-way door):
  → Toàn bộ 10 items — Full RFC process (xem 10.2)
  → Decision matrix (weighted criteria)
  → POC/prototype nếu cần evidence

Đừng over-process two-way doors.
Đừng under-process one-way doors.
Calibrate theo risk level.
```
