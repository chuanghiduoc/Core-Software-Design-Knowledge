## RTO & RPO

```
RPO (Recovery Point Objective):
  Bao nhiêu DATA bạn có thể chấp nhận mất?
  RPO = 0: không được mất data nào (synchronous replication)
  RPO = 1h: chấp nhận mất tối đa 1h data (hourly backups)
  RPO = 24h: chấp nhận mất 1 ngày data (daily backups)

RTO (Recovery Time Objective):
  Bao lâu để hệ thống hoạt động trở lại?
  RTO = 0: zero downtime (active-active multi-region)
  RTO = 5min: auto-failover (hot standby)
  RTO = 1h: restore from backup
  RTO = 24h: rebuild from scratch

Chi phí tỉ lệ NGHỊCH với RPO/RTO:
  RPO=0, RTO=0 → $$$$$ (multi-region active-active)
  RPO=1h, RTO=1h → $$ (automated backups + hot standby)
  RPO=24h, RTO=24h → $ (daily backups, manual restore)

Chọn dựa trên BUSINESS IMPACT:
  Payment service: RPO=0, RTO<5min (mất tiền = mất khách)
  Blog content: RPO=24h, RTO<4h (mất 1 ngày posts = annoying, not fatal)
  Analytics data: RPO=1h, RTO<24h (rebuild from event log possible)
```

## Backup Strategies

### Database Backups

```typescript
// Automated backup strategy for PostgreSQL

// 1. Continuous WAL Archiving (RPO ≈ 0)
// PostgreSQL streams Write-Ahead Logs to S3
// Can restore to ANY point in time

// 2. Automated Snapshots (RPO = snapshot interval)
// RDS automated backups: every 24h + WAL archiving = point-in-time recovery
// Manual snapshots before risky migrations

// 3. Logical Backups (for portability)
// pg_dump for cross-version migrations, partial restores

// Backup verification — CRITICAL: untested backup = no backup
class BackupVerifier {
  async verifyBackup(backupId: string): Promise<VerificationResult> {
    // 1. Restore backup to temporary database
    const tempDb = await this.createTempDatabase();
    await this.restoreBackup(backupId, tempDb);

    // 2. Run integrity checks
    const checks = await Promise.all([
      this.checkTableCounts(tempDb),
      this.checkRecentData(tempDb),     // Has data from last 24h?
      this.checkReferentialIntegrity(tempDb),
      this.runSampleQueries(tempDb),
    ]);

    // 3. Cleanup
    await this.dropTempDatabase(tempDb);

    const allPassed = checks.every(c => c.passed);
    if (!allPassed) {
      await this.alertOpsTeam('Backup verification FAILED', { backupId, checks });
    }

    return { backupId, verified: allPassed, checks, verifiedAt: new Date() };
  }
}

// Schedule: verify backups weekly
// "The backup isn't done until the restore is tested."
```

## High Availability Architectures

### Single-Region HA

```
Active-Passive (Hot Standby):
  ┌──────────┐         ┌──────────┐
  │ Primary  │ ──WAL──► │ Standby  │
  │    DB    │          │    DB    │
  └────┬─────┘          └────┬─────┘
       │ Active              │ Passive (promotes on failure)
       ▼                     ▼
  [App Server 1]       [App Server 2]
  (serving traffic)    (serving traffic)
                 │
           ┌─────▼──────┐
           │Load Balancer│
           └─────────────┘

Failover: Primary DB dies → Standby promotes to Primary (RDS: automatic, ~60s)
```

### Multi-Region HA

```
Region US-East:                    Region EU-West:
  ┌──────────┐                      ┌──────────┐
  │ Primary  │ ───replication──────► │ Replica  │
  │    DB    │                      │    DB    │
  └──────────┘                      └──────────┘
  [App Servers]                     [App Servers]
       │                                 │
  ┌────▼──────┐                    ┌─────▼─────┐
  │    ALB    │                    │    ALB    │
  └───────────┘                    └───────────┘
       │                                 │
       └──────────┬─────────────────────┘
            ┌─────▼──────┐
            │  Route 53  │  (DNS-based routing)
            │ (Geo/Latency)│
            └────────────┘

US users → US-East (low latency)
EU users → EU-West (low latency)
US-East down → ALL traffic → EU-West (failover)
```

## Incident Response

### Severity Levels

```
SEV-1 (Critical): Complete service outage, data loss, security breach
  Response: All hands on deck, 5min response time
  Example: Database down, payment processing broken, data breach

SEV-2 (Major): Partial outage, degraded performance
  Response: On-call team, 15min response time
  Example: One service down, latency > 10x normal, error rate > 10%

SEV-3 (Minor): Minor issue, workaround exists
  Response: Next business day
  Example: UI bug, non-critical feature broken, slow but functional

SEV-4 (Low): Cosmetic, improvement
  Response: Sprint backlog
  Example: Typo, minor UI inconsistency
```

### Incident Response Process

```typescript
// Automated incident detection and response

interface Incident {
  id: string;
  severity: 'sev-1' | 'sev-2' | 'sev-3' | 'sev-4';
  title: string;
  description: string;
  detectedAt: Date;
  acknowledgedAt?: Date;
  resolvedAt?: Date;
  postmortemUrl?: string;
  responders: string[];
  timeline: IncidentEvent[];
}

// Incident lifecycle:
// 1. DETECT: alert fires (automated monitoring)
// 2. ACKNOWLEDGE: on-call confirms they're working on it
// 3. TRIAGE: determine severity, assemble team
// 4. MITIGATE: stop the bleeding (rollback, feature flag off, scale up)
// 5. RESOLVE: fix root cause
// 6. POSTMORTEM: blameless review, action items

// Postmortem template:
interface Postmortem {
  incidentId: string;
  title: string;
  date: Date;
  severity: string;
  duration: string;
  impact: string;          // "2,000 users unable to checkout for 45 minutes"
  summary: string;         // 1-paragraph summary
  timeline: Array<{        // Minute-by-minute timeline
    time: string;
    event: string;
  }>;
  rootCause: string;       // Technical root cause
  contributing: string[];   // Contributing factors
  actionItems: Array<{     // Concrete follow-ups
    action: string;
    owner: string;
    dueDate: string;
    priority: 'P0' | 'P1' | 'P2';
  }>;
  lessonsLearned: string[];
}

// Key principle: BLAMELESS postmortems
// Focus on SYSTEM failures, not PEOPLE failures
// "The deploy script didn't have rollback" not "Bob deployed without testing"
```

## Chaos Engineering

```typescript
// Deliberately inject failures to build confidence in system resilience

// Principle: "Better to break things in controlled conditions
//            than to be surprised at 3am on Saturday"

// Simple chaos experiments:

// 1. Kill a random pod/container
// kubectl delete pod <random-pod> --grace-period=0
// Expected: load balancer routes around it, zero user impact

// 2. Introduce network latency
// tc qdisc add dev eth0 root netem delay 200ms
// Expected: circuit breakers trip, graceful degradation

// 3. Fill disk
// dd if=/dev/zero of=/tmp/fill bs=1M count=10000
// Expected: alerts fire, log rotation works, app handles gracefully

// 4. Simulate dependency failure
class ChaosMiddleware {
  constructor(
    private readonly config: {
      enabled: boolean;
      failureRate: number;     // 0.0 to 1.0
      latencyMs: number;       // Additional latency
      targetServices: string[]; // Which services to affect
    },
  ) {}

  wrap<T>(serviceName: string, fn: () => Promise<T>): Promise<T> {
    if (!this.config.enabled) return fn();
    if (!this.config.targetServices.includes(serviceName)) return fn();

    // Random failure
    if (Math.random() < this.config.failureRate) {
      throw new Error(`[CHAOS] Simulated failure for ${serviceName}`);
    }

    // Random latency
    if (this.config.latencyMs > 0) {
      return new Promise(resolve => setTimeout(resolve, this.config.latencyMs)).then(fn);
    }

    return fn();
  }
}

// Usage in staging environment
const chaos = new ChaosMiddleware({
  enabled: process.env.CHAOS_ENABLED === 'true',
  failureRate: 0.05,  // 5% of calls fail
  latencyMs: 500,     // 500ms extra latency
  targetServices: ['payment-service', 'inventory-service'],
});

const result = await chaos.wrap('payment-service', () =>
  paymentClient.charge(amount)
);

// Run chaos experiments regularly in staging
// Graduate to production with very low failure rate (0.1%)
// Netflix Chaos Monkey: randomly terminates production instances
```

## Runbooks

```typescript
// Every alert MUST have a runbook. No exceptions.

interface Runbook {
  title: string;
  severity: string;
  symptoms: string[];
  diagnosticSteps: RunbookStep[];
  mitigationSteps: RunbookStep[];
  escalation: {
    after: string;       // "15 minutes without resolution"
    contact: string;     // "Backend team lead, then CTO"
  };
  relatedAlerts: string[];
  lastUpdated: string;
}

// Example Runbook: Database Connection Pool Exhausted
const dbPoolExhaustedRunbook: Runbook = {
  title: 'Database Connection Pool Exhausted',
  severity: 'SEV-1',
  symptoms: [
    'Alert: db_connection_pool_waiting > 0',
    'Users see 500 errors or timeouts',
    'Logs show "connection pool timeout" errors',
  ],
  diagnosticSteps: [
    { action: 'Check current connection count', command: 'SELECT count(*) FROM pg_stat_activity;' },
    { action: 'Check for long-running queries', command: "SELECT pid, now() - pg_stat_activity.query_start AS duration, query FROM pg_stat_activity WHERE state != 'idle' ORDER BY duration DESC LIMIT 10;" },
    { action: 'Check for idle transactions', command: "SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction' AND query_start < NOW() - INTERVAL '5 minutes';" },
    { action: 'Check app pool metrics', command: 'curl localhost:3000/metrics | grep db_pool' },
  ],
  mitigationSteps: [
    { action: 'Kill idle-in-transaction connections', command: "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle in transaction' AND query_start < NOW() - INTERVAL '10 minutes';" },
    { action: 'Kill long-running queries (>5min)', command: "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'active' AND query_start < NOW() - INTERVAL '5 minutes' AND query NOT LIKE '%pg_stat%';" },
    { action: 'If still exhausted: restart app pods (rolling)', command: 'kubectl rollout restart deployment/myapp' },
    { action: 'If DB overloaded: enable read-only mode', command: 'curl -X POST localhost:3000/admin/read-only-mode' },
  ],
  escalation: {
    after: '15 minutes without resolution',
    contact: 'Database team lead → Backend team lead → CTO',
  },
  relatedAlerts: ['high-latency', 'error-rate-spike'],
  lastUpdated: '2024-03-01',
};
```
