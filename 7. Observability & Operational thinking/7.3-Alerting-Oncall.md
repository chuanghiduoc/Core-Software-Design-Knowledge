## Alert Design Philosophy

### Symptoms vs Causes

```
Alerting trên CAUSES (nguyên nhân):
  ❌ "CPU > 80%"        → CPU cao nhưng users vẫn ổn? Thì sao?
  ❌ "Memory > 90%"     → Có thể GC đang hoạt động bình thường
  ❌ "1 error in logs"  → Errors luôn xảy ra, có impact users không?
  ❌ "Disk I/O high"    → Đang backup? Đang import data?
  ❌ "Pod restarted"    → OOMKilled nhưng auto-recovered, users không biết

Alerting trên SYMPTOMS (triệu chứng user thấy):
  ✅ "Error rate > 5% cho 3 phút"       → Users đang gặp lỗi
  ✅ "P99 latency > 2s cho 5 phút"      → Users đang chờ quá lâu
  ✅ "Checkout success rate < 95%"       → Revenue đang bị ảnh hưởng
  ✅ "Zero orders in 10 minutes"         → Có gì đó rất sai
  ✅ "Health check failed 3 lần liên tiếp" → Service thực sự down

Cause-based alerts vẫn hữu ích — nhưng ở mức WARNING, KHÔNG phải PAGE.
Dùng causes để debug SAU KHI symptoms alert đã fire.
```

### Alert Quality Framework

```
Mỗi alert phải trả lời được 4 câu hỏi:

1. ACTIONABLE?
   → Khi alert fire, on-call có thể LÀM GÌ ĐÓ không?
   → Nếu không → xóa alert đi

2. IMPORTANT?
   → Alert này có ảnh hưởng đến users hoặc business không?
   → Nếu không → hạ thành warning hoặc log

3. REAL?
   → Alert này có phải false positive không?
   → Nếu > 20% false positive → tune threshold hoặc redesign

4. URGENT?
   → Có cần xử lý NGAY không, hay có thể chờ đến giờ làm việc?
   → Page (đánh thức lúc 3h sáng) chỉ cho urgent issues
```

### Reducing Alert Fatigue

```typescript

// - Quá nhiều alerts → on-call bắt đầu ignore
// - False positives → mất trust vào alerting system
// - Non-actionable alerts → waste time investigating
// - Duplicate alerts → 1 issue trigger 10 alerts cùng lúc

// Strategies giảm alert fatigue:

interface AlertRule {
  name: string;
  condition: string;
  duration: string;           // Phải violate liên tục bao lâu trước khi fire
  severity: 'critical' | 'warning' | 'info';
  labels: Record<string, string>;
  annotations: {
    summary: string;
    description: string;
    runbook: string;          // BẮT BUỘC có runbook
    dashboard: string;        // Link tới dashboard liên quan
  };
  // Grouping: group alerts liên quan lại
  groupBy: string[];
  // Inhibition: suppress alerts nếu alert khác đang active
  inhibitedBy?: string[];
}

const alertRules: AlertRule[] = [
  {
    name: 'HighErrorRate',
    // Rate tính trên 5 phút, phải sustain 3 phút → total 8 phút signal

      histogram_quantile(0.99,

## Alert Routing & Escalation

### Routing Strategy

```
Severity Levels và Actions:

CRITICAL (P1):
  → Page on-call engineer NGAY LẬP TỨC (PagerDuty / OpsGenie)
  → Có thể đánh thức người lúc 3h sáng
  → Chỉ dùng cho: revenue impact, data loss, security breach, service down
  → Response time target: < 5 phút

WARNING (P2):
  → Tạo ticket, notify qua Slack channel
  → Xử lý trong giờ làm việc
  → Dùng cho: degraded performance, approaching capacity, non-critical failures
  → Response time target: < 4 giờ (business hours)

INFO (P3):
  → Log to dashboard, weekly review
  → Dùng cho: anomalies, trends, FYI
  → Response time: next sprint planning
```

## On-Call Rotation

### Best Practices

```
1. ROTATION SCHEDULE
   → 1 tuần per rotation (không nên dài hơn)
   → Primary + Secondary on-call
   → Handoff vào giữa tuần (thứ 3/4), KHÔNG phải thứ 6
   → Overlap 30 phút khi handoff để transfer context

2. COMPENSATION
   → On-call phải được compensate (tiền hoặc time-off)
   → Bị page ngoài giờ → comp time ngày hôm sau
   → On-call không nên là "punishment" → rotate công bằng

3. TEAM SIZE
   → Minimum 4-5 người cho 1 rotation
   → < 4 người → on-call quá thường xuyên → burnout
   → Mỗi người on-call tối đa 1 tuần/tháng

4. PREPARATION
   → Mỗi on-call mới phải shadow 1 rotation trước khi primary
   → Runbooks phải up-to-date
   → Access và permissions phải ready TRƯỚC KHI rotation bắt đầu
   → Test alert routing trước khi handoff

5. POST-ON-CALL
   → Review all incidents trong rotation
   → Update runbooks nếu cần
   → File tickets cho recurring issues
   → Share learnings với team
```

## Incident Management

### Incident Lifecycle

```
DETECT → TRIAGE → MITIGATE → RESOLVE → POSTMORTEM

1. DETECT (Phát hiện)
   ├── Automated: Alert fires
   ├── Customer report: Support ticket
   ├── Internal: Engineer notices anomaly
   └── Third-party: Status page / Twitter

2. TRIAGE (Phân loại)
   ├── Severity? (P1/P2/P3/P4)
   ├── Impact? (Bao nhiêu users bị ảnh hưởng?)
   ├── Scope? (1 service hay toàn hệ thống?)
   └── Assign Incident Commander

3. MITIGATE (Giảm thiểu — NGAY LẬP TỨC)
   ├── Rollback recent deployment?
   ├── Scale up resources?
   ├── Enable feature flag fallback?
   ├── Route traffic away from broken component?
   └── MỤC TIÊU: Stop the bleeding, không cần fix root cause

4. RESOLVE (Giải quyết — SAU KHI mitigate)
   ├── Root cause analysis
   ├── Permanent fix
   ├── Verify fix in production
   └── Close incident

5. POSTMORTEM (Học từ sự cố — TRONG 48 GIỜ)
   ├── Timeline reconstruction
   ├── Root cause analysis
   ├── Action items
   └── Share with team/org
```

### Incident Commander Role

```
Incident Commander (IC) là người ĐIỀU PHỐI incident, KHÔNG PHẢI người fix.

Trách nhiệm IC:
  1. Declare incident và severity
  2. Tạo war room (Slack channel / call)
  3. Assign roles: debug, communicate, document
  4. Make decisions: rollback? scale? notify customers?
  5. Provide regular updates to stakeholders
  6. Declare incident resolved
  7. Schedule postmortem

IC KHÔNG nên:
  ❌ Tự mình debug (trừ khi team quá nhỏ)
  ❌ Micromanage engineers đang fix
  ❌ Blame anyone
  ❌ Communicate directly với customers (delegate cho Customer Success)

IC rotation: bất kỳ senior engineer nào cũng nên có thể làm IC.
Không nhất thiết phải là manager.
```

## Blameless Postmortem

### Tại sao Blameless?

```
Có blame:
  "John deployed bad code" → John sợ deploy → Team chậm lại
  → Team giấu lỗi → Mất cơ hội học → Lỗi lặp lại

Blameless:
  "Deployment pipeline thiếu canary check" → Cải thiện pipeline
  → Team an toàn để chia sẻ lỗi → Học từ sai lầm → Hệ thống tốt hơn

Blameless KHÔNG có nghĩa là ACCOUNTLESS.
Vẫn có accountability, nhưng focus vào SYSTEM, không phải NGƯỜI.
```

### Postmortem Template

```markdown
# Postmortem: [Tên sự cố]

## Metadata
- **Date**: YYYY-MM-DD
- **Duration**: X giờ Y phút (từ detect đến resolve)
- **Severity**: P1/P2/P3

- **Authors**: [Tên người viết postmortem]
- **Status**: Draft / Review / Approved

## Summary
[1-2 câu tóm tắt sự cố và impact]

## Impact
- **Users affected**: X users (~Y% total)
- **Revenue impact**: $X estimated
- **SLO impact**: Error budget consumed Z%
- **Duration of user impact**: X phút/giờ

## Timeline (UTC)
| Time | Event |
|------|-------|
| 14:00 | Deploy v2.5.1 rolled out to production |
| 14:05 | Error rate starts increasing (0.1% → 2%) |
| 14:12 | Alert "HighErrorRate" fires |
| 14:14 | On-call acknowledges alert |
| 14:20 | IC declared, war room created |
| 14:25 | Root cause identified: new code path causes N+1 DB query |
| 14:30 | Decision: rollback deployment |
| 14:32 | Rollback initiated |
| 14:35 | Rollback complete, error rate returning to normal |
| 14:45 | Error rate back to baseline, incident resolved |

## Root Cause
[Mô tả chi tiết root cause — KHÔNG blame individual]

Deploy v2.5.1 introduced a new product recommendation feature
that triggered an N+1 query pattern. Under normal traffic, this
caused each product page request to make 50+ additional DB queries
instead of 1 batched query. The DB connection pool became saturated,
causing cascading timeouts across all API endpoints.

## Contributing Factors
- Load test trước deploy chỉ test happy path, không test new feature path
- Connection pool size (20) quá nhỏ cho N+1 pattern
- Code review không catch N+1 pattern vì ORM hides query details
- Staging environment traffic quá thấp để trigger issue

## What Went Well
- Alert fired trong 7 phút (target: 5 phút)
- On-call responded trong 2 phút
- Rollback executed cleanly
- Total user impact: 33 phút

## What Went Wrong
- Load test không cover new code path
- Không có canary deployment (all-at-once rollout)
- Connection pool exhaustion không có dedicated alert
- Staging không representative cho production traffic

## Action Items
| # | Action | Priority | Owner | Due Date |
|---|--------|----------|-------|----------|
| 1 | Add N+1 query detection to CI pipeline | P1 | @dev-team | 2 weeks |
| 2 | Implement canary deployment for production | P1 | @platform | 1 month |
| 3 | Add connection pool saturation alert | P2 | @sre-team | 1 week |
| 4 | Increase connection pool size to 50 | P2 | @sre-team | 3 days |
| 5 | Add load test scenarios for new features | P2 | @qa-team | 2 weeks |
| 6 | Improve staging to match production traffic patterns | P3 | @platform | 1 quarter |

## Lessons Learned
[Broad lessons that apply beyond this specific incident]

## Runbook Design

### Tại sao Runbook quan trọng?

```
3 giờ sáng. Alert fires. On-call engineer vừa mới ngủ được 2 giờ.
Đầu óc mơ hồ. Không nhớ service này hoạt động thế nào.

Runbook = hướng dẫn step-by-step để ai cũng có thể handle incident.
Không cần là expert. Không cần nhớ. Chỉ cần follow steps.
```

### Runbook Template

```markdown
# Runbook: High Error Rate — Order Service

## Alert
- **Alert name**: HighErrorRate_OrderService
- **Condition**: Error rate > 5% cho 3 phút
- **Severity**: P1 (Critical)

## Quick Assessment (< 2 phút)
1. Mở dashboard: https://grafana.internal/d/order-service
2. Check: Error rate trend (tăng dần hay spike đột ngột?)
3. Check: Có recent deployment không? → `kubectl rollout history deployment/order-service`
4. Check: Downstream dependencies status
   - Payment service: https://grafana.internal/d/payment-service
   - Database: https://grafana.internal/d/postgres
   - Redis: https://grafana.internal/d/redis

## Common Causes & Fixes

### Cause 1: Bad deployment
**Symptoms**: Error rate spike ngay sau deployment
**Fix**:
```bash
# Rollback to previous version
kubectl rollout undo deployment/order-service -n production
# Verify rollback
kubectl rollout status deployment/order-service -n production
```

### Cause 2: Database connection exhaustion
**Symptoms**: Errors contain "connection pool exhausted" hoặc "timeout"
**Fix**:
```bash
# Check connection count
kubectl exec -it postgres-0 -- psql -c "SELECT count(*) FROM pg_stat_activity;"
# Kill idle connections if needed
kubectl exec -it postgres-0 -- psql -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND query_start < now() - interval '10 minutes';"
```

### Cause 3: Downstream service failure
**Symptoms**: Errors contain timeout to specific service
**Fix**:
- Check downstream service status
- If downstream is recovering: wait, circuit breaker should handle
- If downstream is down: enable fallback feature flag
```bash
curl -X POST https://feature-flags.internal/api/flags/payment-fallback/enable
```

## Escalation
- Nếu không resolve được trong 15 phút → escalate to secondary on-call
- Nếu revenue impact > $10k → notify Engineering Manager
- Nếu data loss suspected → notify VP Engineering + Security
```

### Runbook Maintenance

```
Runbook PHẢI được maintain, nếu không sẽ thành tài liệu chết.

Quy tắc:
  1. Mỗi alert PHẢI có runbook link
  2. Mỗi postmortem review runbook accuracy
  3. On-call handoff: flag outdated runbooks
  4. Quarterly review: test runbook steps thực tế
  5. Runbook owner = team owning the service

Đánh giá chất lượng:
  □ Có step-by-step cho mỗi common cause không?
  □ Có command/link cụ thể không? (copy-paste ready)
  □ Có escalation path rõ ràng không?
  □ Last updated < 3 tháng?
  □ Đã verify bằng cách có người khác follow steps?
```

## War Rooms & Incident Communication

### War Room Setup

```
War room = space (physical hoặc virtual) để coordinate incident response.

Virtual war room (phổ biến nhất):
  1. Tạo Slack channel: #incident-YYYY-MM-DD-short-description
  2. Invite: IC, on-call, relevant engineers, customer success
  3. Pin: dashboard link, runbook link, timeline
  4. Bot: auto-post status updates

Rules trong war room:
  ✅ Chỉ nói về incident hiện tại
  ✅ Dùng threads cho discussions chi tiết
  ✅ IC post regular updates (mỗi 15 phút cho P1)
  ✅ Mọi action đều được log (ai làm gì, khi nào)
  ❌ Không blame
  ❌ Không discuss root cause FIX lúc đang incident (fix tạm trước)
  ❌ Không có side conversations
```

### Communication Templates

```typescript
// ===== Incident Communication Templates =====

interface IncidentUpdate {
  timestamp: Date;
  severity: string;
  status: 'investigating' | 'identified' | 'mitigating' | 'resolved';
  summary: string;
  impact: string;
  nextUpdate: string;
}

// Internal update (Slack / war room)
function formatInternalUpdate(update: IncidentUpdate): string {
  return [
    `**[${update.severity}] Incident Update — ${update.status.toUpperCase()}**`,
    `Time: ${update.timestamp.toISOString()}`,
    ``,
    `**Summary**: ${update.summary}`,
    `**Impact**: ${update.impact}`,
    `**Next update**: ${update.nextUpdate}`,
  ].join('\n');
}

// External update (Status page / Customer email)
function formatExternalUpdate(update: IncidentUpdate): string {
  const statusEmoji: Record<string, string> = {
    investigating: 'Investigating',
    identified: 'Identified',
    mitigating: 'Fix in Progress',
    resolved: 'Resolved',
  };

  return [
    `[${statusEmoji[update.status]}]`,
    ``,
    `${update.summary}`,
    ``,
    `We are aware of ${update.impact.toLowerCase()} and are actively working on a resolution.`,
    update.status === 'resolved'
      ? 'The issue has been resolved. We apologize for any inconvenience.'
      : `We will provide another update ${update.nextUpdate.toLowerCase()}.`,
  ].join('\n');
}

```typescript
import { Router, Request, Response } from 'express';

// ===== Health Check Types =====

interface HealthCheckResult {
  status: 'healthy' | 'degraded' | 'unhealthy';
  timestamp: string;
  version: string;
  uptime: number;         // seconds
  checks: DependencyCheck[];
}

interface DependencyCheck {
  name: string;
  status: 'healthy' | 'unhealthy';
  responseTime?: number;  // ms
  message?: string;
  essential: boolean;     // Nếu essential = true và unhealthy → overall unhealthy
}

type HealthChecker = () => Promise<DependencyCheck>;

// ===== Health Check Registry =====

class HealthCheckService {
  private checkers: HealthChecker[] = [];
  private startTime = Date.now();

  register(checker: HealthChecker): void {
    this.checkers.push(checker);
  }

  async check(): Promise<HealthCheckResult> {
    const checks = await Promise.all(
      this.checkers.map(async (checker) => {
        try {
          return await Promise.race([
            checker(),
            this.timeout(5000), // 5 second timeout per check
          ]);
        } catch (error) {
          return {
            name: 'unknown',
            status: 'unhealthy' as const,
            message: (error as Error).message,
            essential: false,
          };
        }
      })
    );

    const hasEssentialFailure = checks.some(
      c => c.essential && c.status === 'unhealthy'
    );
    const hasAnyFailure = checks.some(c => c.status === 'unhealthy');

    return {
      status: hasEssentialFailure ? 'unhealthy'
        : hasAnyFailure ? 'degraded'
        : 'healthy',
      timestamp: new Date().toISOString(),
      version: process.env.APP_VERSION ?? 'unknown',
      uptime: Math.floor((Date.now() - this.startTime) / 1000),
      checks,
    };
  }

  private timeout(ms: number): Promise<DependencyCheck> {
    return new Promise((_, reject) => {
      setTimeout(() => reject(new Error(`Health check timeout after ${ms}ms`)), ms);
    });
  }
}

// ===== Dependency Checkers =====

function createDatabaseChecker(pool: any): HealthChecker {
  return async (): Promise<DependencyCheck> => {
    const start = performance.now();
    try {
      await pool.query('SELECT 1');
      return {
        name: 'database',
        status: 'healthy',
        responseTime: Math.round(performance.now() - start),
        essential: true,
      };
    } catch (error) {
      return {
        name: 'database',
        status: 'unhealthy',
        responseTime: Math.round(performance.now() - start),
        message: (error as Error).message,
        essential: true,
      };
    }
  };
}

function createRedisChecker(redis: any): HealthChecker {
  return async (): Promise<DependencyCheck> => {
    const start = performance.now();
    try {
      await redis.ping();
      return {
        name: 'redis',
        status: 'healthy',
        responseTime: Math.round(performance.now() - start),
        essential: false, // Cache down = degraded, not unhealthy
      };
    } catch (error) {
      return {
        name: 'redis',
        status: 'unhealthy',
        responseTime: Math.round(performance.now() - start),
        message: (error as Error).message,
        essential: false,
      };
    }
  };
}

function createExternalApiChecker(
  name: string,
  url: string,
  essential: boolean,
): HealthChecker {
  return async (): Promise<DependencyCheck> => {
    const start = performance.now();
    try {
      const response = await fetch(url, {
        method: 'GET',
        signal: AbortSignal.timeout(3000),
      });
      return {
        name,
        status: response.ok ? 'healthy' : 'unhealthy',
        responseTime: Math.round(performance.now() - start),
        message: response.ok ? undefined : `HTTP ${response.status}`,
        essential,
      };
    } catch (error) {
      return {
        name,
        status: 'unhealthy',
        responseTime: Math.round(performance.now() - start),
        message: (error as Error).message,
        essential,
      };
    }
  };
}

// ===== Express Routes =====

function createHealthRoutes(healthService: HealthCheckService): Router {
  const router = Router();

  // Liveness probe: "Is the process alive?"
  // Dùng cho: Kubernetes liveness probe
  // KHÔNG check dependencies — chỉ check process alive
  router.get('/health/live', (_req: Request, res: Response) => {
    res.status(200).json({ status: 'alive' });
  });

  // Readiness probe: "Can the process handle traffic?"
  // Dùng cho: Kubernetes readiness probe, load balancer
  // Check essential dependencies
  router.get('/health/ready', async (_req: Request, res: Response) => {
    const result = await healthService.check();
    const statusCode = result.status === 'unhealthy' ? 503 : 200;
    res.status(statusCode).json(result);
  });

  // Startup probe: "Has the process finished initializing?"
  // Dùng cho: Kubernetes startup probe
  // Separate từ readiness để handle slow startups
  router.get('/health/startup', async (_req: Request, res: Response) => {
    const result = await healthService.check();
    const statusCode = result.status === 'unhealthy' ? 503 : 200;
    res.status(statusCode).json(result);
  });

  return router;
}

### Checklist: Alerting & On-Call

```
Alert Design:
  □ Alert trên symptoms, không phải causes
  □ Mỗi alert là actionable, important, real, và urgent
  □ False positive rate < 20%
  □ Mỗi alert có runbook link
  □ Alert grouping để tránh notification storm
  □ Inhibition rules cho cascading failures

On-Call:
  □ Rotation ≥ 4 người
  □ Primary + Secondary on-call
  □ Handoff process documented
  □ On-call compensation policy
  □ Shadow rotation cho new members
  □ Monthly on-call health metrics review

Incident Management:
  □ Severity levels defined (P1-P4)
  □ Incident Commander rotation
  □ Communication templates ready
  □ War room process documented
  □ Status page configured
  □ Postmortem within 48 giờ cho P1/P2
  □ Action items tracked to completion

Health Checks:
  □ Liveness probe (process alive)
  □ Readiness probe (can handle traffic)
  □ Startup probe (initialization complete)
  □ Essential vs non-essential dependency marking
  □ Timeout per health check (< 5 giây)
```
