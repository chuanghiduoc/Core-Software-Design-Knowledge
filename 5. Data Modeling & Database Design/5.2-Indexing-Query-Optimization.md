## 1. How Indexes Work

Index là **data structure riêng biệt** trỏ vào rows trong table, giúp DB tìm data nhanh hơn sequential scan.

### B-tree (Default)

Balanced tree, sorted keys. **Tốt cho:** `=`, `<`, `>`, `BETWEEN`, `IN`, `IS NULL`, `LIKE 'prefix%'`. **Không cho:** `LIKE '%suffix'`, full-text search.

```sql
CREATE INDEX idx_users_email ON users(email);
SELECT * FROM users WHERE email > 'john@';  -- ✅ Range scan
SELECT * FROM users WHERE email LIKE 'j%';  -- ✅ Prefix scan
SELECT * FROM users WHERE email LIKE '%@gmail.com'; -- ❌ Seq scan
```

### Hash Index

Hash table, O(1) equality. **Chỉ tốt cho:** `=`. Hầu như không cần — B-tree equality cũng rất nhanh.

```sql
CREATE INDEX idx_sessions_token ON sessions USING hash(token);
SELECT * FROM sessions WHERE token = 'abc123';  -- ✅ Hash lookup
SELECT * FROM sessions WHERE token > 'abc';      -- ❌ Seq scan
```

### GIN (Generalized Inverted Index)

Inverted index — map values → rows. **Tốt cho:** JSONB, arrays, full-text search.

```sql
CREATE INDEX idx_products_attrs ON products USING GIN(attributes);
SELECT * FROM products WHERE attributes @> '{"color": "red"}';

CREATE INDEX idx_articles_search ON articles
  USING GIN(to_tsvector('english', title || ' ' || body));
SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body) @@ to_tsquery('english', 'database & design');

CREATE INDEX idx_issues_labels ON issues USING GIN(labels);
SELECT * FROM issues WHERE labels @> ARRAY['bug', 'critical'];
```

### GiST (Generalized Search Tree)

Balanced tree tổng quát. **Tốt cho:** geometric data, ranges, exclusion constraints.

```sql
-- Prevent double booking với exclusion constraint
CREATE TABLE room_bookings (
  id SERIAL PRIMARY KEY, room_id INTEGER NOT NULL,
  booked_during TSTZRANGE NOT NULL,
  EXCLUDE USING GIST (room_id WITH =, booked_during WITH &&)
);

-- Geospatial queries (PostGIS)
CREATE INDEX idx_stores_location ON stores USING GIST(location);
SELECT * FROM stores WHERE ST_DWithin(location, ST_MakePoint(106.6, 10.8)::geography, 5000);
```

### BRIN (Block Range INdex)

Index trên block ranges, **cực compact**. Tốt cho naturally-ordered data (time-series, auto-increment).

```sql
-- Table 1 tỷ rows: B-tree = 20GB, BRIN = 100KB
CREATE INDEX idx_events_created ON events USING BRIN(created_at);
-- Chỉ hiệu quả khi data physically correlated (insert theo thứ tự time)
```

### So sánh nhanh

| Type | Size | Best for |
|------|------|----------|
| B-tree | Medium | General purpose, ranges, sorting |
| Hash | Small | Pure equality on very large keys |
| GIN | Large | JSONB, arrays, full-text |
| GiST | Medium | Ranges, geo, exclusion |
| BRIN | Tiny | Time-series, naturally ordered |

## 2. Index Selection Strategy

> Index là trade-off: reads nhanh hơn ↔ writes chậm hơn + storage tăng

### ❌ Over-indexing

```sql
-- ❌ 7 indexes trên 1 table → mỗi INSERT phải update 7 indexes
CREATE INDEX idx1 ON orders(customer_id);
CREATE INDEX idx2 ON orders(status);
CREATE INDEX idx3 ON orders(created_at);
CREATE INDEX idx4 ON orders(total_amount);
CREATE INDEX idx5 ON orders(customer_id, status);
CREATE INDEX idx6 ON orders(customer_id, created_at);
CREATE INDEX idx7 ON orders(status, created_at);
```

### ✅ Index theo actual query patterns

```sql
-- ✅ 2 indexes cover đúng queries thực tế
-- Query 1: WHERE customer_id = ? ORDER BY created_at DESC
CREATE INDEX idx_orders_customer_date ON orders(customer_id, created_at DESC);

-- Query 2: WHERE status = 'pending' AND created_at > NOW() - '7 days'
CREATE INDEX idx_orders_pending_recent ON orders(created_at) WHERE status = 'pending';
```

### Composite Indexes — Thứ tự columns

```sql
-- Rule: Equality columns TRƯỚC, Range/Sort columns SAU
-- Query: WHERE tenant_id = ? AND status = ? AND created_at > ? ORDER BY created_at
CREATE INDEX idx_issues_lookup ON issues(tenant_id, status, created_at);
--                                       ↑equality  ↑equality ↑range+sort

-- ❌ Sai thứ tự → phải scan quá nhiều
CREATE INDEX idx_bad ON issues(created_at, tenant_id, status);
```

### Partial Indexes

```sql
-- Active orders = 5% table nhưng 95% queries → index chỉ active
CREATE INDEX idx_orders_active ON orders(customer_id, created_at)
  WHERE status NOT IN ('completed', 'cancelled');
-- Index nhỏ hơn 20x → fits in memory → nhanh hơn nhiều
```

### Covering Indexes (Index-Only Scans)

```sql
-- INCLUDE columns → avoid table lookup (heap fetch)
CREATE INDEX idx_orders_summary ON orders(customer_id, status)
  INCLUDE (id, total_amount, created_at);
-- "Index Only Scan" — DB chỉ đọc index, không cần access table
```

### Expression Indexes

```sql
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
CREATE INDEX idx_products_category ON products((attributes->>'category'));
```

### Khi nào KHÔNG cần index

- Table < 1000 rows (seq scan nhanh hơn)
- Column cardinality cực thấp (boolean) — trừ khi dùng partial index
- Columns chỉ dùng trong INSERT, không trong WHERE/JOIN/ORDER BY

## 3. EXPLAIN ANALYZE — Đọc Query Plans

```sql
-- EXPLAIN: estimate only | EXPLAIN ANALYZE: chạy thật, đo actual time
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
  SELECT * FROM orders WHERE customer_id = 'abc';
```

### Đọc plan — từ dưới lên trên

```
Limit (actual time=0.52..0.53 rows=20)
  → Sort (Sort Key: created_at DESC, Method: top-N heapsort)
    → Nested Loop (actual time=0.03..0.45 rows=890)
      → Index Scan using idx_orders_pending on orders  ← Đọc từ đây
            Index Cond: (created_at > ...)
            Buffers: shared hit=45                      ← Từ cache ✅
      → Index Scan using users_pkey on users
            Buffers: shared hit=890
Execution Time: 0.567 ms
```

### Red flags trong query plan

| Signal | Vấn đề | Fix |
|--------|--------|-----|
| `Seq Scan` trên large table | Missing index | Tạo index phù hợp |
| `estimated rows` sai 10x+ | Stale statistics | `ANALYZE table` |
| `shared read >> shared hit` | Data không fit buffer pool | Tăng shared_buffers |
| `Sort Method: external merge` | Sort spills to disk | Tăng work_mem |

### Các scan types

| Scan Type | Khi nào tốt | Khi nào xấu |
|-----------|-------------|-------------|
| Seq Scan | Table nhỏ, cần >10% rows | Large table, cần vài rows |
| Index Scan | Selective (<5% rows) | Fetch quá nhiều rows |
| Index Only Scan | Covering index | N/A — luôn tốt |
| Bitmap Index Scan | Medium selectivity (1-20%) | N/A — DB tự chọn |

## 4. Common Query Anti-Patterns

### 4.1 N+1 Query Problem

```typescript
// ❌ 100 orders → 100 separate queries cho customer
const orders = await db.query('SELECT * FROM orders LIMIT 100');
const results = await Promise.all(
  orders.map(async (o) => {
    const customer = await db.query('SELECT * FROM users WHERE id = $1', [o.customerId]);
    return { ...o, customer: customer[0] };
  })
);
// Total: 101 queries!

// ✅ Fix 1: JOIN — 1 query
const results = await db.query(`
  SELECT o.*, u.name AS customer_name FROM orders o
  JOIN users u ON o.customer_id = u.id LIMIT 100
`);

// ✅ Fix 2: Batch — 2 queries
const orders = await db.query('SELECT * FROM orders LIMIT 100');
const customerIds = [...new Set(orders.map((o) => o.customerId))];
const customers = await db.query('SELECT * FROM users WHERE id = ANY($1)', [customerIds]);
const customerMap = new Map(customers.map((c) => [c.id, c]));
```

### 4.2 SELECT * Anti-Pattern

```typescript
// ❌ Fetch 50 columns khi chỉ cần 3 → wasted I/O, memory
const users = await db.query('SELECT * FROM users');

// ✅ Chỉ select columns cần thiết, define DTO per use case
interface UserListItem { id: string; email: string; displayName: string; }
const users = await db.query<UserListItem>('SELECT id, email, display_name FROM users');
```

### 4.3 Implicit Type Casting

```sql
-- ❌ Column là INTEGER, query với TEXT → index bypass
SELECT * FROM orders WHERE id = '12345';  -- implicit cast mỗi row!

-- ✅ Match types chính xác
SELECT * FROM orders WHERE id = 12345;
```

### 4.4 Functions on Indexed Columns

```sql
-- ❌ Function trên indexed column → index bypass
SELECT * FROM users WHERE LOWER(email) = 'john@example.com';
SELECT * FROM orders WHERE EXTRACT(YEAR FROM created_at) = 2024;

-- ✅ Expression index hoặc rewrite query
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
SELECT * FROM orders WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

## 5. Query Optimization Techniques

### CTEs (Common Table Expressions)

```sql
-- ✅ CTE cho readability + reuse
WITH monthly_revenue AS (
  SELECT date_trunc('month', created_at) AS month,
    SUM(total_amount) AS revenue, COUNT(*) AS order_count
  FROM orders WHERE status = 'completed' AND created_at >= NOW() - INTERVAL '12 months'
  GROUP BY 1
)
SELECT month, revenue,
  ROUND((revenue - LAG(revenue) OVER (ORDER BY month))
    / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100, 2) AS growth_pct
FROM monthly_revenue ORDER BY month DESC;
```

### Window Functions

```sql
-- ✅ Top 3 products per category — không cần self-join
SELECT * FROM (
  SELECT p.category, p.name,
    SUM(oi.quantity * oi.unit_price) AS revenue,
    ROW_NUMBER() OVER (PARTITION BY p.category ORDER BY SUM(oi.quantity * oi.unit_price) DESC) AS rank
  FROM products p JOIN order_items oi ON p.id = oi.product_id
  GROUP BY p.category, p.name
) ranked WHERE rank <= 3;
```

### LATERAL Joins

```sql
-- ✅ Top-N per group: 3 orders gần nhất cho mỗi customer
SELECT c.id, c.name, r.*
FROM customers c
CROSS JOIN LATERAL (
  SELECT o.id AS order_id, o.total_amount, o.created_at
  FROM orders o WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC LIMIT 3
) r;
```

### Batch Operations

```typescript
// ❌ Insert từng row = 1000 round trips
// ✅ Batch insert = 1 round trip
await db.query(
  `INSERT INTO events (user_id, type, data) VALUES
   ${events.map((_, i) => `($${i*3+1}, $${i*3+2}, $${i*3+3})`).join(', ')}`,
  events.flatMap(e => [e.userId, e.type, e.data])
);
```

## 6. Connection Pooling

```
Mỗi PostgreSQL connection = 1 OS process = ~5-10MB RAM
100 connections = 500MB-1GB RAM chỉ cho connections
→ Connection pool là BẮT BUỘC cho production
```

```typescript
// ✅ Application-level pool
import { Pool } from 'pg';
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,                        // Max connections
  min: 5,                         // Min idle
  idleTimeoutMillis: 30_000,      // Close idle sau 30s
  connectionTimeoutMillis: 5_000,  // Error nếu không get trong 5s
  statement_timeout: 30_000,      // Kill query > 30s
});

// ❌ KHÔNG tạo pool mới cho mỗi request
// ✅ Shared pool, tạo 1 lần khi app start
```

### PgBouncer

```
App (100 conns) → PgBouncer (20 conns) → PostgreSQL
Pool mode: transaction (khuyến khích) — return connection sau mỗi transaction
```

### Pool sizing

```
Formula: connections = (core_count * 2) + 1
Node.js: pool.max = availablePgConnections / numberOfNodeProcesses
Ví dụ: 4 workers, PG max=100, PgBouncer pool=80 → mỗi process pool.max = 20
```

## 7. Full Example: Optimizing a Slow Dashboard Query

**Scenario:** Monthly Sales Report — 12 seconds trên 10M orders, 50M order_items.

### Step 1: Original query

```sql
SELECT DATE_TRUNC('month', o.created_at) AS month, c.name AS category,
  COUNT(DISTINCT o.id) AS total_orders,
  SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
JOIN categories c ON p.category_id = c.id
WHERE o.status = 'completed' AND o.created_at >= NOW() - INTERVAL '12 months'
GROUP BY 1, 2 ORDER BY 1 DESC, 4 DESC;
-- 12,045ms — Seq Scan trên orders (10M) và order_items (50M)
```

### Step 2: Add indexes

```sql
CREATE INDEX idx_orders_completed_recent ON orders(created_at) WHERE status = 'completed';
CREATE INDEX idx_order_items_covering ON order_items(order_id) INCLUDE (product_id, quantity, unit_price);
ANALYZE orders; ANALYZE order_items;
-- 850ms — 14x improvement
```

### Step 3: Materialized view cho dashboard

```sql
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT date_trunc('month', o.created_at) AS month,
  c.id AS category_id, c.name AS category_name,
  COUNT(DISTINCT o.id) AS total_orders,
  SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM orders o JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id JOIN categories c ON p.category_id = c.id
WHERE o.status = 'completed' GROUP BY 1, 2, 3;

CREATE UNIQUE INDEX idx_mv_sales ON mv_monthly_sales(month, category_id);
-- Dashboard query: <10ms
```

```typescript
// ✅ Dashboard service: materialized view + Redis cache
class DashboardService {
  async getMonthlySales(months = 12): Promise<MonthlySalesReport[]> {
    const cacheKey = `dashboard:monthly-sales:${months}`;
    const cached = await this.redis.get(cacheKey);
    if (cached) return JSON.parse(cached);  // <1ms

    const { rows } = await this.db.query(
      `SELECT * FROM mv_monthly_sales WHERE month >= NOW() - INTERVAL '1 month' * $1
       ORDER BY month DESC, total_revenue DESC`, [months]
    );  // ~8ms

    await this.redis.set(cacheKey, JSON.stringify(rows), 'EX', 60);
    return rows;
  }
}
```

### Results

```
Before:              12,045ms (Seq Scan, no indexes)
After indexes:          850ms (Index Scan, covering index)
After mat. view:          8ms (Pre-computed)
After Redis cache:       <1ms (In-memory)

Trade-offs: +200MB storage, data trễ tối đa 15 phút, INSERT chậm ~5%
```
