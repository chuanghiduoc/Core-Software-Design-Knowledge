## CAP Theorem

> "In a distributed data store, you can only guarantee two out of three: Consistency, Availability, Partition Tolerance."
> — Eric Brewer, 2000 (chứng minh bởi Gilbert & Lynch, 2002)

### Ba thuộc tính

```
C — Consistency:     Mọi read đều nhận được write gần nhất hoặc error
A — Availability:    Mọi request đều nhận được response (không error),
                     nhưng không đảm bảo là data mới nhất
P — Partition Tolerance: Hệ thống tiếp tục hoạt động dù network
                         bị chia cắt giữa các nodes
```

### Hiểu đúng CAP — Phần lớn mọi người hiểu SAI

**Sai lầm #1:** "Chọn 2 trong 3" — Thực tế, **Partition Tolerance không phải là lựa chọn**. Network partition CHẮC CHẮN sẽ xảy ra trong distributed system. Vì vậy, lựa chọn thực sự là: **khi partition xảy ra, bạn chọn C hay A?**

**Sai lầm #2:** "CP nghĩa là không available" — KHÔNG. CP system vẫn available khi không có partition. Chỉ khi partition xảy ra, nó ưu tiên consistency hơn availability.

**Sai lầm #3:** "CAP áp dụng cho toàn bộ hệ thống" — KHÔNG. Các phần khác nhau của hệ thống có thể có trade-off khác nhau. Payment service có thể là CP, product catalog có thể là AP.

### CP Systems — Consistency + Partition Tolerance

Khi network partition xảy ra, hệ thống **từ chối phục vụ** (trả về error) thay vì trả về stale data.

```typescript
// === CP System: Distributed Lock Service ===

interface LockService {
  acquire(resource: string, ttl: number): Promise<LockResult>;
  release(resource: string, token: string): Promise<void>;
}

type LockResult =
  | { acquired: true; token: string; expiresAt: number }
  | { acquired: false; reason: 'already_locked' | 'no_quorum' };

class CPLockService implements LockService {
  constructor(
    private readonly nodes: LockNode[],
    private readonly quorumSize: number // majority = Math.floor(n/2) + 1
  ) {}

  async acquire(resource: string, ttl: number): Promise<LockResult> {
    const token = crypto.randomUUID();
    const startTime = Date.now();

    // Gửi request tới TẤT CẢ nodes
    const results = await Promise.allSettled(
      this.nodes.map(node =>
        node.tryLock(resource, token, ttl)
      )
    );

    const successCount = results.filter(
      r => r.status === 'fulfilled' && r.value === true
    ).length;

    const elapsed = Date.now() - startTime;

    // CP choice: PHẢI đạt quorum mới coi là thành công
    // Nếu network partition khiến không đủ quorum → trả về failure
    if (successCount >= this.quorumSize && elapsed < ttl) {
      return {
        acquired: true,
        token,
        expiresAt: startTime + ttl,
      };
    }

    // Không đạt quorum → rollback locks đã acquire
    await this.releaseFromAll(resource, token);
    return { acquired: false, reason: 'no_quorum' };
  }

  async release(resource: string, token: string): Promise<void> {
    await this.releaseFromAll(resource, token);
  }

  private async releaseFromAll(resource: string, token: string): Promise<void> {
    await Promise.allSettled(
      this.nodes.map(node => node.releaseLock(resource, token))
    );
  }
}
```

**Ví dụ thực tế CP:**
- **ZooKeeper** — Leader-based, mọi write phải qua leader, quorum read
- **etcd** — Raft consensus, dùng trong Kubernetes
- **HBase** — Strong consistency, single region server per region
- **MongoDB (default)** — Write concern majority, read concern majority
- **Google Spanner** — Linearizable reads, TrueTime API

### AP Systems — Availability + Partition Tolerance

Khi network partition xảy ra, hệ thống **vẫn phục vụ** nhưng có thể trả về stale data.

```typescript
// === AP System: Shopping Cart (Amazon-style) ===

interface CartItem {
  productId: string;
  quantity: number;
  addedAt: number; // vector clock timestamp
}

interface ShoppingCart {
  userId: string;
  items: CartItem[];
  vectorClock: VectorClock;
}

class APCartService {
  constructor(
    private readonly localStore: CartStore,
    private readonly replicaPeers: CartPeer[],
  ) {}

  // Luôn accept write — ngay cả khi không liên lạc được replicas
  async addToCart(userId: string, item: CartItem): Promise<ShoppingCart> {
    // Ghi vào local store TRƯỚC (availability first)
    const cart = await this.localStore.addItem(userId, item);

    // Async replicate — không block response
    // Nếu network partition, replicas sẽ nhận sau
    this.replicateAsync(cart).catch(err => {
      console.warn('Replication failed, will retry:', err.message);
      this.enqueueForRetry(cart);
    });

    return cart;
  }

  // Khi partition heal, merge conflicting carts
  async mergeConflicts(
    localCart: ShoppingCart,
    remoteCart: ShoppingCart
  ): Promise<ShoppingCart> {
    // AP systems cần conflict resolution strategy
    // Amazon's choice: UNION — không bao giờ mất item khách đã thêm
    const mergedItems = this.unionMerge(localCart.items, remoteCart.items);
    const mergedClock = VectorClock.merge(
      localCart.vectorClock,
      remoteCart.vectorClock
    );

    return {
      userId: localCart.userId,
      items: mergedItems,
      vectorClock: mergedClock,
    };
  }

  private unionMerge(local: CartItem[], remote: CartItem[]): CartItem[] {
    const merged = new Map<string, CartItem>();

    for (const item of [...local, ...remote]) {
      const existing = merged.get(item.productId);
      if (!existing || item.addedAt > existing.addedAt) {
        merged.set(item.productId, item);
      }
    }

    return Array.from(merged.values());
  }

  private async replicateAsync(cart: ShoppingCart): Promise<void> {
    await Promise.allSettled(
      this.replicaPeers.map(peer => peer.replicate(cart))
    );
  }

  private enqueueForRetry(cart: ShoppingCart): void {
    // Đưa vào retry queue — anti-entropy process sẽ xử lý
  }
}
```

**Ví dụ thực tế AP:**
- **Cassandra** — Tunable consistency, default eventual
- **DynamoDB** — Eventually consistent reads (default)
- **CouchDB** — Multi-master replication
- **DNS** — Cached everywhere, eventual consistency
- **CDN** — Cache invalidation is eventually consistent

### Bảng so sánh thực tế

```
┌─────────────────┬────────────────────┬────────────────────────────────┐
│ Loại hệ thống   │ Khi partition xảy ra│ Use case phù hợp             │
├─────────────────┼────────────────────┼────────────────────────────────┤
│ CP              │ Trả error/timeout   │ Payment, inventory, locks     │
│ AP              │ Trả stale data      │ Shopping cart, feed, cache     │

└─────────────────┴────────────────────┴────────────────────────────────┘
```

## PACELC Theorem

> "If there is a Partition (P), choose between Availability (A) and Consistency (C);
> Else (E), when running normally, choose between Latency (L) and Consistency (C)."
> — Daniel Abadi, 2012

### Tại sao CAP chưa đủ?

CAP chỉ nói về trường hợp **có partition**. Nhưng phần lớn thời gian, hệ thống **không có partition**. PACELC bổ sung: ngay cả khi mọi thứ bình thường, bạn vẫn phải chọn giữa **latency** và **consistency**.

```
                    ┌─── Partition xảy ra ──→ Chọn A hay C?
                    │
  PACELC: ─────────┤
                    │
                    └─── Bình thường (E) ───→ Chọn L hay C?
```

### Phân loại hệ thống theo PACELC

```typescript
// Minh họa trade-off PACELC qua configuration

// PA/EL — Ưu tiên Availability khi partition, Latency khi bình thường
// → DynamoDB, Cassandra (default)
const dynamoConfig = {
  readConsistency: 'eventual',      // EL: đọc từ replica gần nhất → low latency
  partitionBehavior: 'serve_stale', // PA: vẫn serve khi partition
};

// PC/EC — Ưu tiên Consistency luôn luôn
// → VoltDB, traditional RDBMS with sync replication
const voltdbConfig = {
  readConsistency: 'linearizable',     // EC: mọi read qua leader
  partitionBehavior: 'reject_writes',  // PC: reject khi partition
};

// PA/EC — Ưu tiên Availability khi partition, Consistency khi bình thường
// → MongoDB (majority write concern)
const mongoConfig = {
  writeConcern: 'majority',          // EC: đợi majority ack
  readPreference: 'primaryPreferred', // EC: prefer primary
  partitionBehavior: 'elect_new_primary', // PA: vẫn hoạt động
};

// PC/EL — Ưu tiên Consistency khi partition, Latency khi bình thường
// → PNUTS (Yahoo), Cosmos DB (bounded staleness)
const cosmosConfig = {
  consistencyLevel: 'BoundedStaleness', // EL: cho phép stale trong bound
  partitionBehavior: 'reject_if_stale', // PC: reject nếu quá stale
};
```

## FLP Impossibility

> "No deterministic consensus protocol can guarantee agreement in an asynchronous system
> where even a single process can crash."
> — Fischer, Lynch, Paterson, 1985

### Ý nghĩa thực tế

FLP chứng minh rằng trong hệ thống **asynchronous** (không có upper bound cho message delay):
1. Bạn **không thể phân biệt** process chậm và process đã crash
2. Không có thuật toán consensus nào **luôn terminate** trong mọi trường hợp

```typescript
// Minh họa vấn đề FLP: Không phân biệt được slow vs crashed

class HealthChecker {
  private readonly timeout: number;

  constructor(timeoutMs: number) {
    this.timeout = timeoutMs;
  }

  async checkNode(node: NodeClient): Promise<NodeStatus> {
    try {
      const response = await Promise.race([
        node.ping(),
        this.createTimeout(),
      ]);

      if (response === 'TIMEOUT') {
        // FLP core problem: node chậm hay đã crash?
        // Trong async system, KHÔNG CÓ CÁCH phân biệt
        return {
          status: 'unknown', // KHÔNG PHẢI 'dead'!
          reason: 'timeout',
          // Đây là lý do cần failure detector với
          // accrual/phi strategy thay vì binary alive/dead
        };
      }

      return { status: 'alive', latency: response.latency };
    } catch (error) {
      return { status: 'suspected_dead', error: String(error) };
    }
  }

  private createTimeout(): Promise<'TIMEOUT'> {
    return new Promise(resolve =>
      setTimeout(() => resolve('TIMEOUT'), this.timeout)
    );
  }
}

// Phi Accrual Failure Detector — giải pháp thực tế cho FLP
// Thay vì binary alive/dead, dùng suspicion level liên tục
class PhiAccrualFailureDetector {
  private heartbeatHistory: number[] = [];
  private lastHeartbeat: number = Date.now();

  recordHeartbeat(): void {
    const now = Date.now();
    const interval = now - this.lastHeartbeat;
    this.heartbeatHistory.push(interval);

    // Giữ sliding window
    if (this.heartbeatHistory.length > 1000) {
      this.heartbeatHistory = this.heartbeatHistory.slice(-1000);
    }
    this.lastHeartbeat = now;
  }

  // Phi = -log10(P(timeSinceLastHeartbeat))
  // Phi cao → khả năng node đã crash cao
  phi(): number {
    const timeSinceLast = Date.now() - this.lastHeartbeat;
    const mean = this.mean();
    const stdDev = this.standardDeviation();

    if (stdDev === 0) return timeSinceLast > mean ? Infinity : 0;

    // Sử dụng normal distribution
    const y = (timeSinceLast - mean) / stdDev;
    const p = 1 - this.normalCDF(y);

    return -Math.log10(p);
  }

  isSuspected(threshold: number = 8): boolean {
    // threshold = 8 → P(mistake) ≈ 10^-8
    return this.phi() > threshold;
  }

  private mean(): number {
    if (this.heartbeatHistory.length === 0) return 0;
    return this.heartbeatHistory.reduce((a, b) => a + b, 0)
      / this.heartbeatHistory.length;
  }

  private standardDeviation(): number {
    const avg = this.mean();
    const squareDiffs = this.heartbeatHistory.map(v => Math.pow(v - avg, 2));
    return Math.sqrt(
      squareDiffs.reduce((a, b) => a + b, 0) / squareDiffs.length
    );
  }

  private normalCDF(x: number): number {
    const a1 = 0.254829592, a2 = -0.284496736;
    const a3 = 1.421413741, a4 = -1.453152027;
    const a5 = 1.061405429, p = 0.3275911;
    const sign = x < 0 ? -1 : 1;
    x = Math.abs(x) / Math.SQRT2;
    const t = 1.0 / (1.0 + p * x);
    const y = 1 - (((((a5 * t + a4) * t) + a3) * t + a2) * t + a1) * t * Math.exp(-x * x);
    return 0.5 * (1.0 + sign * y);
  }
}
```

### Cách vượt qua FLP trong thực tế

FLP áp dụng cho hệ thống **hoàn toàn asynchronous**. Thực tế, chúng ta "cheat" bằng cách:

1. **Timeouts** — Giả định partial synchrony (có upper bound, nhưng không biết trước)
2. **Randomization** — Thuật toán ngẫu nhiên (Ben-Or) có thể terminate with probability 1
3. **Failure detectors** — Oracle cho biết node nào đã crash (Chandra & Toueg)
4. **Raft/Paxos** — Sacrifice liveness cho safety: luôn đúng, nhưng có thể bị stuck

## Two Generals Problem

> Hai vị tướng cần thống nhất thời gian tấn công, nhưng giao tiếp qua kênh không đáng tin cậy.
> Chứng minh: **không thể đạt agreement** qua unreliable channel.

### Bản chất vấn đề

```
  Tướng A ←──── tin nhắn có thể bị mất ────→ Tướng B

  A gửi: "Tấn công lúc bình minh"
  → B nhận được? Không chắc.

  B gửi ACK: "Đồng ý tấn công lúc bình minh"
  → A nhận được ACK? Không chắc.

  A gửi ACK-ACK: "Tôi biết bạn đồng ý"
  → B nhận được? Không chắc.

  ... vòng lặp vô tận ACK
```

### Ảnh hưởng tới thiết kế hệ thống

Two Generals Problem chính là TCP handshake problem. TCP "giải quyết" bằng cách:
- 3-way handshake (SYN, SYN-ACK, ACK) — pragmatic, không perfect
- Timeout + retransmission
- Chấp nhận edge case (half-open connections)

```typescript
// Two Generals trong thực tế: Payment processing
// Bạn KHÔNG THỂ biết chắc 100% payment đã xử lý hay chưa

interface PaymentGateway {
  charge(amount: number, idempotencyKey: string): Promise<PaymentResult>;
}

class PaymentProcessor {
  constructor(
    private readonly gateway: PaymentGateway,
    private readonly store: PaymentStore,
  ) {}

  async processPayment(orderId: string, amount: number): Promise<PaymentResult> {
    // Idempotency key = giải pháp thực tế cho Two Generals
    const idempotencyKey = `payment_${orderId}`;

    // Check: đã xử lý rồi?
    const existing = await this.store.findByIdempotencyKey(idempotencyKey);
    if (existing) {
      return existing; // Idempotent: trả kết quả cũ
    }

    try {
      const result = await this.gateway.charge(amount, idempotencyKey);
      await this.store.save({ idempotencyKey, result, orderId });
      return result;
    } catch (error) {
      if (this.isNetworkError(error)) {
        // Two Generals Problem: request ĐÃ tới gateway chưa?
        // Không biết! → Phải query lại
        return this.reconcile(idempotencyKey, orderId);
      }
      throw error;
    }
  }

  private async reconcile(
    idempotencyKey: string,
    orderId: string,
  ): Promise<PaymentResult> {
    // Hỏi gateway: "bạn đã xử lý payment này chưa?"
    // Idempotency key cho phép gateway trả lại kết quả
    const result = await this.gateway.charge(0, idempotencyKey);
    return result;
  }

  private isNetworkError(error: unknown): boolean {
    return error instanceof Error &&
      ['ECONNRESET', 'ETIMEDOUT', 'ECONNREFUSED'].some(
        code => error.message.includes(code)
      );
  }
}
```

## Byzantine Generals Problem

> Phiên bản mở rộng của Two Generals: nhiều tướng, và một số có thể là **phản bội**
> (gửi thông tin sai có chủ đích).
> — Leslie Lamport, Robert Shostak, Marshall Pease, 1982

### Crash failure vs Byzantine failure

```
Crash failure:    Node ngừng hoạt động (dễ detect hơn)
Byzantine failure: Node hoạt động SAI — gửi data sai,
                   gửi message khác nhau cho các node khác nhau
```

### Kết quả toán học

Để chịu được `f` Byzantine nodes, cần **tối thiểu `3f + 1` nodes tổng cộng**.
- 1 Byzantine node → cần 4 nodes
- 2 Byzantine nodes → cần 7 nodes
- Chi phí rất cao → chỉ dùng khi thực sự cần

### Ứng dụng thực tế

```typescript
// Byzantine Fault Tolerance trong thực tế
// Hầu hết hệ thống KHÔNG cần BFT — chỉ cần CFT (Crash Fault Tolerance)

// Khi nào cần BFT:
// 1. Blockchain — nodes không trust nhau
// 2. Aviation — sensor có thể gửi sai data
// 3. Financial systems cực kỳ critical

// Khi nào CFT là đủ (phần lớn trường hợp):
// 1. Internal microservices — trust nhau
// 2. Database replication — trust replicas
// 3. Distributed cache — trust cache nodes

interface BFTValidator {
  validateResponse<T>(
    responses: Array<{ nodeId: string; value: T }>,
    totalNodes: number,
  ): { consensus: T | null; confidence: number };
}

// Simple BFT: majority vote
class MajorityVoteBFT implements BFTValidator {
  validateResponse<T>(
    responses: Array<{ nodeId: string; value: T }>,
    totalNodes: number,
  ): { consensus: T | null; confidence: number } {
    const maxByzantine = Math.floor((totalNodes - 1) / 3);
    const requiredAgreement = 2 * maxByzantine + 1;

    // Đếm frequency mỗi response value
    const valueCounts = new Map<string, { value: T; count: number }>();

    for (const resp of responses) {
      const key = JSON.stringify(resp.value);
      const existing = valueCounts.get(key);
      if (existing) {
        existing.count++;
      } else {
        valueCounts.set(key, { value: resp.value, count: 1 });
      }
    }

    // Tìm giá trị có nhiều agreement nhất
    let maxEntry: { value: T; count: number } | null = null;
    for (const entry of valueCounts.values()) {
      if (!maxEntry || entry.count > maxEntry.count) {
        maxEntry = entry;
      }
    }

    if (maxEntry && maxEntry.count >= requiredAgreement) {
      return {
        consensus: maxEntry.value,
        confidence: maxEntry.count / responses.length,
      };
    }

    return { consensus: null, confidence: 0 };
  }
}
```

## Consistency Models Spectrum

> Consistency model định nghĩa **hợp đồng** giữa distributed system và client:
> "Client sẽ thấy data như thế nào khi đọc sau khi ghi?"

### Từ strong nhất đến weak nhất

```
Strong ← ─────────────────────────────────────── → Weak

Linearizability
  │  Sequential Consistency
  │    │  Causal Consistency
  │    │    │  Read-your-writes
  │    │    │    │  Monotonic reads
  │    │    │    │    │  Eventual Consistency
  │    │    │    │    │    │
  ▼    ▼    ▼    ▼    ▼    ▼
 Dễ reason    ────────────→     Hiệu năng cao
 Latency cao  ────────────→     Latency thấp
```

### 1. Linearizability (Strong Consistency)

Mạnh nhất. Mọi operation dường như xảy ra **tại một thời điểm duy nhất** giữa invocation và response. Như thể chỉ có một bản copy của data.

```typescript
// Linearizability: Mọi read thấy write gần nhất nhất
// Ví dụ: Account balance PHẢI linearizable

interface LinearizableStore<T> {
  // Read luôn trả về giá trị mới nhất đã committed
  read(key: string): Promise<T>;
  // Write: sau khi return, mọi read tiếp theo PHẢI thấy giá trị này
  write(key: string, value: T): Promise<void>;
  // Compare-and-swap: atomic read-modify-write
  cas(key: string, expected: T, desired: T): Promise<boolean>;
}

// Use case: account balance, inventory count, leader election
// Systems: ZooKeeper, etcd, Spanner
```

### 2. Sequential Consistency

Yếu hơn linearizability. Mọi operation **có thể reorder**, nhưng phải giữ **program order** của mỗi process. Không cần real-time ordering.

```typescript
// Sequential consistency: giữ order trong mỗi process,
// nhưng cross-process order có thể khác real-time

// Process A: write(x, 1) → write(x, 2)
// Process B: read(x)     → read(x)
//
// Linearizable: Nếu write(x,2) hoàn thành trước read(x),
//               read(x) PHẢI trả về 2
//
// Sequential:   read(x) có thể trả về 1 rồi 2, hoặc 2 rồi 2
//               Nhưng KHÔNG THỂ trả về 2 rồi 1 (vi phạm process order)
```

### 3. Causal Consistency

Chỉ giữ ordering cho các events có **quan hệ nhân quả**. Events không liên quan có thể thấy theo thứ tự khác nhau ở các nodes khác nhau.

```typescript
// Causal consistency: Nếu A causes B, mọi node thấy A trước B
// Nhưng events không liên quan có thể thấy theo thứ tự khác

interface CausalStore {
  write(key: string, value: string, causalContext: CausalContext): Promise<CausalContext>;
  read(key: string, causalContext: CausalContext): Promise<{ value: string; context: CausalContext }>;
}

// Ví dụ: Social media comments
// User A: Post "Hello"           (event 1)
// User A: Comment "First!"       (event 2, caused by event 1)
// User B: Comment "Nice post!"   (event 3, caused by event 1)
//
// Causal consistency đảm bảo:
// - Mọi người thấy "Hello" trước "First!" (causal relationship)
// - Mọi người thấy "Hello" trước "Nice post!" (causal relationship)
// - "First!" và "Nice post!" có thể thấy theo thứ tự khác nhau (concurrent)

class CausalSession {
  private context: VectorClock;

  constructor(private readonly store: CausalStore) {
    this.context = new VectorClock();
  }

  async write(key: string, value: string): Promise<void> {
    // Mỗi write mang theo causal context hiện tại
    const newContext = await this.store.write(key, value, this.context);
    this.context = newContext; // cập nhật context
  }

  async read(key: string): Promise<string> {
    // Read với context → chỉ nhận data SAU context hiện tại
    const { value, context } = await this.store.read(key, this.context);
    this.context = VectorClock.merge(this.context, context);
    return value;
  }
}
```

### 4. Read-Your-Writes Consistency

Đảm bảo một process luôn thấy **writes của chính nó**. Không đảm bảo gì về writes của process khác.

```typescript
// Read-your-writes: Tôi luôn thấy những gì tôi đã viết

// Problem: Update profile → refresh → thấy data cũ!
// Solution: Read-your-writes consistency

class UserProfileService {
  constructor(
    private readonly primary: DatabaseClient,   // write target
    private readonly replica: DatabaseClient,    // read target (có thể lag)
  ) {}

  async updateProfile(userId: string, data: ProfileUpdate): Promise<void> {
    await this.primary.update('profiles', userId, data);
    // Lưu write timestamp cho user này
    await this.sessionStore.set(
      `last_write:${userId}`,
      Date.now().toString(),
      { ttl: 30 } // 30 seconds
    );
  }

  async getProfile(userId: string, sessionUserId: string): Promise<Profile> {
    if (userId === sessionUserId) {
      // Đọc profile CỦA CHÍNH MÌNH → đọc từ primary
      const lastWrite = await this.sessionStore.get(`last_write:${userId}`);
      if (lastWrite && Date.now() - parseInt(lastWrite) < 30_000) {
        return this.primary.findById('profiles', userId);
      }
    }
    // Đọc profile NGƯỜI KHÁC → đọc từ replica (fast)
    return this.replica.findById('profiles', userId);
  }
}
```

### 5. Eventual Consistency

Yếu nhất. Chỉ đảm bảo: nếu không có write mới, **cuối cùng** mọi read sẽ trả về giá trị cuối cùng. "Cuối cùng" có thể là milliseconds hoặc minutes.

```typescript
// Eventual consistency: data SẼ đồng bộ... eventually

// DNS là ví dụ điển hình nhất:
// - Update DNS record
// - Mất 0-72 giờ để propagate toàn cầu
// - Trong thời gian đó, user khác nhau thấy IP khác nhau

// CDN cache invalidation:
// - Update file trên origin
// - Edge nodes vẫn serve cached version
// - TTL hết → fetch từ origin → eventually consistent
```

### Chọn consistency model nào cho use case nào?

```typescript
// Decision framework
function chooseConsistencyModel(requirements: SystemRequirements): ConsistencyModel {
  // Financial transactions: account balance, payment
  if (requirements.financiallyBound) {
    return 'linearizable';
    // Cost: higher latency, lower throughput
  }

  // User-facing reads after writes: profile update, settings
  if (requirements.userSeesOwnWrites) {
    return 'read-your-writes';
    // Cost: need session tracking or sticky routing
  }

  // Social features: comments, reactions, feeds
  if (requirements.preserveCausality) {
    return 'causal';
    // Cost: need vector clocks or dependency tracking
  }

  // Content delivery, caching, analytics
  if (requirements.highThroughputLowLatency) {
    return 'eventual';
    // Cost: users may see stale data temporarily
  }

  // Default: strong enough for most applications
  return 'read-your-writes';
}
```
