## Technical Debt

### Phân loại Technical Debt

```
1. DELIBERATE + PRUDENT (Good debt):
   "Chúng ta biết design này không optimal, nhưng ship now và refactor sprint sau"
   → Acceptable: documented, planned, time-boxed

2. DELIBERATE + RECKLESS (Dangerous debt):
   "Không có thời gian viết tests, deploy thôi"
   → Nguy hiểm: accumulates interest fast

3. INADVERTENT + PRUDENT (Learning debt):
   "Bây giờ mới hiểu cách tốt hơn để structure module này"
   → Natural: refactor khi touch lại code

4. INADVERTENT + RECKLESS (Mess):
   "Design pattern nào? Layer nào?"
   → Không phải debt, là chaos. Cần training + standards.
```

### Đo lường Technical Debt

```typescript
// Signals that debt is accumulating:

// 1. Velocity declining
// Sprint 1: 30 story points
// Sprint 5: 25 story points
// Sprint 10: 15 story points ← Same team, less output

// 2. Bug rate increasing
// Month 1: 5 bugs reported
// Month 6: 20 bugs reported ← Fragile codebase

// 3. Lead time increasing
// "Adding a new field used to take 1 hour, now takes 2 days"

// 4. Code metrics
// Cyclomatic complexity increasing
// Test coverage decreasing
// Build time increasing
// Deployment frequency decreasing

// Track debt explicitly:
interface TechDebtItem {
  id: string;
  title: string;
  description: string;
  area: string;                    // 'database' | 'api' | 'auth' | 'frontend'
  severity: 'low' | 'medium' | 'high' | 'critical';
  estimatedEffort: string;         // '2h' | '1d' | '1w' | '1sprint'
  interestRate: string;            // "Costs us ~2h/sprint in workarounds"
  createdAt: Date;
  resolvedAt?: Date;
}

// Maintain a tech debt register (wiki page, Linear project, etc.)
// Review monthly: is debt growing? Which items cause most pain?
```

### Managing Technical Debt

```
Strategy 1: The "20% Rule"
  Allocate 20% of sprint capacity to tech debt reduction.
  Every sprint: 80% features + 20% debt paydown.
  → Sustainable, prevents debt accumulation.

Strategy 2: The "Boy Scout Rule"
  Leave code better than you found it.
  Working on feature X? If you touch module Y, clean it up.
  → Organic improvement, zero dedicated time needed.

Strategy 3: Debt Sprints
  Every 4th sprint = full tech debt sprint.
  → Larger refactoring possible, but features pause.

Strategy 4: Refactoring as Features
  "Refactor auth module" isn't a tech task — it's a feature:
  "Reduce login latency from 2s to 200ms by replacing auth module"
  → Gets prioritized alongside business features.

Which to use? Combine 1 + 2 as default.
Add 3 when debt is clearly blocking feature delivery.
Use 4 for major architectural changes.
```

## Refactoring Strategies

### Strangler Fig — Replace incrementally

```typescript
// Replace legacy system piece by piece, not big bang rewrite

// Phase 1: New code handles NEW features
// Legacy handles all existing features
// New system proxies unknown requests to legacy

class StranglerProxy {
  constructor(
    private readonly newSystem: RequestHandler,
    private readonly legacySystem: RequestHandler,
    private readonly routingRules: RoutingRule[],
  ) {}

  async handle(request: Request): Promise<Response> {
    const rule = this.routingRules.find(r => r.matches(request));

    if (rule?.target === 'new') {
      return this.newSystem.handle(request);
    }

    // Default: legacy system
    return this.legacySystem.handle(request);
  }
}

// Phase 2: Migrate existing features one by one
const routingRules: RoutingRule[] = [
  // Migrated to new system
  { path: '/api/v2/users/**', target: 'new', migratedAt: '2024-01-15' },
  { path: '/api/v2/orders/**', target: 'new', migratedAt: '2024-02-01' },

  // Still on legacy
  { path: '/api/v2/billing/**', target: 'legacy' },
  { path: '/api/v2/reports/**', target: 'legacy' },
];

// Phase 3: All traffic → new system. Decommission legacy.
// Monitoring: compare responses between old and new (shadow traffic)
```

### Branch by Abstraction

```typescript
// Refactor without long-lived feature branches

// Step 1: Create abstraction (interface) around code to change
interface NotificationSender {
  send(userId: string, message: NotificationMessage): Promise<void>;
}

// Step 2: Old implementation wraps existing code
class LegacyNotificationSender implements NotificationSender {
  async send(userId: string, message: NotificationMessage): Promise<void> {
    // Existing code, unchanged
    await this.oldEmailService.sendEmail(userId, message.subject, message.body);
  }
}

// Step 3: New implementation built alongside
class ModernNotificationSender implements NotificationSender {
  async send(userId: string, message: NotificationMessage): Promise<void> {
    const channels = await this.preferences.getChannels(userId);
    await Promise.all(channels.map(ch => ch.send(userId, message)));
  }
}

// Step 4: Feature flag to switch
class NotificationSenderFactory {
  create(userId: string): NotificationSender {
    if (featureFlags.isEnabled('modern-notifications', userId)) {
      return new ModernNotificationSender(/* ... */);
    }
    return new LegacyNotificationSender(/* ... */);
  }
}

// Step 5: Gradually roll out (1% → 10% → 50% → 100%)
// Step 6: Remove old implementation and feature flag

// Benefits:
// - Main branch always deployable
// - Gradual rollout, easy rollback
// - Old and new coexist safely
```

## Migration Patterns

### Database Migration (Large-scale)

```typescript
// Migrating from MySQL to PostgreSQL — zero downtime

// Phase 1: Dual Write
// Write to BOTH old (MySQL) and new (PostgreSQL)
class DualWriteRepository implements UserRepository {
  constructor(
    private readonly mysql: MysqlUserRepo,
    private readonly postgres: PostgresUserRepo,
  ) {}

  async save(user: User): Promise<void> {
    // Write to both, primary = MySQL (current source of truth)
    await this.mysql.save(user);
    try {
      await this.postgres.save(user);
    } catch (error) {
      // Log but don't fail — PostgreSQL is secondary
      logger.error('Dual write to PostgreSQL failed', { userId: user.id, error });
    }
  }

  async findById(id: string): Promise<User | null> {
    // Read from MySQL (still source of truth)
    return this.mysql.findById(id);
  }
}

// Phase 2: Backfill historical data to PostgreSQL
// Phase 3: Shadow reads — read from both, compare, alert on differences
// Phase 4: Switch reads to PostgreSQL
// Phase 5: Switch writes to PostgreSQL (new source of truth)
// Phase 6: Remove MySQL writes
// Phase 7: Decommission MySQL
```

### Framework Migration

```typescript
// Migrating from Express to Fastify — route by route

// Shared: mount both frameworks
import express from 'express';
import fastify from 'fastify';

const expressApp = express();
const fastifyApp = fastify();

// Migrated routes → Fastify
fastifyApp.get('/api/v2/users/:id', async (request, reply) => {
  const user = await userService.findById(request.params.id);
  return user ? reply.send(user) : reply.status(404).send({ error: 'Not found' });
});

// Not yet migrated → Express
expressApp.get('/api/v2/orders/:id', orderController.getById);

// Reverse proxy: try Fastify first, fall back to Express
const server = http.createServer(async (req, res) => {
  if (isMigratedRoute(req.url)) {
    // Inject into Fastify
    fastifyApp.server.emit('request', req, res);
  } else {
    // Inject into Express
    expressApp(req, res);
  }
});

// Migrate route by route, test each one, until Express is empty
```

## Backward Compatibility

### API Backward Compatibility

```typescript
// NEVER break existing clients. EVER.

// Adding fields → backward compatible ✅
// Response v1: { id, name, email }
// Response v2: { id, name, email, phone }  // New field, old clients ignore it

// Removing fields → BREAKING ❌
// Instead: deprecate, give clients time to migrate

// Changing types → BREAKING ❌
// Instead: new field with new type

// Versioning for breaking changes:
// /api/v1/users → old format
// /api/v2/users → new format
// Run both for 6+ months, then deprecate v1

// Deprecated field handling:
interface UserResponseV2 {
  id: string;
  name: string;         // Still present
  firstName: string;    // New field
  lastName: string;     // New field
  /** @deprecated Use firstName + lastName instead. Will be removed 2025-01-01. */
  fullName?: string;    // Deprecated but still returned for backward compat
}
```

### Database Backward Compatibility

```sql
-- SAFE migrations (backward compatible):
ALTER TABLE users ADD COLUMN phone VARCHAR(20);           -- Add column ✅
ALTER TABLE users ALTER COLUMN bio SET DEFAULT '';         -- Add default ✅
CREATE INDEX idx_users_phone ON users(phone);             -- Add index ✅

-- UNSAFE migrations (may break running code):
ALTER TABLE users DROP COLUMN old_field;                  -- Drop column ❌
ALTER TABLE users ALTER COLUMN name TYPE TEXT;             -- Change type ❌
ALTER TABLE users RENAME COLUMN name TO full_name;        -- Rename ❌

-- SAFE way to rename a column:
-- Step 1: Add new column
ALTER TABLE users ADD COLUMN full_name VARCHAR(100);
-- Step 2: Backfill data
UPDATE users SET full_name = name;
-- Step 3: Deploy code that writes to BOTH columns
-- Step 4: Deploy code that reads from new column
-- Step 5: Drop old column (weeks later, after all code deployed)
ALTER TABLE users DROP COLUMN name;
```

## System Lifecycle

```
Phase 1: EXPLORATION (0-6 months)
  - MVP, prototype, validate idea
  - Monolith, simple stack, move fast
  - Tech debt: acceptable, speed matters
  - Architecture: whatever ships fastest

Phase 2: GROWTH (6-24 months)
  - Product-market fit found, scaling users
  - Modular monolith, add caching, optimize DB
  - Tech debt: start paying down, establish standards
  - Architecture: modularize, add monitoring, CI/CD

Phase 3: MATURITY (2-5 years)
  - Stable product, multiple teams
  - Consider extracting services (if data supports it)
  - Tech debt: systematic management, 20% rule
  - Architecture: CQRS for complex domains, event-driven for decoupling

Phase 4: EVOLUTION (5+ years)
  - Legacy system with new requirements
  - Strangler fig for modernization
  - Tech debt: constant battle, needs executive support
  - Architecture: gradual migration, don't rewrite from scratch

The WORST decision: "Let's rewrite everything from scratch"
  - Takes 2x longer than estimated
  - New system has different bugs, not fewer
  - Business features frozen during rewrite
  - Team morale drops

The BEST approach: Incremental improvement
  - Replace components one at a time
  - Each replacement delivers value immediately
  - Old system continues working during migration
  - Learn and adjust as you go
```
