## Test Pyramid vs Trophy vs Diamond

### Test Pyramid (Mike Cohn, 2009)

```
         /  E2E  \           ← Ít, chậm, đắt
        /----------\
       / Integration \       ← Vừa phải
      /----------------\
     /    Unit Tests     \   ← Nhiều, nhanh, rẻ
    /____________________\
```

**Khi nào phù hợp:** Domain logic phức tạp (financial calculations, rule engines), libraries/frameworks.

```typescript
// Pyramid hoạt động tốt khi domain logic phức tạp — test từng rule rẻ, nhanh
class PricingCalculator {
  calculateDiscount(order: Order, customer: Customer): Money {
    if (customer.tier === 'platinum' && order.total.isGreaterThan(Money.of(1000))) {
      return order.total.multiply(0.15);
    }
    if (customer.isFirstOrder()) return Money.of(10);
    if (order.items.length > 5) return order.total.multiply(0.05);
    return Money.zero();
  }
}

describe('PricingCalculator', () => {
  const calculator = new PricingCalculator();

  it('gives 15% for platinum customers with orders over $1000', () => {
    const order = OrderBuilder.create().withTotal(Money.of(2000)).build();
    const customer = CustomerBuilder.create().withTier('platinum').build();
    expect(calculator.calculateDiscount(order, customer)).toEqual(Money.of(300));
  });
});
```

### Testing Trophy (Kent C. Dodds, 2018)

```
         /  E2E  \           ← Ít
        / Integration \      ← NHIỀU NHẤT — sweet spot
       /   Tests        \
      |   Unit Tests     |   ← Vừa phải
      |  Static Analysis |   ← TypeScript + ESLint
```

**Khi nào phù hợp:** Web apps, API servers, CRUD-heavy services. TypeScript strict mode đã bắt nhiều lỗi type-level.

### Testing Diamond (2020s, microservices)

```
         /  E2E  \           ← Rất ít (smoke tests)
        / Integration \      ← NHIỀU NHẤT
       /   Tests        \
          / Unit \           ← Ít (chỉ complex logic)
```

**Khi nào phù hợp:** Microservices nhỏ gọn, service chủ yếu orchestrate, data-intensive apps.

### Chọn model nào?

```
┌─────────────────────────┬──────────┬─────────┬─────────┐
│ Đặc điểm dự án         │ Pyramid  │ Trophy  │ Diamond │
├─────────────────────────┼──────────┼─────────┼─────────┤
│ Complex domain logic    │    ✅    │         │         │
│ CRUD/API service        │          │   ✅    │   ✅    │
│ Frontend (React/Vue)    │          │   ✅    │         │
│ Microservice nhỏ        │          │         │   ✅    │
│ Library/Framework       │    ✅    │         │         │
└─────────────────────────┴──────────┴─────────┴─────────┘
```

> **Thực tế:** Hầu hết production systems dùng **hybrid**. Pyramid cho domain logic, Trophy cho API layer, Diamond cho infrastructure services.

## Cost of Testing: ROI Analysis

### Ma trận ROI

```
        Effort to Write & Maintain
              Low          High
         ┌────────────┬────────────┐
  High   │  ★ SWEET   │  CAREFUL   │
  Value   │   SPOT     │  DECISION  │
         ├────────────┼────────────┤
  Low    │  NICE TO   │  ❌ AVOID  │
  Value   │   HAVE     │            │
         └────────────┴────────────┘
```

### Ranking test types theo ROI

```typescript
// 1. STATIC TYPES (TypeScript) — ROI cao nhất, gần như miễn phí
// 2. UNIT TESTS cho pure business logic — ROI rất cao, effort thấp
// 3. INTEGRATION TESTS cho critical paths — ROI cao, effort trung bình
// 4. CONTRACT TESTS — ROI cao trong microservices
// 5. E2E TESTS cho happy paths — ROI trung bình, effort cao
// 6. UNIT TESTS cho glue code — ROI thấp ❌ (controller chỉ gọi service)
// 7. E2E TESTS cho edge cases — ROI rất thấp ❌
```

### Quy tắc 80/20

```
80% confidence đến từ:
├── TypeScript strict mode (free)
├── 20-30 integration tests cho critical paths
├── Unit tests cho complex business rules
└── 3-5 E2E smoke tests

20% còn lại đòi hỏi hàng trăm tests thêm → Tùy dự án có đáng đầu tư không.
```

## What to Test vs What NOT to Test

### PHẢI test (high value)

```typescript
// 1. Business rules — sai = mất tiền thật
class LoanApprovalService {
  evaluate(application: LoanApplication): ApprovalDecision {
    if (application.creditScore < 600) return ApprovalDecision.rejected('Credit too low');
    if (application.debtToIncomeRatio > 0.43) return ApprovalDecision.rejected('DTI too high');
    return ApprovalDecision.approved(application.requestedAmount);
  }
}

// 2. Data transformations — external API thay đổi format là vỡ
// 3. Edge cases và error handling — empty arrays, null, boundaries
// 4. Integration points — DB queries, API calls, message publishing
```

### KHÔNG NÊN test (low value)

```typescript
// ❌ Implementation details (service gọi repo.save() bao nhiêu lần)
// ❌ Trivial getters/setters — TypeScript đã đảm bảo type
// ❌ Framework code — Express routing, TypeORM save()
// ❌ Glue code không có logic — controller chỉ forward request
// ❌ Private methods — test qua public interface
```

## Testing Behaviors, Not Implementations

```typescript
// ❌ Testing IMPLEMENTATION — brittle, breaks on refactor
it('should call hashPassword, then save to repository', async () => {
  const mockHasher = jest.fn().mockResolvedValue('hashed123');
  const mockRepo = { save: jest.fn() };
  const service = new UserService(mockHasher, mockRepo);
  await service.register({ email: 'a@b.com', password: '123' });
  expect(mockHasher).toHaveBeenCalledWith('123');
  expect(mockRepo.save).toHaveBeenCalledWith({ email: 'a@b.com', passwordHash: 'hashed123' });
});
// → Refactor thứ tự hash/save → test fail, nhưng behavior vẫn đúng

// ✅ Testing BEHAVIOR — stable, survives refactoring
describe('User Registration', () => {
  it('registers a user and stores password securely', async () => {
    const service = createUserService(testDependencies);
    const user = await service.register({ email: 'alice@example.com', password: 'SecureP@ss1' });

    expect(user.email).toBe('alice@example.com');
    const stored = await testDb.findUser(user.id);
    expect(stored.passwordHash).not.toBe('SecureP@ss1'); // hashed!

    const authenticated = await service.authenticate('alice@example.com', 'SecureP@ss1');
    expect(authenticated).toBe(true);
  });

  it('rejects duplicate email addresses', async () => {
    const service = createUserService(testDependencies);
    await service.register({ email: 'alice@example.com', password: 'Pass1' });
    await expect(
      service.register({ email: 'alice@example.com', password: 'Pass2' }),
    ).rejects.toThrow(DuplicateEmailError);
  });
});
```

### Heuristic: Test name nên đọc như specification

```typescript
// ❌ 'calls validateEmail then hashPassword then repository.save'
// ✅ 'registers a new user with a valid email'
// ✅ 'rejects transfer when sender has insufficient balance'
// ✅ 'applies bulk discount when order contains more than 10 items'
```

## Test-Driven Development (TDD)

### Cycle: Red → Green → Refactor

```
  RED:      Viết test mô tả behavior → FAIL
  GREEN:    Viết code TỐI THIỂU → PASS
  REFACTOR: Cải thiện code, giữ test xanh → Lặp lại
```

### Khi TDD giúp ích

```typescript
// 1. Complex business logic — TDD forces nghĩ rõ requirements
it('rejects coupon already used by this customer', async () => {
  const coupon = await createCoupon({ code: 'SAVE10', maxUses: 1 });
  const customer = await createCustomer();
  await applyDiscount(customer, coupon); // OK lần đầu
  await expect(applyDiscount(customer, coupon)).rejects.toThrow(CouponAlreadyUsedError);
});

// 2. Bug fixes — viết test reproduce bug trước, fix sau, bug never returns
// 3. API design — thiết kế interface từ góc nhìn consumer
```

### Khi TDD gây hại

```
❌ Prototyping — chưa biết solution, TDD chậm bạn lại
❌ UI development — UI thay đổi quá nhanh
❌ Glue code — không có logic để test-first
❌ Team chưa quen — learning curve gây resistance
```

### Biến thể thực dụng

```
Test-First (TDD thuần): business logic, bug fixes, well-defined requirements
Test-During:            hầu hết development hàng ngày
Test-After:             prototypes đã stabilize, legacy code cần safety net
```

## Flaky Tests

### Flaky = có lúc pass, có lúc fail, cùng code — PHÁ HỦY TRUST

```typescript
// Top nguyên nhân và fix:

// 1. TIME DEPENDENCY → inject FakeClock thay vì dùng Date.now()
it('expires token after 1 hour', () => {
  const clock = new FakeClock(new Date('2024-01-01T00:00:00Z'));
  const token = createToken({ clock });
  clock.advance({ hours: 1, seconds: 1 });
  expect(token.isExpired()).toBe(true); // Deterministic
});

// 2. SHARED STATE → mỗi test tạo data riêng
it('deactivates user', async () => {
  const user = await createUser({ active: true }); // own data, not shared
  await updateUser(user.id, { active: false });
  expect((await getUser(user.id)).active).toBe(false);
});

// 3. RACE CONDITIONS → use waitFor utility
it('processes event', async () => {
  publishEvent('order.created', order);
  await waitFor(async () => {
    const result = await getOrder(order.id);
    expect(result.status).toBe('confirmed');
  }, { timeout: 5000, interval: 100 });
});

// 4. NETWORK CALLS → mock external dependencies (MSW)
// 5. TEST ORDER DEPENDENCY → mỗi test self-contained
// 6. RESOURCE EXHAUSTION → proper cleanup in afterEach
```

### Quản lý trong team

```
1. QUARANTINE: Flaky test → tag "flaky" → không block CI
2. FIX OR DELETE: > 1 tuần không fix → DELETE
3. RULE: Không merge PR thêm flaky test mới
```

## Test Speed

### Ngưỡng tâm lý

```
< 1s    → TDD khả thi, chạy liên tục
< 10s   → Chạy trước mỗi commit
< 5min  → CI chạy mỗi PR
> 10min → Developer SKIP test → push & pray
```

### Chiến lược giữ nhanh

```typescript
// 1. PARALLELIZE — maxWorkers: '75%'
// 2. IN-MEMORY DB cho unit tests (SQLite :memory:)
// 3. SELECTIVE — vitest --changed (chỉ tests liên quan)
// 4. LAYER — test:unit (<5s) → test:integration (<30s) → test:e2e (<2min)
// 5. REUSE — app instance shared, isolate via transaction rollback
const app = createFullApp(); // once
beforeEach(() => testDb.beginTransaction());
afterEach(() => testDb.rollbackTransaction());
```

## Testing Quadrant (Brian Marick)

```
                  Business-Facing
                       │
          Q2           │           Q3
  Functional Tests     │     Exploratory Testing
  Acceptance Tests     │     Usability Testing
  Story Tests          │     UAT, Alpha/Beta
                       │
  ── Supporting ───────┼─────── Critiquing ──
     Development       │        the Product
                       │
          Q1           │           Q4
  Unit Tests           │     Performance Tests
  Integration Tests    │     Security Tests
  Component Tests      │     Load Tests
                       │
                  Technology-Facing
```

### Cân bằng 4 quadrants

```
Q1 (Unit/Integration): Mỗi PR            → Developer owned
Q2 (Acceptance):       Mỗi release        → Dev + QA owned
Q3 (Exploratory):      Mỗi sprint         → QA + Product owned
Q4 (Performance/Sec):  Weekly/pre-release  → Platform/SRE owned

Thiếu Q1: Developers sợ refactor
Thiếu Q2: Features ship nhưng sai requirements
Thiếu Q3: Bugs lạ lọt production (automated tests miss human insights)
Thiếu Q4: Hệ thống chậm/không an toàn dưới load
```

## Tổng kết

```
1. Chọn model (Pyramid/Trophy/Diamond) PHÙ HỢP dự án, không dogmatic
2. Đầu tư vào tests có ROI cao nhất — pure logic + critical paths
3. Test BEHAVIOR, không test implementation
4. Tests = documentation sống — viết để người sau ĐỌC HIỂU
5. TDD là CÔNG CỤ, không phải TÔN GIÁO
6. Flaky tests = cancer — quarantine, fix, hoặc delete
7. Test speed = developer experience — chậm = skip
8. Cover cả 4 quadrants — automated không thay thế human judgment
```
