## Schema Design Principles

### Normalize nhưng đừng cuồng tín

```sql
-- 3NF (Third Normal Form) — mặc định cho write-heavy, transactional data

-- ✅ Normalized: no data duplication, update in one place
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  total_cents INTEGER NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID REFERENCES orders(id) NOT NULL,
  product_id UUID REFERENCES products(id) NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  unit_price_cents INTEGER NOT NULL,
  -- Snapshot price tại thời điểm đặt hàng
  -- KHÔNG join product.price vì price thay đổi
);

-- Denormalize KHI CẦN cho read performance
-- Ví dụ: order_items LƯU unit_price_cents thay vì join products
-- vì historical price matters, không phải current price
```

## SQL vs NoSQL

| Tiêu chí | SQL (PostgreSQL) | Document (MongoDB) | Key-Value (Redis) | Wide-Column (Cassandra) |
|----------|------------------|--------------------|--------------------|-----------------------|
| **Data model** | Relational tables | JSON documents | Key → Value | Column families |
| **Schema** | Strict, enforced | Flexible, optional | Schemaless | Schema per column family |
| **Queries** | Complex JOIN, aggregation | Document queries, aggregation pipeline | GET/SET by key | Partition key queries |
| **Transactions** | Full ACID | Single-doc ACID, multi-doc limited | Limited (MULTI) | Lightweight transactions |
| **Scaling** | Vertical (+ read replicas) | Horizontal (sharding) | Horizontal (cluster) | Horizontal (masterless) |
| **Best for** | General purpose, transactions | Content, catalogs, user profiles | Cache, sessions, rate limiting | Time series, IoT, high write throughput |

### Decision Matrix

```
Structured data + relationships + ACID? → PostgreSQL
Flexible schema + rapid iteration? → MongoDB
Cache + sessions + counters + pub/sub? → Redis
Time series + high write throughput? → Cassandra/ScyllaDB
Full-text search + analytics? → Elasticsearch
Graph relationships? → Neo4j
```

### Polyglot Persistence — Dùng nhiều databases

```typescript
// Real-world: mỗi use case dùng DB phù hợp nhất

class ProductService {
  constructor(
    private readonly postgres: Pool,      // Source of truth, transactions
    private readonly redis: Redis,         // Cache hot data
    private readonly elasticsearch: Client, // Full-text search
  ) {}

  async createProduct(input: CreateProductInput): Promise<Product> {
    // Write to PostgreSQL (source of truth)
    const product = await this.postgres.query(
      'INSERT INTO products (...) VALUES (...) RETURNING *',
      [input.name, input.description, input.price],
    );

    // Index in Elasticsearch (searchable)
    await this.elasticsearch.index({
      index: 'products',
      id: product.id,
      body: { name: product.name, description: product.description, category: product.category },
    });

    // Warm cache
    await this.redis.set(`product:${product.id}`, JSON.stringify(product), 'EX', 3600);

    return product;
  }

  async search(query: string): Promise<Product[]> {
    // Search in Elasticsearch (optimized for full-text)
    const results = await this.elasticsearch.search({
      index: 'products',
      body: { query: { multi_match: { query, fields: ['name^2', 'description'] } } },
    });
    return results.hits.hits.map(hit => hit._source as Product);
  }

  async getById(id: string): Promise<Product | null> {
    // Try cache first (Redis)
    const cached = await this.redis.get(`product:${id}`);
    if (cached) return JSON.parse(cached);

    // Fall back to PostgreSQL
    const result = await this.postgres.query('SELECT * FROM products WHERE id = $1', [id]);
    const product = result.rows[0] ?? null;

    // Warm cache for next time
    if (product) {
      await this.redis.set(`product:${id}`, JSON.stringify(product), 'EX', 3600);
    }

    return product;
  }
}
```

## Database Migration Strategy

```typescript
// Migrations = version-controlled database changes
// KHÔNG bao giờ sửa DB schema bằng tay trong production

// migration file: 20240315120000_create_users.ts
export async function up(knex: Knex): Promise<void> {
  await knex.schema.createTable('users', (table) => {
    table.uuid('id').primary().defaultTo(knex.fn.uuid());
    table.string('name', 100).notNullable();
    table.string('email', 255).notNullable().unique();
    table.enum('role', ['viewer', 'editor', 'admin']).defaultTo('viewer');
    table.enum('status', ['active', 'suspended', 'deleted']).defaultTo('active');
    table.timestamp('created_at').defaultTo(knex.fn.now());
    table.timestamp('updated_at').defaultTo(knex.fn.now());
  });
}

export async function down(knex: Knex): Promise<void> {
  await knex.schema.dropTable('users');
}

// Zero-downtime migration strategies:

// 1. ADD column (safe — backward compatible)
// Deploy new code that handles both with/without new column
// Run migration to add column
// Deploy code that uses new column

// 2. REMOVE column (dangerous — plan carefully)
// Step 1: Deploy code that STOPS USING the column
// Step 2: Wait for all old code to be replaced
// Step 3: Run migration to remove column

// 3. RENAME column (avoid — do add + migrate + remove instead)
// Step 1: Add new column
// Step 2: Deploy code that writes to BOTH columns
// Step 3: Backfill old data to new column
// Step 4: Deploy code that reads from new column only
// Step 5: Remove old column
```

## Caching Strategies

### Cache Patterns

```typescript
// === Cache-Aside (Lazy Loading) — Most common ===
// Application manages cache explicitly

async function getUser(id: string): Promise<User | null> {
  // 1. Check cache
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  // 2. Cache miss → query DB
  const user = await db.query('SELECT * FROM users WHERE id = $1', [id]);
  if (!user) return null;

  // 3. Populate cache
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // 5 min TTL

  return user;
}

// Invalidate on write
async function updateUser(id: string, data: UpdateUserInput): Promise<User> {
  const user = await db.query('UPDATE users SET ... WHERE id = $1 RETURNING *', [id, ...]);
  await redis.del(`user:${id}`); // Invalidate cache
  return user;
}

// === Write-Through — Cache updated on every write ===
async function updateUserWriteThrough(id: string, data: UpdateUserInput): Promise<User> {
  const user = await db.query('UPDATE users SET ... WHERE id = $1 RETURNING *', [id, ...]);
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // Update cache
  return user;
}

// === Write-Behind (Write-Back) — Write cache first, DB async ===
// Fastest writes, risk of data loss if cache crashes
// Use for: counters, analytics, non-critical data

class WriteBackCounter {
  constructor(
    private readonly redis: Redis,
    private readonly db: Knex,
    private readonly flushIntervalMs: number = 5000,
  ) {
    setInterval(() => this.flush(), flushIntervalMs);
  }

  async increment(key: string): Promise<number> {
    return this.redis.incr(`counter:${key}`);
  }

  private async flush(): Promise<void> {
    const keys = await this.redis.keys('counter:*');
    for (const key of keys) {
      const value = await this.redis.getdel(key);
      if (value) {
        const name = key.replace('counter:', '');
        await this.db('counters')
          .insert({ name, value: Number(value) })
          .onConflict('name')
          .merge({ value: this.db.raw('counters.value + ?', [Number(value)]) });
      }
    }
  }
}
```

### Cache Invalidation

```typescript
// "There are only two hard things in Computer Science:
//  cache invalidation and naming things." — Phil Karlton

// Strategy 1: TTL-based (simplest)
await redis.set(key, value, 'EX', 300); // Auto-expire after 5 min
// Pro: simple, self-healing
// Con: stale data for TTL duration

// Strategy 2: Event-based invalidation
eventBus.on('user:updated', async (event) => {
  await redis.del(`user:${event.userId}`);
  await redis.del(`user:email:${event.oldEmail}`);
  await redis.del('users:list:*'); // Invalidate list caches
});

// Strategy 3: Versioned cache keys
const cacheVersion = await redis.get('users:version') ?? '0';
const cacheKey = `users:list:v${cacheVersion}:page${page}`;

// On any user change:
await redis.incr('users:version'); // All old cache keys become orphaned
// Pro: atomic invalidation of all related caches
// Con: thundering herd after version bump

// Strategy 4: Stale-while-revalidate
async function getUserSWR(id: string): Promise<User | null> {
  const cached = await redis.get(`user:${id}`);
  if (cached) {
    const data = JSON.parse(cached);
    if (data._cachedAt && Date.now() - data._cachedAt > 60_000) {
      // Stale — return cached but refresh in background
      refreshInBackground(id).catch(console.error);
    }
    return data;
  }
  return fetchAndCache(id);
}
```

## Data Consistency Patterns

### Strong vs Eventual Consistency

```
Strong Consistency:
  Write → immediately visible to all readers
  Cost: latency, availability (CAP theorem)
  Use for: financial transactions, inventory counts

Eventual Consistency:
  Write → eventually visible to all readers (milliseconds to seconds)
  Cost: stale reads possible
  Use for: social feeds, analytics, search indexes, caches
```

### Optimistic Concurrency Control

```typescript
// Prevent lost updates without locking

// Database: version column
async function updateUser(id: string, data: Partial<User>, expectedVersion: number): Promise<User> {
  const result = await db.query(
    `UPDATE users
     SET name = COALESCE($1, name),
         email = COALESCE($2, email),
         version = version + 1,
         updated_at = NOW()
     WHERE id = $3 AND version = $4
     RETURNING *`,
    [data.name, data.email, id, expectedVersion],
  );

  if (result.rowCount === 0) {
    throw new ConcurrencyError('User was modified by another process. Please retry.');
  }

  return result.rows[0];
}

// API layer
app.patch('/api/users/:id', async (req, res) => {
  try {
    // Client sends version from last GET
    const user = await updateUser(req.params.id, req.body, req.body.version);
    res.json({ data: user });
  } catch (error) {
    if (error instanceof ConcurrencyError) {
      res.status(409).json({
        error: { code: 'CONFLICT', message: 'Resource was modified. Fetch latest and retry.' },
      });
    }
  }
});
```

### Transactional Outbox

```typescript
// Ensure DB write + event publish are atomic

async function placeOrder(command: PlaceOrderCommand): Promise<Order> {
  return db.transaction(async (trx) => {
    // 1. Save order (within transaction)
    const order = await trx('orders').insert({
      id: crypto.randomUUID(),
      user_id: command.userId,
      total_cents: command.totalCents,
      status: 'pending',
    }).returning('*');

    // 2. Save outbox event (within SAME transaction)
    await trx('outbox').insert({
      id: crypto.randomUUID(),
      aggregate_type: 'Order',
      aggregate_id: order[0].id,
      event_type: 'OrderPlaced',
      payload: JSON.stringify({
        orderId: order[0].id,
        userId: command.userId,
        totalCents: command.totalCents,
      }),
      created_at: new Date(),
    });

    return order[0];
    // Transaction commits → BOTH order and event are persisted atomically
    // Background worker polls outbox → publishes to message broker
  });
}
```
